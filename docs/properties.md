# プロパティの仕様

アイテムとページに付く「プロパティ」の仕様をまとめる。サーバーは `journal`、フロントエンドは `client` を前提にする。

## 1. プロパティ定義

キーごとに1つの定義を持つ。定義はSQLiteの `property_definitions` テーブルにある。

| 列 | 意味 |
|---|---|
| `key` | キー。英数字と `_` と `-` だけを使える |
| `value_type` | 型。`text` / `number` / `checkbox` / `date` / `datetime` / `bounds` / `list` / `tags` |
| `is_system` | システム管理キーなら1。ユーザーは定義を追加・変更・削除できない |
| `for_page` | ページに付けられるキーなら1 |
| `modified` | ユーザーが定義した日時（ミリ秒）。DBの版7より前からある定義は0 |
| `provisional` | 仮の定義なら1（ADR 046）。仮の定義は `settings/properties.json` に書かない |

ユーザーが消した定義は、`deleted_property_definitions(key, deleted_date)` に、消した日時とともに残る。項目の `deleted_items` と同じ形である。同じキーをユーザーが定義し直すと、その行は消える。

ユーザー定義のキーの型は、キーの名前の接尾辞で決まる（ADR 047）。接尾辞は `_n`（`number`）、`_d`（`date`）、`_dt`（`datetime`）、`_cb`（`checkbox`）、`_bounds`（`bounds`）、`_list`（`list`）で、接尾辞がなければ `text` である。型は最後の接尾辞だけで決まり、大文字の接尾辞は本体の一部として扱う。判定は共有のクレート `property-names` の `type_of` が行う。Settings画面や `POST /api/config/property-definitions` は完全な名前（`rating_n`）を受け取る。`valueType` を送れば、名前から決まる型と合うかを確かめ、合わなければ400エラーになる。送らなければ、名前から決まる型になる。名前の本体が予約の接尾辞で終わるキー（`rating_n_n`）も400エラーになる。ほかのユーザーのキーと本体が同じキー（`rating_n` があるときの `rating_d`）も400エラーになる。同じ本体は、画面で同じ名前に見えるからである。ただし、ほかの端末の定義ファイルや `.md` から届いたキーは、本体が同じでも受け入れる。画面は、本体が重なるキーにだけ型を添える（`rating (number)`）。Emacs版は、いつも本体と型を並べる。`tags` 型は `tags` キーだけが使う。

値がリストかどうかも、キーの名前で決まる（ADR 046）。`list` 型のキーの名前は `_list` で終わる（`member_list` など）。`tags` だけは例外で、`_list` で終わらない名前のリストのキーである。`_list` で終わる名前のキーを `list` 以外の型で定義したり、`_list` で終わらない名前のキーを `list` 型で定義したりすると、400エラーになる。名前で決めるのは、定義が届く前でも、どの端末も同じようにリストかどうかを決められるためである。判定は `domain::property_key::PropertyKey` が行う。

`tags` と `list` は、どちらも値の並びで、保存のしかたも同じである。型を分けているのは、UIが値をデータ型だけで見分けて、`tags` 型の値を `#` 付きで表示できるようにするためである。`tags` 型にはキーの名前を見なくてもタグの見た目を与えられ、`list` 型はただの値の並びとして表示する。

型は名前で決まるので、変わらない。既存キーに別の型で値を送っても定義は変わらない。起動のたびに、名前と型の合わないユーザー定義（ADR 047より前の端末で定義された `rating` の `number` など）は、名前から決まる型に直す。ただし、リストとスカラーの間では変えない。値は送った型ではなく、定義の型でチェックして保存する。例えば `number` のキーに `valueType: "text"` で数値でない値を送ると400エラーになる。

### システム管理キー

| キー | 型 | ページで使えるか | 誰が書くか |
|---|---|---|---|
| `tags` | tags | 使える | アイテムではサーバーが本文の `#hashtag` から作る。ページではユーザーが編集する。以前は `tag` という名前だった（起動時のマイグレーションで `tags` に変わる） |
| `begin` | datetime | 使えない | サーバー。タスクの開始時刻 |
| `end` | datetime | 使えない | サーバー。タスクの終了時刻。あればタスクは完了扱い |
| `plan` | date | 使えない | サーバー。タスクの予定日。日次ジャーナルの項目がタスクになったときに、タスクの切り替えと同じトランザクションで、その日の日付を書く（ADR 011） |
| `due` | date | 使えない | タスクの期限。今はMCPから付けるだけで、読む処理はない |
| `cancelled` | date | 使えない | タスクを中止した日。今はMCPから付けるだけで、読む処理はない |
| `zoom` | number | 使えない | フロントエンド。Shift+ホイールの拡大率 |
| `id` | text | 使えない | ページファイルのfrontmatter |
| `created` | datetime | 使える | ページの作成日時。`pages.created_date` そのもので、ページのプロパティとして編集できる |
| `modified` | datetime | 使える | ページの更新日時。`pages.modified_date` そのもので、ページのプロパティとして編集できる |
| `published` | datetime | 使える | ユーザー。ページを公開した日時。左カラムのページ一覧はこの値で並び替えられる。無いページは `modified` で代用する |
| `atlas_bounds` | bounds | 使えない | フロントエンド。atlasページの項目のうち、カードとコールアウトの位置と大きさ。`x,y` は中央の座標で、原点はキャンバスの中央。yは下向きが正。`height` は倍率を表し、倍率1は `40`。倍率の下限は0.5で、上限はない。`width` が0なら、カードの幅はラベルの長さで決まる。0でなければ、それがカードの幅になる。初めて置いたカードは `0,40` になる。Ctrl＋wheelでカードを拡大縮小すると、`height` だけが変わり、`width` は0になる |
| `atlas_type` | text | 使えない | フロントエンド。atlasページの項目の見た目の種類。今は `callout`（コールアウト）だけである。ないときは、ふつうのカードである |
| `atlas_side` | text | 使えない | フロントエンド。グループのタイトルを沿わせる辺か、コールアウトのフキダシを置く辺。`top` / `bottom` / `left` / `right` のどれかで、ないときは `top` として読む |

### atlasページの本文

atlasページ（ディレクトリの `index_atlas.md`）は、ほかのページと同じ普通のページである（ADR 053）。サーバーは、本文を自分では書かない。ページを作っても、名前を変えても、動かしても、消しても、atlasの本文は変わらない。開発者は、アウトラインでも `.md` でも、自由に編集できる。atlasは、このページの項目の木を平面に描くビューである。

新しく作ったatlasページは、ほかのページと同じく、空の項目を1つ持つ。`index_atlas.md` にも、ほかのページと同じく項目ごとの更新日時を書き、取り込むときは項目ごとに突き合わせる。

今の画面は、項目を次のように読む。

- ページカード: 1行目が1つのwiki link（`[[パス]]`）だけの項目。リンク先がatlasと同じディレクトリのページなら青、ほかのディレクトリなら薄いオレンジで描く。子のフォルダの `index` へのカードも、青で描く。atlasと同じディレクトリにないページへのカードは、ページの一覧を読み終えたあとに灰色で描き、押しても何も開かない。ただし、`today` へのカードは、どのatlasでもオレンジで描き、押すと今日のページが開く。ほかのディレクトリのページへのカードには、リンクのラベルを出す。本文がwiki linkなので、ページのバックリンクにatlasページが出る。
- ノーマルカード: 1行目が1つのwiki linkだけではない項目。薄い黄色で描き、1行目をラベルにする。1行目のリンクは、押すとページのリンクと同じく開く。カード自体は何も開かない。何も書いていない項目は描かない。
- グループ: 子を持つ項目で、本文の1行目がタイトルである。どの項目も親になれ、入れ子の深さに上限はない。入れ子のグループは、外のグループの内側に描く。プロパティに `atlas_side` を持つ。親がページカードなら、タイトルはそのページの名前とアイコンで、押すとそのページを開く。親がコールアウトなら、タイトルの代わりに、キャラクターとフキダシをグループの `atlas_side` の辺に描く。
- コールアウト: `atlas_type=callout` の項目で、本文がテキストである。プロパティに `atlas_bounds`（`x,y,0,40×倍率`）と `atlas_side` を持つ。

カードの右クリックのメニューの「Show Text」で、項目の全文を、ページの本文と同じ見た目でポップアップに出す。

`atlas_bounds` のないカードとコールアウトは、atlasに描かない。右サイドバーの「座標のない項目」に、項目の順に出す。atlasに置くと、その項目に `atlas_bounds` を足す。親の項目は、下の項目を囲んで描かれ、自分の `atlas_bounds` を持たないので、「座標のない項目」には出ない。

atlasと同じディレクトリのページのうち、どのページカードからもリンクされていないものは、右サイドバーの「未追加の項目」に出す。`atlas_bounds` のない項目のリンクと、親の項目のリンクも数える。コールアウトの本文のリンクと、ノーマルカードの文中のリンクは数えない。atlasページ自身は出さない。ディレクトリ自身の `index` は、ほかのページより先に出す。未追加の項目をatlasに置くと、そのページへのwiki linkの項目を作る。

### 古い形からの移行

以前のサーバーは、atlasの本文を自分で作っていた。その形のatlasは、次のときに普通のページの形に移す。

- サーバーを起動したとき。DBにある古い形のatlasを、すべて移す。
- 古い形の `index_atlas.md` を取り込んだとき。取り込んだあとに、同じ書き換えを当てる。

`atlas_page`、`atlas_type` の `group`、`atlas_type` の `callouts` のどれかが残っていれば、古い形とみなす。書き換えは次のとおりである。

- ページのカードから `atlas_page` を消す。座標のないカードも、項目は残す。
- グループから `atlas_type` を消す。`atlas_side` は残す。
- コールアウトの親（`atlas_type=callouts`）を消し、その子のコールアウトをレベル1に上げる。
- 項目の並びは変えない。

移行は普通の編集として扱い、移したページの修正日付は移した時刻にする。移す直前に、元の `index_atlas.md` を `index_atlas` の競合のファイルの名前で1回だけ残す。移す必要のないatlasには、何もしない。2台が別々に移しても、項目のidと本文は同じなので、項目ごとの突き合わせでそろい、送り合いにならない。

取り込んだファイルの中身がDBと同じで、ファイルの `modified` の方が新しいときは、ページの `modified` をファイルの日付にそろえる。そろえないと、次にこのPCで変えたときの日付が、相手のファイルより古くなり、相手で競合になるためである。

atlas専用のAPIはない。atlasの画面も、アウトラインと同じ項目のAPI（作成、更新、移動、プロパティ）で編集する。1回の操作が複数の変更になるときは、`POST /api/items/batch` でまとめて1回で送る。batchの `update` は、`properties` で項目のプロパティを書き、`droppedProperties` で消せる。親でなくなった項目の `atlas_side` のように要らなくなったプロパティは、コアが同じbatchで消す。

グループは次のように扱う。

- Ctrlを押しながら、カードを別のカードに落とすと、そのカードのグループに入る。相手がグループに入っていなければ、2枚で新しいグループを作る。リンクカードもグループに入る。
- Ctrlを押しながら、カードをグループの領域（blob）に落とすと、そのグループの項目の子になる。領域が入れ子のときは、最も内側の領域の項目を選ぶ。
- グループに入るカードは、置いた場所で、兄弟の中の入り先が決まる（ADR 053）。自分より下にある最初の兄弟の前に入り、下に兄弟がなければ、グループの木の末尾に入る。上下は `atlas_bounds` のYで比べ、Yが同じならXが小さい方を上とする。`atlas_bounds` のない兄弟は、比べる相手にしない。ほかの兄弟の順は変えない。
- Ctrlを押しながら、カードをグループの領域の外に落とすと、そのグループから出る。出たカードは、元のグループの木の末尾の次に、グループの項目と同じレベルで入る。
- カードは1つのグループにしか入らない。カードが出たグループの項目は、下の項目が1つでも、なくなっても、消さない。
- グループの色は、グループの項目のidから、picturesque-marksの6色の1つを選ぶ。
- タイトルは、グループの領域の外側に、指定した辺に沿って描く。左右の辺では、文字の足元が領域を向くように回す。
- グループ領域のダブルクリックか、右クリックメニュー「Edit Title」のダイアログで、タイトルと辺を決める。空のタイトルは、タイトルを消す。

コールアウトは次のように扱う。

- `x,y` はキャラクターの中央の座標で、カードと同じ座標系である。`atlas_side` は、キャラクターのどちら側にフキダシを置くかを表す。
- キャラクターは、picturesque-marksがテキストをsignatureとして描くfaceで、色は黒である。フキダシが左か下のときは、キャラクターを左右反転する。フキダシの線は手描き風に波打つ。波の形は項目のidから決まるので、描き直しても変わらない。
- 倍率はコールアウト全体の大きさで、カードと同じく下限は0.5、上限はない。小数第2位までで保存する。
- キャンバスの何もない場所の右クリックメニュー「Add Callout」で、その点に倍率1で置く。カードと同じく、選択してドラッグで動かし、Ctrl＋wheelで拡大縮小する。グループには入らない。コールアウトのダブルクリックか、右クリックメニュー「Edit Callout」でテキストと辺を変える。

リンクカードは次のように扱う。ディレクトリの外のページにもリンクできる。

- キャンバスの何もない場所の右クリックメニュー「Add Link」のダイアログで、リンク先を入力する。入力に合うページ名を、下に最大8件出す。候補のクリックか、OKかEnterで、その点に `x,y,0,40` で置く。
- blobは、ページのカードと同じくリンク先の名前から描く。色は薄いオレンジで、ページのカードの薄い青と区別する。ラベルはリンク先のパスの最後の部分で、リンクの色で描く。indexページは `ディレクトリ名/` と書き、ルートのindexページは `(root)/` と書く。ラベルのクリックでリンク先を開く。
- 位置と倍率の扱いは、ページのカードと同じである。
- リンクカードのダブルクリックか、右クリックメニュー「Edit Link」で、同じダイアログを開いてリンク先を変える。位置と倍率は変わらない。空の入力では何も変えない。
- 右クリックメニュー「Remove Link」で、項目ごと消す。

システム管理キーはサーバー起動時に `seed_system_keys` が必ずフラグを立てる。ユーザーが別の型で定義していたキーが後からシステム管理キーになったときは、型も予約された型に書き換える。

ユーザー定義キーは `for_page` が既定で1になる。

## 2. 値の保存

スカラー値は `properties` テーブルに入る。主キーは `(target_type, target_id, key)` で、1対象につき1キー1値である。`target_type` は `item` か `page` である。

値の列は `value` の1つだけで、どの型の値も文字列で入る（ADR 046）。型は値の読み方で、型が変わっても `value` は変わらない。REST・MCPから書くときは、定義の型で値を確かめ、次の形の文字列にして入れる。

| 型 | `value` に入る文字列 |
|---|---|
| `number` | 整数なら `"2"`、小数なら `"1.5"`。数値でない入力は400エラー |
| `checkbox` | `"true"` のときだけ `"true"`、ほかは `"false"` |
| `text` / `date` / `datetime` | そのまま。日付の形式チェックはない |
| `bounds` | `x,y,width,height` の4つの数値をカンマでつなぐ。空白は除き、各数値は `number` と同じ形で書き直す。例: `" 10, 20.5,160 ,56"` は `"10,20.5,160,56"` になる。4つの有限な数値でない入力は400エラー |

数は文字列で持つので、`value` のまま比べると `"10"` が `"9"` より小さくなる。数で比べる検索や並べ替えを足すときは、`value` から作る生成列を足す（ADR 046）。

リスト値は `property_list_items` テーブルに1値1行で入る。`sort_order` で順序を保つ。

## 3. REST API

### 定義

- `GET /api/config/property-definitions`
  - `propertyDefinitions`: `{ key: 型 }` のマップ。古いクライアント向け。
  - `definitions`: `[{ key, valueType, system, page }]` の配列。
- `POST /api/config/property-definitions`
  - ボディは `{ key, valueType, page? }`。`page` は省略すると `true`。
  - システム管理キーと同名、定義済み、型が5種以外、キーに使えない文字がある、のどれかなら400。
  - 成功すると `GET` と同じ形で全定義を返す。
- `DELETE /api/config/property-definitions/{key}`
  - ユーザー定義キーを削除する。そのキーの値は、すべてのページとアイテムから消える。
  - 値を失ったページは `modified_date` が更新され、Markdownファイルが書き出され、SSEで通知される。
  - システム管理キー、未定義のキーなら400。
  - 成功すると `GET` と同じ形で残りの全定義を返す。

### アイテム

- `PUT /api/items/{id}/properties/{key}`: ボディは `{ valueType, value }`。値は定義の型で確かめ、`valueType` は使わない。定義のないキーは400で断る（ADR 047）。型は定義するときだけ決まるからである。`date` は年月日（`2026-03-01`）、`datetime` はRFC 3339の日時（`2026-03-01T10:00:00Z`）で、合わなければ400である。古いファイルにある時差のない日時（`2026-02-13T08:57:58`）も受け付ける。
  - `list` 型のキーはカンマ区切りの文字列を受け取り、そのキーのリストとして保存する。`tags` は本文の `#hashtag` からサーバーが作るので、ここでは書かない。
- `DELETE /api/items/{id}/properties/{key}`

どちらも更新後のアイテムを `{ item }` で返す。

### ページ

- `PUT /api/pages/{id}/properties/{key}`: ボディは `{ valueType, value }`。
  - `created` と `modified` はRFC 3339の日時（例 `2026-01-02T03:04:05Z`）を受け取り、`pages` テーブルの日付を書き換える。`properties` テーブルには入らない。形式が違えば400。
  - `tags` はカンマ区切りの文字列を受け取り、リストとして保存する。タグページを持つのは `tags` だけである。
  - `list` 型のキーもカンマ区切りの文字列を受け取り、そのキーのリストとして保存する。`tags` には触らない。
  - `for_page` が0のキー（`zoom` など）は400。
  - 定義のないキーは400で断る（ADR 047）。値の確かめは項目と同じである。
- `DELETE /api/pages/{id}/properties/{key}`: `created` と `modified` は消せない（400）。

どちらも更新後のページを `{ page }` で返す。`page.properties` にスカラー値とリスト値が入る。ページ一覧を返すAPIのうち backlinks では `properties` は空である。recent と children はスカラー値だけを入れて返す。左カラムのページ一覧が `published` で並び替え、`published` のあるページのアイコンを塗りつぶすためである。children はリスト値のうち `tags` も入れる。atlasのカードが、ページのタグからアイコンを作るためである。

### ファイルへの書き出し

アイテムまたはページのプロパティだけを変えたときも、ページの `modified_date` を更新し、Markdownファイルを書き出す。これは `ItemService::set_property` / `delete_property` と `PageService::set_property` / `delete_property` が行う。MCPの `upsert_property` ツールも同じ経路を通る。

## 4. Markdownファイルでの表現

### アイテム

メタデータ行に `key="value"` として書く。`idx`、`collapsed`、`transclude`、`modified` の後に、残りのキーをアルファベット順で並べる。`modified` は項目の更新日時で、ページのファイルにだけ書く。アトラスのファイルと、木のエクスポートには書かない。リスト値はカンマ区切りで1つの値にする。値の `\` と `"` はエスケープする。

```
<!-- @@ <id> idx="..." modified="2026-03-01T00:00:00Z" plan="2026-03-01" tags="a,b" zoom="1.5" -->
```

ファイルの取り込みでは、メタデータ行のスカラー値と、名前が `_list` で終わるキーのリストの値を、項目のプロパティに合わせる。定義のないキーも、名前でリストかどうかを決める。行にないキーの値は消す。`tags` だけは読まず、本文の `#hashtag` から作り直す。

### ページ

frontmatterに書く。`id` / `created` / `modified` の後にスカラー値を `key: value` で、リスト値をYAMLのリストで書く。

```
---
id: <id>
created: 2026-10-16T00:00:00Z
modified: 2026-10-16T00:00:00Z
owner: "me: now"
tags:
  - a
  - b
---
```

値が空、または `"` `\` `: ` ` #` を含む、または `:` で終わる、または端に空白がある、またはYAMLで意味を持つ記号で始まるときは `"` で囲む。`2026-01-02T03:04:05Z` のような日時はそのまま書く。`"` は `\"` にする。`outline_parser` はこの形式を読み戻せる。

ファイルの取り込みでは、frontmatterの `tags` をページの `tags` として読む。ファイルのほうが新しい版なので、`tags` がなければページのタグも空になる。古いファイルの `tag` も読み、`[a, b]` の形や先頭の `#` も受け付ける。書き出しの形と違うときは、ファイルを書き戻して `tags` のブロックリストにそろえる。

frontmatterの残りのキーは、ページのプロパティとして読む（`PageService::replace_page_properties`）。ファイルだけからページを作った端末も、これでプロパティを持つ。読まないと、その端末が次にファイルを書いたときに、frontmatterからプロパティが消える。

- ページより新しいファイルが、ページのプロパティを決める。ファイルにないキーの値は、ページから消す。ページより古いファイルは、ページのプロパティを変えない。`tags` と同じ決まりである。
- 定義のないキーには、仮の定義を作る（ADR 046）。型は名前から決まる型である（ADR 047）。仮の定義は `settings/properties.json` に書かない。ほかの端末の定義が届けば、それに置き換わる。取り込みで、仮の定義のキーの値が端末のDBに1つもなくなれば、仮の定義を消す（`PropertyRepository::drop_unused_provisional_in`）。項目のメタデータ行も同じである。
- 名前が `_list` で終わるキーは、定義があってもなくても、リストとして読む。
- `for_page` が0のシステム管理キー（`zoom` など）、キーにできない名前の行は、読み飛ばす。ファイルのほかの部分は取り込む。`for_page` が0のユーザーのキーは取り込む。`for_page` は、ページのプロパティのUIで選べるキーを決めるためだけに使う。ほかの端末では、ページに付けられる定義かもしれないからである。
- ユーザーのキーの値は、型に合わなくても、ファイルに書かれた文字列のまま取り込む（`PropertyRepository::take_in_scalar_in`）。システム管理キーの値は、型に合わなければ読み飛ばし、ページや項目の値が残る。アプリが型どおりに値を読むからである。今、型を確かめるのは `number`、`checkbox`、`bounds` である。
- Dropboxのconflicted copyからは、プロパティを読まない。

### タグページ

タグには、設定のタグディレクトリの下に同じ名前のページ（タグページ）が対応する。ページの `tags` と本文の `#hashtag` は同じに扱う。

- タグが増えると、まだないタグページを作る。
- タグが減ると、どのページにもアイテムにも使われなくなったタグのタグページを消す。ただし、空のアイテムが1つだけのページに限る。何か書いてあれば残す。
- ページを削除すると、そのページのタグと中のアイテムの本文タグも消えるので、同じ条件でタグページを消す。
- アプリからの変更（REST・MCP）とファイルの取り込みの両方で、この処理を行う。

## 5. フロントエンドのUI

### Settings画面

- 全定義を一覧にする。システム管理キーは読み取り専用で表示する。
- キーと型を入力してユーザー定義キーを追加できる。
- ユーザー定義キーはDeleteボタンで削除できる。押すとその場で確認を求め、Yesで削除する。

### ページのプロパティ

- ページがプロパティを持つときは、タイトルと本文の間に常にプロパティUIを出す。
- ページがプロパティを持たないときは、「…」メニューの「プロパティの編集」でUIを出す。
- `created` と `modified` の行は常に先頭にある。すべてのページが持つので、この2行だけではUIは自動では開かない。「X」は付かない。
- `modified` はサーバーが保存のたびに動かすので、UIからは変更できない。表示だけである。
- `datetime` 型の値は現地時刻で分まで表示し、分まで入力する。サーバーへは秒を0にしたUTC（`YYYY-MM-DDTHH:MM:SSZ`）で送る。
- 「+」で足した行が `datetime` 型のときは、現在の日時が初期値として入っている。Enterでそのまま確定できる。
- 値は、変更して入力欄を離れたとき、Enterを押したとき、入力欄の外をクリックしてフォーカスが外れたときに確定する。足したばかりの行は、値が空のままならフォーカスが外れても確定しない。その行の「X」を押すと、確定せずに行が消える。
- 1プロパティ1行。「+」で行を足し、「X」で消す。
- キーは `for_page` が1の定義から選ぶ。

## 6. 今後の課題

### プロパティ定義の同期

ADR 046で、定義をMarkdownフォルダーの `settings/properties.json` に置き、端末の間で同期すると決めた。

ファイルには、キーごとに `page` と `modified`、または消した日時の `deleted` を書く。型は名前から決まるので、ファイルには書かない（ADR 047）。古い版が書いた `type` は読み飛ばすが、名前から決まる型と合わない定義は読まない。

- 端末は、その端末のユーザーが定義を足したときと消したときに、`settings/properties.json` を書く（`DefinitionsFileService::write_file`）。書く中身は、端末のDBの本物のユーザー定義と `deleted_property_definitions` を、ファイルにある定義とキーごとに合わせた結果である（`domain::property_definitions::merge`）。ファイルにあって、端末がまだ取り込んでいないほかの端末の定義を消さないためである。
- 形式は、ADR 046の「ファイルの形式」のとおりである（`infrastructure::export::definitions_file`）。キーは辞書順で、日時はUTCのISO 8601である。システム管理キーは書かない。読むときは、ユーザーが作れない定義（システム管理キー、名前に合わない型、知らない型、キーにできない名前、日時のない定義）を読み飛ばす。
- 端末は、ほかの端末が書いた `settings/properties.json` を受け取ると、その定義と端末のDBの定義をキーごとに合わせ、結果を端末のDBに入れる（`DefinitionsFileService::take_in`）。合わせた結果が受け取ったファイルと違えば、ファイルを書き直す。同じなら書き直さない。
  - 新しい定義が届くと、端末は、DBの定義の `for_page` を変え、`deleted_property_definitions` からそのキーの行を消す。仮の定義も本物の定義になる。値は変えない。
  - 消したことが届くと、端末は、消した日時を `deleted_property_definitions` に入れる。端末のDBにそのキーの値がなければ、定義の行を消す。値があれば、定義を仮の定義（`provisional` が1）にして残し、値も残す。このキーにユーザーがRESTやMCPで値を書いても、仮の定義のままで、消したことも残る。値がなくて定義の行を消したキーには、値を書けない。使い直すには、定義し直す（ADR 047）。
  - ページのファイルは書き直さず、ページの `modified` も進めない。
- `settings/properties.json` のconflicted copy（`settings/properties (… conflicted copy …).json`）は、もう1つの版として端末のDBに合わせ、`settings/properties.json` を書き直してから消す（`take_in_copy`）。
- 取り込むのは、ジャーナルサーバーの監視（`settings/` も見る。監視を始めるときに `settings/` を作る）と、coreの走査（`MarkdownReconcileService` が毎回 `settings/` を見る）である。どちらも `MarkdownImportService::sync_file` に渡す。どのファイルを渡すかは `import_service::takes_in` が決める。
- 端末は、`settings/properties.json` を読んで合わせて書く処理を、1つずつ行う（`DefinitionsFileService` のMutex）。クライアントのリクエストと取り込みが、いくつものスレッドから書くからである。
- 端末は、DBの定義が変わると、SSEの `{"type":"propertyDefinitionsUpdated"}` を送る。ファイルの取り込みでは、取り込みの前と後で定義の一覧（`PropertyRepository::find_definitions`）を比べ、違えば送る（`MarkdownImportService::sync_file`）。ユーザーが定義を変えたときは、`settings/properties.json` を書いたあとに送る（`Journal::definitions_changed`）。
- クライアントのcoreは、このメッセージを受けたときと、SSEがつながるたびに、定義を読み直す（`screens::sse`）。
