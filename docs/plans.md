## APIの方針：RESTとMCP

2026-11-11にユーザーが決めた。ジャーナルサーバーのAPIを足す、変える、消すときは、まずここを読む。

- MCPとRESTは、全く同じことができる
- MCPは、RESTをSSOT（唯一の正）として、JSONをRESTの形にそろえる
- いまMCPにだけあるものは、RESTになくてはならない。逆もそうである。RESTにだけあるものは、MCPになくてはならない

この方針から、次のことが決まる。

- 片方だけを消さない。消すなら、RESTとMCPの両方から消す。クライアントがリポジトリの中にないことは、片方だけを消す理由にならない
- 足すときは、両方に足す
- 答えのJSONの形を決めるのはRESTである。MCPは、同じ形で返す

## journal-core

- [ ] ジャーナルサーバーの中身を、ライブラリ`journal-core`として切り出す（ADR 029）
  - 目的は、Androidのシェルが、PCと同じ中身をアプリに組み込んで使うことである。REST、MCP、embed版が、同じ入口（`Journal`）を通る
  - ジャーナルサーバーの動きは変えない。RESTとMCPの答えは、切り出しの前と同じである。既存の結合テストで守る
  - [ ] MCPのページと項目の答えを、RESTの形にそろえる（2026-11-11にユーザーが決めた）。Androidのシェルの最初の版より後に行う
    - 今のMCPは、ページと項目を、RESTと違う形で書く。入口の答えはRESTの形なので、MCPは、その答えから今の形へ書き直している（`mcp.rs`の`page_record_json`と`item_record_json`）。そろえると、この書き直しが要らなくなる
    - 違いは4つある
      - 日付（`createdDate`、`modifiedDate`）: MCPはISO 8601の文字（`2026-11-11T10:00:00Z`）、RESTはミリ秒の数
      - プロパティ（`properties`）: MCPにはなく、RESTにはある
      - 親のないページの`parentId`: MCPは`null`、RESTは空の文字
      - トランスクルージョンの木（`transcludedTrees`）: MCPの`get_page_by_id`にはなく、RESTの`GET /api/pages/{id}`にはある
    - 今の形で書いている道具は、`get_page_by_id`、`get_or_create_doc`、`update_page`、`get_recent_pages`、`get_backlinks`、`get_or_create_journal`、`get_most_recent_journal_before`と、項目の道具のうち4つである。その4つは、`create_item`、`update_item`、`move_items`、`get_items_by_type`である。項目の道具のほかのもの（`get_item`、`cycle_task`など）は、すでにRESTの形（`ItemDto`）で書いている
    - MCPの答えが変わるので、MCPを使う側を先に確かめる。`peta-journal`、`kcg-lecture`、`report`などのスキルと、日付を文字として読んでいるところである
    - 入口へ下ろし終えてから行う。途中でそろえると、下ろす作業と答えの変更が1つのPRに混ざる
  - [ ] コアの振る舞いを確かめている結合テストを、`journal-core`に移す（2026-11-13にユーザーが決めた。フォルダーの並べ替えとは別の仕事である）
    - 今は、コードの大半が`journal-core`にあるのに、テストの大半は`journal-server`にある。`journal-core`は約17,600行で、テストは139個である。すべて`src`の中の単体テストである。`journal-server`は約3,900行で、テストは388個である。うち379個が、サーバーを立ててHTTPで確かめる`tests/`の結合テストである（2026-11-13に数えた）
    - こうなった理由。切り出しの間は、既存の結合テストが、動きが変わらないことを守った（ADR 029）。切り出しのあとも、テストは元の場所に残っている
    - 困ること。AndroidとiOSが使う道（`default-features = false`で、HTTPを通らない）を、テストが通らない。コアの振る舞いを1つ確かめるのに、サーバーを立てる。HTTPの層の誤りと、コアの誤りが、同じテストで落ちる。ミュータントは、ワークスペースの全体のテストで確かめる必要がある（`mutants.toml`の`test_workspace = true`）
    - 目標の形。コアの振る舞いは、`Journal`の入口を直接呼ぶテストで確かめる。サーバーには、RESTとMCPの層のテストだけを残す
    - 先に調べること: 379個のうち、どれがコアの振る舞いで、どれがHTTPの層か
    - 終わったら、`journal-core`を直下に出すかを決める（ADR 039のAlternative 3）
  - [ ] ミューテーションテストが、`AppResult`と`HttpResult`を返す関数の中身を置き換えられるようにする
    - `cargo-mutants`は、戻り値の型を名前で見る。`Result`は知っているが、型の別名の`AppResult`と`HttpResult`は知らない。そのため「`Ok(既定値)`を返す」ミュータントを作らず、`AppResult::new()`のような、ビルドできないものを作る
    - 項目を入口へ下ろしたPR（2026-11-11）では、467個のうち429個がこれだった。入口の操作とハンドラーには、関数の中身を丸ごと置き換える検査が効いていない。演算子のミュータント（`!`、`==`、`<`）は効いている
    - ビルドできないものは、`-E "(App|Http)Result::(new|from|from_iter)\("`で外して回せる。時間は省けるが、検査は増えない
    - 直す方法の候補は、戻り値を`Result<T, AppError>`と書くことである。書き換えは広い。ほかの方法があるかは、調べていない

## UndoとRedo

- [ ] 日をまたぐ移動を、Undoに記録する
  - ジャーナルで、項目を隣の日へ動かす移動（`move_across_days`）は、Undoに記録していない。Ctrl+Zでは戻らない
- [ ] 移動の応答が届く前のCtrl+Zを確かめる
  - 移動は、サーバーの応答が届いてからUndoに記録される。それより前のCtrl+Zでは、移動が戻らない。E2Eで、サーバーが移動を保存した直後にCtrl+Zを押すと、何の要求も出ないことを確かめた
  - Undoの履歴に前の操作があれば、移動ではなく、その操作が戻るとみているが、未確認である
  - タスクの切り替え（Ctrl+Enter）でも同じことが起きる。2026-11-11に、E2Eで見た。切り替えの答えが届く前にCtrl+Zを押すと、その切り替えではなく、1つ前の切り替えが戻った
- [ ] 選択した項目の移動のUndoのあとの、選択とエディタを確かめる
  - Undoは、カーソルの記録がない更新では、最初に更新した項目のエディタを開く。選択した項目をまとめて動かした移動のUndoでも、選択には戻らず、エディタが開くとみているが、未確認である
- [ ] Undoで作り直した項目に、折りたたみ、トランスクルージョン、プロパティを戻す
  - 作り直しは、本文と階層だけを送る。タスクの種別は本文の接頭辞からは戻らず、折りたたみとトランスクルージョンも戻らない
- [ ] サーバーがページの並び順の値を振り直したあとの、Undoでの位置を確かめる
  - 項目の作成や移動で値の余地がなくなると、サーバーはページの全項目の値を振り直す。答えは、書いた項目だけを返す。コアが持つほかの項目の値は古いままになるとみているが、未確認である
  - Undoは、作り直す項目や動かした項目の位置を、コアが持つ値の比較で求める。古い値と新しい値を比べると、違う位置に置くおそれがある。分割の表示は、答えの中の2つの項目の値だけを比べるので、影響を受けない
- [ ] 重なった書き込みの要求が、サーバーで送った順に書かれるかを確かめる
  - UndoとRedoの要求が重なったとき、どちらのトランザクションが先に始まるかは、決まっていないとみている。逆の順に書かれると、サーバーにはUndoした本文が残り、画面はRedoした本文を表示する。Redoのテストを81回繰り返した調べでは、81回とも正しい順だった。起きるかどうかは未確認である
  - 直すなら、コアが同期を1つずつ順に送る（前の応答を待ってから次を送る）方法がある
- [ ] 入力の自動保存の応答が、Undoのあとに届く場合を確かめる
  - 自動保存の応答は、本文と解析結果を無条件に項目へ書く。保存の要求が出たあとにUndoをすると、遅れた応答が、Undoした本文を入力した本文に戻すとみているが、未確認である
