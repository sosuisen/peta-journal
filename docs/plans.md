## PetaJournalのURLとリンクの生成

URLの知識を1か所にする決定は、ADR 061（`docs/adr/adr-061-page-urls-in-one-crate.md`）にある。ADR 051は、この決定と密接に関係している（2026-11-17に開発者が言った）。

### ADR 051：wikilinkとhashtagのhrefを、ast2htmlのテンプレートで決める

ADR 051は、`/pages/`といった値をhrefに埋め込む機能を提供する。値は、ADR 061の`page-urls`から取る。

2026-11-16に開発者が受理した。flatmarkdownに`HtmlOptions`と`ast_to_html_with`を足し、0.9.0を出してから、Webのシェルを切り替える。flatmarkdown側のタスクは、flatmarkdownの`docs/plans.md`にある。

- [ ] flatmarkdownの3つのクレートを0.9.0に上げる。`client/`のCargo.tomlとCargo.lockを直す
- [ ] Webのシェルの`item_html`で`ast_to_html_with`を使う。wikilinkは`/pages/{}`、hashtagは`/pages/<タグ用ディレクトリ>{}`にする
  - [ ] タグ用ディレクトリが変わったら、項目のHTMLを作り直す（`item_view.rs`の`Memo`が設定も読む）
  - [ ] `point_links_at_pages`、`point_links`、`data-page`の属性を消す
  - [ ] Ctrl+クリック、中クリック、右クリックのメニューで、正しいページが開くことを確かめる
- [ ] 「HTMLとしてコピー」（ADR 027）とmemoviewは変えない

### リンクの符号化

- [ ] ADR 051を改めて、描画のライブラリが、テンプレートに名前を入れるときにパーセント符号化するようにする（2026-11-18に開発者が決めた）
  - 理由：`%`、`?`、`#`を含むページ名のリンクが壊れる。たとえば`[[What?]]`は`/pages/What?`になり、ブラウザーは`What`というページを開こうとする。ADR 051は符号化しないと決め、この制限を認めていた
  - サーバーが返す`url`も、同じ関数で作る（ADR 061）。そのため、この作業が終わると、本文の中のリンクと`url`が同時に符号化される。終わるまでは、どちらも壊れる
  - 決めること：どの文字を符号化するか。`[[Page#item]]`のように、ページの中の場所を指す`#`は残す必要がある。ADR 061の`page-urls`のURLを読む関数が、符号化したURLを元のページ名に戻せるようにする
  - 対象は、flatmarkdownの`ast2html`（Rust版とwasm版）と`ast2react`である。flatmarkdown側の作業になる
  - 決めること：Rust（`ast2html`）とTypeScript（`ast2react`）の符号化の規則をそろえる方法。`ast2react`はRustの関数を呼べないので、同じ規則をTypeScriptでも持つことになる。候補は、`ast2react`がwasm版の関数を呼ぶ方法と、同じ入力と出力の表を両方のテストで使う方法である

## journal-core

### 機能向上

- [ ] ジャーナルサーバーの中身を、ライブラリ`journal-core`として切り出す（ADR 029）
  - 目的は、Androidのシェルが、PCと同じ中身をアプリに組み込んで使うことである。REST、MCP、embed版が、同じ入口（`Journal`）を通る
  - ジャーナルサーバーの動きは変えない。RESTとMCPの答えは、切り出しの前と同じである。既存の結合テストで守る
  - [ ] コアの時計を差し替えられるようにするかを決める。テストを`journal-core`に移し終えてから考える
    - 今、コアは日付をその場でシステムの時計から取る（`infrastructure/persistence/db.rs:121`の`now_millis()`。10ファイルの33か所から呼ぶ）。項目、ページ、プロパティの定義の更新日時は、すべてこの値である
    - 2台の同期は、この日付で新しい方を選ぶ。そのためテストは、2つの操作の日付がずれるように、間で5ミリ秒待つ。`journal-server`のテストに20か所（`item_merge.rs`に7、`definitions_sync.rs`に7、`api.rs`に5、`mcp/main.rs`に1）、`journal-core`の単体テストに2か所ある（2026-11-18に数えた）
    - 困ること。後の操作が新しいという前提を、待ち時間に頼っている。2つの操作が同じミリ秒になる場合は、テストできない。`item_merge.rs:154`のコメントにある取り違え（Bのファイルの日付がAの最後の同期と同じになり、Aが手で編集したファイルと見る）は、実際の端末でも起こりうる
    - 差し替えられれば、待ちは「時計を1ミリ秒進める」になり、同じミリ秒の場合も狙ってテストできる。費用は、`now_millis()`の33か所と`IdGenerator`（hmtid）を、渡した時計で読む形に書き換えることである。ファイルの更新時刻はOSが付けるので、時計を差し替えても、テストはファイルの日付を別に書く
  - [ ] ミューテーションテストが、`AppResult`と`HttpResult`を返す関数の中身を置き換えられるようにする
    - `cargo-mutants`は、戻り値の型を名前で見る。`Result`は知っているが、型の別名の`AppResult`と`HttpResult`は知らない。そのため「`Ok(既定値)`を返す」ミュータントを作らず、`AppResult::new()`のような、ビルドできないものを作る
    - 項目を入口へ下ろしたPR（2026-11-11）では、467個のうち429個がこれだった。入口の操作とハンドラーには、関数の中身を丸ごと置き換える検査が効いていない。演算子のミュータント（`!`、`==`、`<`）は効いている
    - ビルドできないものは、`-E "(App|Http)Result::(new|from|from_iter)\("`で外して回せる。時間は省けるが、検査は増えない
    - 直す方法の候補は、戻り値を`Result<T, AppError>`と書くことである。書き換えは広い。ほかの方法があるかは、調べていない

- [ ] フォルダ同期の項目のマージ（`journal-core`の`infrastructure/export/item_merger.rs`、ADR 006）に、2〜3台の場面を自動で作る性質テストをproptestで足す（2026-11-18に開発者と話した）

  - Leanで証明する案は採らない。ADR 006は、時計のずれや「相手が消したとみなす」推定で項目を失う場面を、すでに認めている。証明しようとしても、そこで失敗するだけである。Leanの模型とRustのコードがずれていく問題もある。マージは`deleted_items`などPCごとの状態にもよるので、「どの順でも収束する」をきれいに示す定番の証明も当てはまらない。性質テストなら、実際のコードを確かめられ、見つけた反例はそのまま失敗するテストとして残せる
  - 確かめる性質の案
    - 収束：ファイルが行き渡って同期が止まったら、全台のDBの項目（中身、`idx`、順）が一致する
    - 静止：変更がなければ、書き戻しが往復し続けない。「日付が同じで中身が違えば、今の時刻で書き戻す」規則があるので、特に確かめる
    - `idx`：同じ隙間に足した項目が、届く順によらず同じ並びになる
    - 失わない：時計がずれず、conflicted copyが届く場面では、ユーザーが消していない編集は、DBか`.conflict`に残る
  - 届く順をすべて試したくなったら、Rustのモデル検査器staterightを考える

## UndoとRedo

### 機能向上

- [ ] 日をまたぐ移動を、Undoに記録する
  - ジャーナルで、項目を隣の日へ動かす移動（`move_across_days`）は、Undoに記録していない。Ctrl+Zでは戻らない

### 調査・バグ修正

- [ ] 移動の応答が届く前のCtrl+Zを確かめる
  - 移動は、サーバーの応答が届いてからUndoに記録される。それより前のCtrl+Zでは、移動が戻らない。E2Eで、サーバーが移動を保存した直後にCtrl+Zを押すと、何の要求も出ないことを確かめた
  - Undoの履歴に前の操作があれば、移動ではなく、その操作が戻るとみているが、未確認である
  - タスクの切り替え（Ctrl+Enter）でも同じことが起きる。2026-11-11に、E2Eで見た。切り替えの答えが届く前にCtrl+Zを押すと、その切り替えではなく、1つ前の切り替えが戻った
- [ ] 選択した項目の移動のUndoのあとの、選択とエディタを確かめる
  - Undoは、カーソルの記録がない更新では、最初に更新した項目のエディタを開く。選択した項目をまとめて動かした移動のUndoでも、選択には戻らず、エディタが開くとみているが、未確認である
- [ ] Undoで作り直した項目に、折りたたみ、トランスクルージョン、プロパティを戻す
  - 作り直しは、本文と階層だけを送る。タスクの種別は本文の接頭辞からは戻らず、折りたたみとトランスクルージョンも戻らない
- [ ] サーバーがページの並び順の値を振り直したあとの、Undoでの位置を確かめる
  - 項目の作成や移動で値の余地がなくなると、サーバーはページの全項目の値を振り直す。答えは、書いた項目だけを返す。コアが持つほかの項目の値は古いままになるとみているが、未確認である
  - Undoは、作り直す項目や動かした項目の位置を、コアが持つ値の比較で求める。古い値と新しい値を比べると、違う位置に置くおそれがある。分割の表示は、答えの中の2つの項目の値だけを比べるので、影響を受けない
- [ ] 重なった書き込みの要求が、サーバーで送った順に書かれるかを確かめる
  - UndoとRedoの要求が重なったとき、どちらのトランザクションが先に始まるかは、決まっていないとみている。逆の順に書かれると、サーバーにはUndoした本文が残り、画面はRedoした本文を表示する。Redoのテストを81回繰り返した調べでは、81回とも正しい順だった。起きるかどうかは未確認である
  - 直すなら、コアが同期を1つずつ順に送る（前の応答を待ってから次を送る）方法がある
- [ ] 入力の自動保存の応答が、Undoのあとに届く場合を確かめる
  - 自動保存の応答は、本文と解析結果を無条件に項目へ書く。保存の要求が出たあとにUndoをすると、遅れた応答が、Undoした本文を入力した本文に戻すとみているが、未確認である
