# ADR 069: Keep Only the Edited Items When a Page Is Read Again

## Status

Accepted

## Context

`client-core`は、開いているページのMarkdownファイルが変わったと知らされると、そのページをサーバーから読み直し、画面の項目をサーバーの版に置き換える（`client/libs/client-core/src/ops/file_reload.rs`）。
知らせは、ほかの端末からDropboxで届いたファイル、ほかのクライアントのAPIでの変更、MCPでの変更のどれでも来る。

今のコアは、ページのどれかの項目を編集している間、そのページ全体の読み直しを待たせる。
編集中かどうかは、`OutlineState`の`editing_item_ids`が空かどうかだけで決まる（`ops/edit.rs`の`is_edit_in_progress`）。
編集中に来た知らせのページは`Model`の`file_reload_pending`に入り、`editing_item_ids`が空になって1.5秒たってから読み直される。
打ちかけの本文を、サーバーの版で上書きしないためである。

この決まりは、実際の使い方と合わなかった。
Webのアウトライナーでは、カーソルがほぼいつもどこかの項目にあるので、`editing_item_ids`はほとんど空にならない。
ユーザーが打つのをやめて待っても、ほかの端末やMCPの変更は、ページを再読み込みするまで画面に出ない。
#731（2026-11-13、iPhoneと`shell-leptos`）と#866（2026-11-20、MCPで足した項目）は、この決まりで起きていた。
Androidの実機でも、Syncで届いたページが、検索欄にフォーカスを移すまで変わらなかった（#768）。
監視とSSEの知らせは届いていた（#831、#835）。

決まりは`client-core`にあるので、Webのアウトライナーとネイティブのシェルのすべてに効く。
ほかの端末の変更とこちらの打ちかけが同じ項目に重なったときの扱いは、ADR 006（項目ごとのLast-Writer-Wins）の規則と矛盾しないように決める必要がある。

## Decision

ページを読み直すときに、ページ全体を待たせる決まりをやめる。
コアは、編集中でもすぐにページを読み直し、手元の版を残す項目のほかは、サーバーの版に置き換える。
`file_reload_pending`、`file_reload_scheduled`、1.5秒の待ち（`FLUSH_DELAY_MS`）は取り除く。

### 手元の版を残す項目

手元の版を残す項目は、次のどちらかに当たる項目である。

- `editing_item_ids`にある項目。
- まだサーバーに保存していない打ちかけの本文がある項目（`EditState`の`dirty_item_ids`にあるか、`pending_saves`に保存が待っている項目）。

以下では、この2つを合わせて「残す項目」と呼ぶ。
`editing_item_ids`だけにしないのは、カーソルを別の項目へ移した直後に、前の項目の保存がまだ終わっていないことがあるためである。
残す項目のうち、`dirty_item_ids`と`pending_saves`のどちらにもない項目を「打っていない項目」と呼ぶ。

### 残す項目が、サーバーの版でも変わっていたとき

コアは、サーバーの版と手元の版の`body`を比べる。

1. 打っていない項目なら、コアはサーバーの版の`body`を画面に出す。
   カーソルの位置は、新しい`body`の長さに収める。
2. 打っている項目なら、コアは手元の`body`を残す。
   その後の保存で、サーバーのDBの項目とページのファイルは手元の`body`で上書きされる。

2の上書きで、ほかの端末の編集は失われる。
これは、ADR 006で、後に書いた側が勝つ（Last-Writer-Wins）としたのと同じ結果である。

### 残す項目が、サーバーの版で消えていたとき

1. 打っていない項目なら、コアはその項目を画面から消し、`editing_item_ids`から外す。
   フォーカスは、サーバーの版でその項目の前にある項目へ移す。
2. 打っている項目なら、コアは手元の`body`で、同じidの項目を作り直す。
   作り直す場所は、手元の並びでその項目の前にあった項目のすぐ後とする。
   前の項目もサーバーの版にないときは、ページの最初とする。
   idが変わらないので、編集はそのまま続き、カーソルの位置も変わらない。

2で項目を作り直すのは、サーバーが消えた項目への保存を受け付けないためである。
journal-coreの`ItemService::update_item`は、最初に`get_item_by_id`で項目を探し、見つからなければエラーを返す。
一方で、`ItemService::create_item`はidを受け取り、そのidで項目を作る。削除の取り消しが項目を作り直すのと同じ道である。

### 残す項目の位置が、サーバーの版で変わっていたとき

コアは、残す項目の`level`、`idx`、並びの位置を、サーバーの版に合わせる。
手元の版を残すのは`body`だけである。
編集とカーソルは項目のidについていくので、項目がほかの場所へ動いても、編集はその場所で続く。
画面の並びをサーバーの版とそろえることで、編集が終わったあとに読み直す必要をなくすためである。

### 変えないこと

- 読み直しの答えより後に、ここで変更をしていたとき（`AskedAt::is_overtaken`）は、今までどおり、答えを捨ててもう一度読み直す。
  編集中でも待たせない。
- トランスクルージョンの木（`transcluded_trees`）は、今までどおり答えから合流する。
  トランスクルージョンの元の項目は、上と同じ規則で残す項目として扱う。

## Alternatives

### Alternative 1: 今の決まりのまま、編集が終わるまでページ全体を待たせる

コードは変わらず、打ちかけの本文が上書きされることもない。
しかし、カーソルがほぼいつもある画面では、ほかの端末の変更が出ない。
#731と#866がそのまま残るので、選ばなかった。

### Alternative 2: `editing_item_ids`の項目だけを残す

残す項目の決め方が単純になる。
しかし、カーソルを移した直後で保存が終わっていない項目は、サーバーの古い版に置き換わり、打った文が画面から消える。
保存が届けば戻るが、一度消えて見えるので、選ばなかった。

### Alternative 3: 残す項目では、いつも手元の`body`を残す

打っていなくても手元の版を残すので、判定が要らない。
しかし、カーソルを置いただけの項目では、ほかの端末の編集が画面に出ない。
その項目でのちに打つと、古い`body`を元にした保存で、ほかの端末の編集を上書きしてしまうので、選ばなかった。

### Alternative 4: 同じ項目が両方で変わったら、競合として画面に出す

どちらを残すかを、ユーザーが選べる。
しかし、競合を出す画面を、すべてのシェルに作る必要がある。
ADR 006のフォルダー同期も、項目の競合はLast-Writer-Winsで決めており、ここだけ選ばせる理由が弱いので、選ばなかった。

### Alternative 5: 残す項目を、今の位置と字下げのまま残す

編集している項目が、画面上で動かない。
しかし、画面の並びとサーバーの版の並びがずれる。
編集が終わったあとにもう一度読み直す必要があり、今の待ちの仕組みが残るので、選ばなかった。

## Confidence Level

確信度は中程度である。

ページ全体を待たせる決まりが#731と#866の原因であることには、高い確信がある。
Webの画面でも、カーソルがある間は`editing_item_ids`が空にならないことを、開発者が確かめた。
一方で、打っている項目が消えたときに作り直す動きは、`client-core`のテストでしか確かめていない。

次の状況になったら、この決定を見直す。

- 打っている項目でほかの端末の編集を上書きして、実際に困ったとき。
  この場合は、Alternative 4の競合の表示を検討する。
- 編集中の項目が読み直しで動き、打っている最中に画面が跳んで困ったとき。
- 消えた項目を作り直したことで、ほかの端末が消した項目が戻り続けるとき。

## Consequences

### 良い結果

- ほかの端末、ほかのクライアント、MCPの変更が、編集中でもすぐに画面に出る。
  #731と#866が直る。
- `file_reload_pending`と1.5秒の待ちがなくなり、読み直しの道が1つになる。
- 画面の並びが、いつもサーバーの版とそろう。

### 悪い結果

- 打っている項目がほかでも変わっていると、ほかの端末の編集は保存で失われる。
  ADR 006と違い、`.conflict`のファイルも残らない。
- ほかの端末が消した項目でも、こちらで打っていれば、同じidで作り直される。
- 編集中の項目が、読み直しで画面の別の場所へ動くことがある。
- 打っていない項目のカーソルは、新しい`body`の長さに収めるだけなので、文の中の位置はずれることがある。

### 中立的な結果

- `client-core`の決まりなので、Webのアウトライナーとネイティブのシェルのすべてで振る舞いが変わる。
  シェルの側の変更は要らない見込みである。
- `client-core`の`file_reload`のテストのうち、編集中は待つことを確かめるテストは、編集中でも出ることを確かめるテストに書き換わる。
- Androidの`DownloadedPageTest`が確かめている、編集していないときの読み直しは変わらない。
