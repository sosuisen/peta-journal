# ADR 029: journal-core as the Library Under the Journal Server and the Embedded Shells

## Status

Accepted

## Context

ジャーナルサーバー（`journal-server-rust/crates/server`）は、1つのクレートである。SQLiteのDB、Markdownのフォルダーとの同期、検索、拡張関数、REST、SSE、MCPを、すべて持つ。シェルは、どれもRESTとSSEを通してこのサーバーを使う。

Androidのシェルを作ることにした。Androidには、ジャーナルサーバーを別のプロセスで動かす場所がない。開発者は、この用途のために、サーバーの中身をアプリに組み込む版（embed版）を作るつもりでいた。項目の親子関係の構築や移動は、ほかのシェルがRESTで行うのと同じように、組み込んだ中身のAPIで行う。

2026-11-11に、今のクレートを調べた。

第一に、サービスの層（`domain`、`application`、`persistence`、`export`）は、同期のコードである。axumにもtokioにも依存しない。tokioに触るのは、ハンドラーが使う`blocking`と、定期の仕事を回す`state.rs`だけである。

第二に、RESTのハンドラーは、サービスを呼ぶだけではない。サービスの前後に、4つの処理を持つ。要求の文字列をIDや位置に直す。ページを作ったときとタグが変わったときに、拡張関数を呼ぶ。どのページが変わったかを決めて、SSEで知らせる。トランスクルージョンで見せているページも、その対象である。最後に、プロパティとトランスクルージョンの木を足して、答えを組み立てる。

第三に、MCP（`mcp.rs`）は、同じ処理を自分でもう一度書いている。

そのため、embed版がサービスを直接呼ぶと、拡張関数が動かず、知らせが出ず、答えの形もずれる。

第四に、依存である。今のライブラリを`aarch64-linux-android`向けにビルドすると、`rquickjs`で止まった。`rquickjs-sys` 0.14.0は、このターゲットのバインディングを同梱していない。rusqlite、tantivy、lindera、peta-atlas、flatmarkdown、notify、axum、rmcpは、個別にコンパイルが通った。

第五に、検索の索引の大きさである。Android（`arm64`）向けのリリースビルドで、SQLiteだけのライブラリは2.0MBだった。tantivyを足すと6.8MB、lindera（IPADICを埋め込む）も足すと53.0MBだった。APKでの圧縮後は、順に1.1MB、3.0MB、14.4MBである。実際のDBは、653ページ、23,627項目、本文176万文字である。索引を使わずに全項目を`LIKE`で調べると、PCで約15msだった。端末での速さとメモリーは、測っていない。

第六に、拡張関数である。`rquickjs`の`bindgen`フィーチャーは、試せなかった。libclangが要るが、調べたPCにはない。拡張関数のファイルは、PCごとの設定フォルダーにある。同期するフォルダーには入っていない。

知らせの届け先は、すでに一部がトレイトである。`AtlasEvents`、`ExtensionEvents`、`ConfirmEvents`を、`SseBroadcaster`が実装している。検索の索引も、`SearchIndex`というトレイトである。

フロントエンドのコア（`peta-core`）は、RESTの答えと同じJSONの形を、自分の型で持っている。`ApiOp`をHTTPの要求に直し、答えのJSONを読む処理は、コアの`rest.rs`にある。

ギアは5速である。

## Decision

ジャーナルサーバーの中身を、ライブラリ`journal-core`として切り出す。置き場所は`journal-server-rust/crates/core`である。ジャーナルサーバーと、アプリに組み込む版（embed版）は、どちらもこのライブラリを使う。

### 分け方

`journal-core`は、`domain`、`application`、`persistence`、`export`（書き出し、取り込み、合流）、検索の索引、答えの型（今の`presentation/dto.rs`）を持つ。axum、tokio、rmcp、notifyには依存しない。

`journal-server`には、次のものが残る。RESTのルーターとハンドラー、SSE、MCPの道具の定義、フォルダーの監視、定期の仕事を回す部分、Webフロントエンドの配信、フォルダーを選ぶダイアログ、URLとフォルダーをOSで開く処理、`main.rs`である。

### 入口

`journal-core`は、入口になる型`Journal`を持つ。操作は、今のRESTの操作と同じ単位にする。1つの操作は、次のことを全部行う。要求の値を確かめる。サービスを呼ぶ。拡張関数を呼ぶ。変わったページを決めて知らせる。プロパティとトランスクルージョンの木を足して、答えを組み立てる。

RESTのハンドラーとMCPの道具は、この入口を呼ぶだけにする。ハンドラーに残るのは、HTTPの要求を読むことと、`?fields=`で項目を絞ることである。

### 知らせ

変わったページの知らせは、外から渡すトレイトで出す。今の`AtlasEvents`、`ExtensionEvents`、`ConfirmEvents`と同じ形である。ジャーナルサーバーは、これを`SseBroadcaster`で実装する。embed版は、同じ知らせをシェルへ渡す。

### 定期の仕事

書き出しのキューの処理、フォルダーの調べ、索引の確定は、`journal-core`が関数として持つ。いつ呼ぶかは、外が決める。ジャーナルサーバーは、今までどおりtokioで回す。索引の確定は、今は索引の実装の中でtokioを使っている。これを外へ出す。

### エラー

`AppError`は`journal-core`に置く。HTTPの状態への直し方は、`journal-server`が持つ。

### 依存

検索の索引は、embed版でもtantivyとlinderaを使う。検索の結果を、PCと同じにするためである。

拡張関数（`rquickjs`）は、フィーチャーにする。既定では入る。最初のAndroid版は、これを外してビルドする。外したときは、拡張関数を呼ぶところが何もしない。

### embed版のつなぎ方

フロントエンドの側に、クレートを1つ足す。このクレートが、`shell-native`の`Host`を実装する。`ApiOp`を`journal-core`の入口の呼び出しに直し、答えをJSONに書いて、コアの`rest.rs`にある既存の読み取りに渡す。知らせは、SSEのメッセージと同じJSONにして、コアへ渡す。

`journal-core`は、フロントエンドのコア（`peta-core`）を知らない。

### 進め方

ジャーナルサーバーの動きは変えない。RESTとMCPの答えは、切り出しの前と同じである。既存の結合テストが、これを守る。切り出しは、検索、ページ、項目、ジャーナル、アトラス、設定の順に、1つずつ行う。

### このADRで決めないこと

Androidのシェルは、ADR 030で決める。Dropbox SDKでの同期、端末でのDBとフォルダーの置き場所、Kotlinの型、HTMLの描き方である。拡張関数を同期するフォルダーへ移すことも、ここでは決めない。

## Alternatives

### Alternative 1: axumのルーターを、プロセスの中で呼ぶ

クレートは分けない。embed版は、ソケットを開かずに、今のルーターへ要求を渡す。コアの`rest.rs`と、`server-client`の`Http`トレイトが、そのまま使える。

長所は、書く量が最も少ないことである。RESTと同じ動きになることも、何もしなくても保証される。

短所は3つある。アプリに、axum、tokio、rmcpが入る。要求も答えも、毎回JSONとHTTPの形を通る。MCPが同じ処理をもう一度書いている問題は、残る。

開発者は、項目の操作を中身のAPIで行う形を望んだ。そのため、選ばなかった。

### Alternative 2: 端末の中で、ジャーナルサーバーをそのまま動かす

アプリの中でサーバーを起動し、`localhost`のポートで待つ。シェルは、PCと同じくRESTとSSEでつなぐ。`shell-native`は変えずに済む。

長所は、Alternative 1と同じである。SSEも、そのまま使える。

短所は、Alternative 1の短所に加えて、端末でポートを開くことである。同じ端末のほかのアプリが、ノートを読み書きできる。アプリが裏に回ったときの、サーバーの止め方と起こし方も要る。

選ばなかった。

### Alternative 3: ファイルから直接答える`Host`を作る

DBを持たない。Dropboxの`.md`ファイルを読み、`ApiOp`のうち読み取りだけに答える。`.md`を読む部分だけを、サーバーから小さなクレートに切り出す。

長所は、切り出す量が小さいことである。DBも索引も要らない。

短所は、サーバーの読み取りを、別の形で作り直すことである。本文の検索、バックリンク、トランスクルージョンは、DBがないと答えにくい。編集を足すときには、合流（ADR 006）をもう一度書くか、この案を捨てることになる。

最初に考えた案である。embed版の考えを聞いて、やめた。

### Alternative 4: 答えを、型から型へ写す

`journal-core`の答えの型から`peta-core`の型へ、フィールドを1つずつ写す。JSONを通さない。

長所は、速いことである。

短所は、写す関数を、答えの型ごとに書くことである。既定値や型の違いの扱いを、もう一度決めることになり、RESTの答えとずれうる。JSONの費用がかかるのは、ページを開くときだけである。

選ばなかった。遅いと測れたら、ページの答えだけをこの形に替える。

### Alternative 5: 答えの型を、サーバーとフロントエンドで共有する

答えの型を1つのクレートに置き、両方が使う。変換もJSONも要らない。

短所は、今の2つの型が食い違っていることである。サーバーの項目には`parent_item_id`があり、コアの項目にはない。プロパティの型も違う。そろえる作業は、サーバー、コア、すべてのシェルに及ぶ。

今回の範囲には大きすぎるので、選ばなかった。

### Alternative 6: embed版では、索引を使わずにSQLiteで検索する

`SearchIndex`の実装を、もう1つ書く。本文を`LIKE`で調べる。

長所は、辞書の約46MBが要らないことである。索引を作ることも、保つことも要らない。今のデータの量では、速さも足りる。

短所は、検索の結果がPCと違うことである。活用形がそろわない。並び順とスニペットも、新しく書く。

開発者は、PCと同じ結果を選んだ。SQLiteのFTS5（trigram）も考えたが、3文字より短い語が当たらないので、日本語には向かない。

### Alternative 7: 拡張関数を、最初からAndroidに入れる

`rquickjs`の`bindgen`フィーチャーで、Android向けのバインディングを作る。

長所は、Androidで作ったページにも、PCと同じ拡張関数が働くことである。

短所は、Androidをビルドするどの機械にも、LLVMが要ることである。通るかどうかも、確かめていない。最初の版では、拡張関数が動く場面がなく、動かす関数のファイルも端末にない。

今は選ばなかった。Androidでページを作れるようにするときに、見直す。

## Confidence Level

方向についての確信度は高い。細部についての確信度は中程度である。

確信が高いのは、分け方である。サービスの層は、同期のコードで、axumにもtokioにも依存しない。ハンドラーの処理は、どれも同じ段でできている。知らせと検索の索引は、すでにトレイトである。切り出しは、今の形に沿って進められる。ジャーナルサーバーの動きが変わらないことは、既存の結合テストが守る。

確かめたことは3つある。`rquickjs`のほかの依存は、Android（`arm64`）向けにコンパイルが通った。tantivyとlinderaを入れたライブラリは、リンクまで通り、53.0MBだった。実際のDBの大きさも測った。

確かめていないことは5つある。

第一に、端末での動きである。確かめたのは、ビルドだけである。SQLite、tantivy、辞書の読み込みを、端末でもエミュレーターでも動かしていない。tantivyは、索引のファイルをメモリーに写して読む。Androidのアプリの領域でこれが働くかは、未確認である。

第二に、メモリーである。tantivyは、書き込み用に50MBを予約する設定である。辞書も、読み込むとメモリーを使う。端末で足りるかは、測っていない。

第三に、切り出しの量である。ハンドラーは約80KB、MCPは29KBある。調べたのは、ページ、項目、検索のハンドラーである。ジャーナル、アトラス、設定、同期、アセットのハンドラーは、呼んでいるサービスを見ただけで、中身は読んでいない。入口へ下ろしにくい処理が、そこにあるかもしれない。

第四に、JSONを通す費用である。端末で、大きなページを開くときに何msかかるかは、測っていない。PCで5msから10msという見積もりも、ADR 024の値からの推測である。

第五に、拡張関数を外したビルドである。外したときに、ほかのコードがコンパイルを通るかは、まだ試していない。

次のときに、この決定を見直す。

- 端末で、tantivyか辞書が動かないか、メモリーが足りないと分かったとき。Alternative 6を検討する。
- 端末で、ページを開く時間のうち、JSONの費用が目立つと測れたとき。Alternative 4を検討する。
- Androidでページを作れるようにするとき。Alternative 7を検討する。
- 切り出しの途中で、入口へ下ろせない処理が多いと分かったとき。Alternative 1を検討する。
- アプリの大きさが問題になったとき。辞書を埋め込まずに、初回に取ってくる形を考える。

## Consequences

### 良い結果

REST、MCP、embed版が、同じ入口を通る。拡張関数の呼び出し、知らせ、答えの組み立ては、1か所になる。MCPが同じ処理をもう一度書いている今の重なりが、なくなる。

Androidのシェルは、PCと同じ中身を使う。取り込み、項目ごとの合流（ADR 006）、検索は、同じコードである。編集を足すときも、合流を書き直さない。

embed版の答えは、RESTの答えと同じJSONを、同じコードで読む。新しい変換のコードがないので、ずれない。

`journal-core`は、HTTPなしでテストできる。今は、ハンドラーにある処理を確かめるには、サーバーを立てる必要がある。

SwiftUIとWinUIのシェルにも、道が開く。サーバーを別に動かさずに、同じ中身を組み込める。

### 悪い結果

切り出しは、大きな作業である。ハンドラーとMCPを合わせて、約110KBのコードを直す。その間、サーバーの新しい機能は、切り出しとぶつかりやすい。

Androidのアプリは、辞書のために大きくなる。1つのABIあたり約51MB、APKでは約13MB増える。

embed版は、答えのたびにJSONを書いて読む。大きなページを開くときに、その分だけ遅くなる。

最初のAndroid版には、拡張関数がない。Androidでページを作れるようにすると、PCで作ったページと中身が違ってくる。

入口の操作を1つ足すたびに、直すところが増える。`journal-core`の入口、RESTのハンドラー、MCPの道具、embed版の`ApiOp`からの対応である。

`journal-core`の入口の形が、約束になる。今は、ハンドラーがサービスを自由に組み合わせている。切り出しのあとは、入口にない組み合わせを、外から行えない。

### 中立的な結果

`journal-server-rust`のワークスペースのクレートは、`hmtid`、`core`、`server`の3つになる。

フロントエンドのワークスペースに、`journal-core`に依存するクレートが1つ増える。フロントエンドからサーバーのワークスペースへの依存は、今は`hmtid`だけである。

定期の仕事を回す役は、外に出る。embed版では、これを誰が回すかを、ADR 030で決める。

カバレッジとミューテーションテストの設定（`.cargo/config.toml`、`.cargo/mutants.toml`）を、2つのクレートに合わせて直す。

構成図（`docs/frontend-architecture.svg`）に、`journal-core`とembed版を描き足す。

Androidのシェルの詳細は、ADR 030で決める。
