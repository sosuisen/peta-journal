# ADR 003: Atlas Crate Inside the Repository

## Status

Accepted

## Context

PetaJournalは、ディレクトリごとのアトラスを`index_atlas.md`のアウトラインとして持つ。サーバーはそのアウトラインを書き、フロントエンドは読んで`atlas.js`で描く。項目の種類の判定、グループの対応付け、アイコンやblobのSVG、`atlas.js`が読むシーンのJSONは、サーバーとフロントエンドの両方で使う処理である。

2026年10月、sosuisen.netでも同じアトラスを描くことになった。サイトはAstroの静的サイトで、`npm run sync`のときにRustのツールで`index_atlas.md`をシーンのJSONに変換する。下書きのカードはラベルを伏せ、元のラベルの幅をフォントで測って保つ。この処理もPetaJournalと同じ規則で動く必要がある。

そこで、アトラスの処理をクレート`peta-atlas`にまとめ、サーバー・フロントエンド・サイトの3つから使う。問題は、このクレートをどこに置くかである。別リポジトリに置けば独立性は高いが、クレートを変えるたびにPetaJournal側の依存を上げる手順が増える。同じリポジトリに置けば1つのPRで変えられるが、サイトのような外のプロジェクトはPetaJournalのチェックアウトに依存する。

このクレートは、将来、別のリポジトリに切り出す前提である。切り出しやすい形で置く必要がある。

## Decision

クレート`peta-atlas`を、peta-journalリポジトリの`atlas-rust/`に置く。サーバー（`journal-server-rust`）とフロントエンド（`frontend-rust`）は、パス依存`path = "../../../atlas-rust"`で使う。sosuisen.netも、隣のチェックアウトへのパス依存`path = "../../../../PetaJournal/peta-journal/atlas-rust"`で使う。

将来の切り出しを前提に、クレートは次の形に保つ。

- `atlas-rust/`は、サーバーとフロントエンドのどちらのワークスペースにも入れない。独立したクレートとして、自分の`Cargo.toml`と`.gitignore`を持つ。
- クレートは、PetaJournalの他のクレートに依存しない。依存するのは外部のクレート（`picturesque-marks`、`serde`、`rustybuzz`）だけにする。
- PetaJournalの固有の型は、クレートの中に持ち込まない。項目は`AtlasItem`トレイトで受け取り、サーバーとフロントエンドがそれぞれ自分の型に実装する。
- PetaJournalでしか使わない機能は、サーバーかフロントエンドに置き、クレートに入れない。
- 機能フラグ（`marks`、`measure`）で、使う側が要る部分だけを選べるようにする。
- `BUILD.md`にクレートの節を置き、構成と役割を書く。

切り出すときは、`atlas-rust/`を`git subtree split`で履歴ごと新しいリポジトリにし、3つの使う側のパス依存をGit依存かcrates.ioの版に替える。

## Alternatives

### Alternative 1: 最初から別リポジトリにする

クレートを`peta-atlas`リポジトリに置き、PetaJournalとサイトはGit依存かcrates.ioの版で使う。独立性は最も高い。しかし、クレートを変えるたびに、まずクレートのPRを出し、それからPetaJournalで依存を上げる2段階になる。CIは2つのリポジトリにまたがり、1つのPRでクレートと使う側を同時に確かめられない。クレートはまだ作ったばかりで、サーバーとフロントエンドの変更に合わせて頻繁に変わる。この段階で2段階の手順を取ると速度が落ちるため、選ばなかった。

### Alternative 2: サーバーかフロントエンドのワークスペースに入れる

`frontend-rust/crates/atlas`のように、既存のワークスペースのメンバーにする。ビルドの設定は最も簡単になる。しかし、サーバーはフロントエンドのワークスペースの外にあり、サイトはさらに外にある。ワークスペースのメンバーは、そのワークスペースの`Cargo.lock`と依存の解決に縛られる。切り出すときにワークスペースから外す作業が要る。そのため選ばなかった。

### Alternative 3: クレートにせず、サーバーとフロントエンドにそれぞれ持つ

アトラスの処理をサーバーとフロントエンドに重複して書き、サイトも自分で書く。依存の設定は要らない。しかし、項目の種類の判定やラベルの規則が3か所にあり、片方だけが変わるとアトラスの見え方が食い違う。実際、クレートにまとめる前は、`card_label`のテストがサーバーとフロントエンドに重複していた。そのため選ばなかった。

## Confidence Level

中程度。同じリポジトリに置くこと自体には確信がある。1つのPRでクレートと使う側を変え、CIで確かめられる。サイトのような外のプロジェクトが隣のチェックアウトに依存する不便さは、サイトの本番ビルドがコミット済みの生成物を使うため、今は問題にならない。

確信が中程度なのは、切り出す時期が決まっていないためである。クレートの境界が正しいかは、サイト以外の使う側が現れたときに分かる。

次の状況になったら見直す。

- PetaJournal以外のプロジェクトが2つ以上クレートを使うようになったとき。パス依存の手間が、2段階のPRの手間を上回る。
- クレートの変更がサーバーとフロントエンドの変更から独立してきたとき。1つのPRで同時に変える利点が薄れる。
- クレートがPetaJournalの固有の型に依存し始めたとき。切り出せなくなる前に、境界を直すか、切り出すかを決める。

## Consequences

良い結果。アトラスの規則が1か所になる。項目の種類の判定、グループの対応付け、SVG、シーンのJSON、ラベルの幅の測定を、サーバー・フロントエンド・サイトが同じコードで行う。クレートの変更と使う側の変更を1つのPRにまとめ、CIで同時に確かめられる。クレートは独立した形を保つので、切り出すときの作業は、`git subtree split`と依存の書き換えだけで済む。

悪い結果。サイトのように外からクレートを使うプロジェクトは、隣にPetaJournalのチェックアウトを置く必要がある。`npm run sync`はPetaJournalの`main`の状態に依存し、クレートの変更がサイトに影響することがある。クレートに版がないので、サイトがどの時点のクレートを使ったかはPetaJournalのコミットでしか分からない。

中立的な結果。クレートに入れてよいものの基準が決まる。PetaJournalの固有の型に依存するものは入れない。PetaJournalでしか使わない機能も入れない。この基準を守る限り、クレートはいつでも切り出せる。切り出した後は、使う側のパス依存をGit依存かcrates.ioの版に替え、このADRをSupersededにする。
