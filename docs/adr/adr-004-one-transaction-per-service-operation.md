# ADR 004: One Transaction per Service Operation

## Status

Accepted

## Context

サーバーのリポジトリは、メソッドが呼ばれるたびにプールから接続を取り、自分でトランザクションを開いて閉じる。この形の箇所は34か所ある。サービスは、そのメソッドを何回も呼んで1つの操作を組み立てる。項目の作成は「保存→親の計算し直し→タグの同期」、削除は「写しの作成→削除→プロパティの削除→親の計算し直し」である。

そのため、サービスの操作は途中で失敗しうる。失敗すると、中途半端な状態がDBに残る。たとえば、結合で本文だけがつながって元の項目が残る。グループ削除で一部の項目だけが消える。

検索索引、Markdownの書き出し、SSEの通知は、DBの外にある。これらはトランザクションに入れられない。

SQLiteはWALモードで動く。書き込みは`BEGIN IMMEDIATE`で始め、ロックを先に取る。1つの接続が書き込みのトランザクションを開いている間、別の接続の書き込みは待たされる。busy timeoutは30秒である。

## Decision

サービスの操作ごとに、1つのトランザクションを開く形を採用する。

- サービスが操作の最初に接続を1つ取り、`BEGIN IMMEDIATE`でトランザクションを始める。DBの変更がすべて済んだらcommitする。
- リポジトリには、渡された接続の上で動く関数を置く。`save_in`、`delete_in`のように`_in`を付ける。接続を自分で取る既存のメソッドは、その関数を呼ぶ薄い包みにする。
- トランザクションの中では、別の接続で書き込む処理を呼ばない。デッドロックになるためである。タグページの作成や削除も、この中では呼ばない。
- DBの外の仕事（検索索引、タグページ、書き出し、SSE）は、commitの後にまとめて行う。サービスは、トランザクションの中でその一覧を集め、commitのあとに実行する。
- 一度にすべてを移さない。グループ削除から入れ、結合・作成・移動の順に、操作ごとに移す。
- 接続を自分で取るメソッドと`_in`関数の両方があるのは、移行中の形である。最終形では、リポジトリの関数は接続を引数に取るものだけにし、接続を自分で取る側は消す。

## Alternatives

### Alternative 1: 今のまま（リポジトリのメソッドごとにトランザクション）

変更がない。ただし、サービスの操作が途中で失敗すると中途半端な状態が残る。結合で本文だけがつながる、グループ削除で一部だけが消える、といった形である。この問題を直すことが目的なので、選ばない。

### Alternative 2: リポジトリに「まとめて行う」メソッドを足す

たとえば`delete_tree`や`merge`をリポジトリに置き、その中で1つのトランザクションを開く。トランザクションの境界はリポジトリに閉じる。短所は、操作の手順（写しの作成、削除、親の計算し直し）がリポジトリに移り、ドメインのルールがインフラ層に漏れることである。操作が増えるたびにリポジトリが太る。選ばない。

### Alternative 3: Transactional Outbox

DBの外の仕事（検索索引、書き出し、通知）を、同じトランザクションでoutboxテーブルに書き、別の処理が拾って実行する。commitの後の処理が落ちても取りこぼさない。長所は堅さである。短所は、テーブルと拾う処理が増えることである。このサーバーは1人のローカルで動き、検索索引と書き出しは起動時に作り直せる。今は過剰なので選ばない。取りこぼしが問題になったら見直す。

## Confidence Level

高い。トランザクションの境界をサービスに置く形は、Unit of Work（Fowler, PoEAA）として広く使われている。Springの`@Transactional`、Railsのサービスオブジェクト内の`transaction`、Rustのsqlxやdieselで接続を引数に取る慣習と同じ形である。

見直すのは次のときである。

- 1つの操作が長くなり、書き込みロックを長く持つようになったとき。SQLiteは書き込みが1つなので、ほかの書き込みが待たされる。
- 複数のサービスにまたがる操作が出てきたとき。トランザクションをどこで開くかを決め直す。
- commitの後の処理の取りこぼしが実害になったとき。Transactional Outboxを検討する。

## Consequences

良い結果。

- サービスの操作は、全部か無かになる。中途半端な状態がDBに残らない。
- 操作の手順はサービスに残り、リポジトリは薄いままである。
- DBの外の仕事がcommitの後に集まるので、失敗の影響がDBに及ばない。

悪い結果。

- 移行中は、接続を自分で取るメソッドと`_in`関数の両方がある。読み手は2つの形を見る。移行が終わるまで続く。
- トランザクションの中で別の接続の書き込みを呼ぶとデッドロックになる。レビューで見る必要がある。コンパイラは止めてくれない。
- commitの後の処理が落ちると、検索索引や書き出しがDBとずれる。起動時の作り直しで戻る。

中立的な結果。

- リポジトリの関数は、`&Connection`を引数に取る形に揃っていく。`Transaction`は`Connection`にderefするので、同じ関数がトランザクションの中でも外でも使える。
- 移行は操作ごとに行う。グループ削除が最初で、結合・作成・移動と続く。移行の進み具合は`docs/plans.md`に書く。
