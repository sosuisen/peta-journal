# ADR 043: Code Points as the Unit of Text Positions

## Status

Accepted

## Context

PetaJournalでは、本文の中の位置を、モジュールの間で受け渡す。目的は5つある。

- A. 編集中のカーソル：Enterで項目を分ける位置、貼り付ける位置、開くリンク、上下に移るときのカーソル、画像を入れる位置。シェルからcoreへ、coreからサーバーへ渡る。
- B. カーソルの置き場所の指示（`FocusRequest.cursor`、Undoの戻し先）：coreからシェルへ渡る。
- C. 表示した文字に触れた位置：シェルからcoreへ渡る。
- D. 表示の段落の始まり（`RichParagraph.start`など）：coreからシェルへ渡る。Cのために使う。
- E. 文字列の長さ：検索の抜粋など。サーバーの中で使う。

位置の数え方は、4つある。家族の絵文字「👨‍👩‍👧」は、UTF-8では18バイト、UTF-16では8単位、コードポイントでは5、書記素（人が1文字と感じる単位）では1である。

core、サーバー、Emacsは、コードポイントで数えている。RESTの貼り付けと分割の`cursor`も、コードポイントである。一方、5つのシェルのUI（ブラウザ、AppKit、UIKit、WinUI、Android）は、UTF-16で数える。RustはUTF-8で文字列を持つので、切るときはバイトの位置に直す。書記素を数えている所はない。iOSが、触れた位置を絵文字の境に寄せるときに使うだけである。

UTF-16とコードポイントの換算は、各シェルが自分で書いている。macOSとWindowsは自前のループ、iOSは自前の関数、Androidは標準の関数、Web版はRustの関数を使う。書き方がばらばらなので、動きも食い違う。iOSは、サロゲートペアの途中を指されると、カーソルを本文の最後に置く。Web版は、キーの再生でUTF-16の位置を1ずつ動かすので、絵文字の半分だけを消すおそれがある。

表示した文字への接触（C）は、iOSとAndroidだけが`ShownTextTouched`でcoreに送る。coreが、表示の文字の位置を本文のMarkdownの位置に直す。Web版、macOS、Windowsは、表示の文字の位置を、そのままMarkdownの位置として使う。そのため、リンクや強調の記号の分だけ、カーソルがずれる。

coreが自分で決める位置は、書記素の境を見ない。触れた位置を直した結果が絵文字の途中に入ると、Enterで1つの絵文字が2つの項目に割れるおそれがある。

2026-11-14に、重複したコードをまとめる作業の中で、これらを調べた。どのモジュールが、どの数え方で、何のために位置を使うかを決めておく必要がある。

## Decision

モジュールの間で受け渡す文字の位置と長さは、コードポイント（Rustの`char`、Unicodeのスカラー値）で数える。core、サーバー、Emacs、REST、MCPの間では、換算をしない。

UTF-16は、シェルの中だけで使う。UIのテキスト欄や表示の文字の位置は、シェルからcoreへ渡る前に、コードポイントへ直す。coreからシェルへ渡る位置は、シェルがUTF-16に直す。換算が要る境は、次の2つだけである。

- **テキスト欄の境（AとB）。** 編集中のカーソルとカーソルの置き場所の指示は、本文のMarkdownの中の位置である。UTF-16とコードポイントの換算は、Rustの1組の関数で行う。関数は`client-core`に置く。Web版はそれを直接使い、macOSとWindowsは`client-shell-http`から、iOSは`client-shell-embedded`から使う。サロゲートペアの途中を指す位置は、その文字の後ろに寄せる。Androidは、標準の`codePointCount`と`offsetByCodePoints`をそのまま使ってよい。結果が同じだからである。
- **表示の文字の境（CとD）。** 表示した文字に触れた位置は、どのシェルも`ShownTextTouched`でcoreに送る。シェルは、表示の文字の位置をMarkdownの位置として使わない。Markdownの位置に直すのはcoreである。Web版、macOS、Windowsも、iOSとAndroidと同じ形に移す。

UTF-8のバイトの位置は、Rustの中で文字列を切るときだけ使う。モジュールの外には出さない。

書記素は、受け渡しの単位にしない。区切り方がUnicodeの版とOSで変わるからである。coreが自分で位置を決めるときは、その位置を書記素の境に寄せる。触れた位置をMarkdownの位置に直すときが、これに当たる。寄せる処理には`unicode-segmentation`クレートを使う。

## Alternatives

### Alternative 1: 位置をUTF-16で数える

coreもサーバーもUTF-16で数え、5つのシェルの換算をなくす。エディターの通信の標準（LSP）も、初めはUTF-16だった。

長所は、5つのシェルが、受け取った位置をそのまま使えることである。

短所は2つある。1つ目は、UTF-16の位置がサロゲートペアの途中を指せることである。単位をUTF-16にすると、どのメッセージにもこの壊れた位置が届きうるので、受け取る側のすべてが確かめて直す必要がある。コードポイントなら、壊れた位置はシェルとの境でしか生まれず、そこで1回直せば済む。2つ目は、換算がなくならず、移るだけであることだ。Emacsと、RESTを呼ぶ多くの道具は、コードポイントで数える。換算が5つのシェルから、Emacsと外の利用者に移り、APIの単位も分かりにくくなる。

なお、絵文字の途中に位置が入る問題は、UTF-16でも残る。書記素の境に寄せる処理は、どちらの単位でも要る。変更が大きいこと（coreで位置を扱う17か所と、テストの約100か所）も加わるので、採らない。

### Alternative 2: 位置を書記素で数える

人が1文字と感じる単位で数える。絵文字が割れることは、原理的になくなる。

しかし、書記素の区切り方は、Unicodeの版で変わる。Rustのクレートと各OSの区切り方が食い違うと、同じ位置が別の文字を指す。また、どのUIも書記素では位置を返さないので、すべての境で換算が要る。採らない。書記素は、coreが決めた位置を寄せるときだけ使う。

### Alternative 3: 各シェルが、今のまま自分で換算する

変更はない。しかし、換算の決まりが5つの言語に残り、iOSのような食い違いが続く。表示の文字の位置をMarkdownの位置として使うずれも、Web版、macOS、Windowsに残る。採らない。

### Alternative 4: イベントに本文を添えて、coreが換算する

シェルはUTF-16の位置と、その時点のテキスト欄の文字列を送り、coreが換算する。シェルは換算を知らなくて済む。しかし、キーを押すたびに本文を境の向こうへ送ることになる。編集中の本文と、coreが持つ本文がずれる時もある。採らない。

## Confidence Level

確信は高い。コードポイントは、core、サーバー、Emacs、RESTで、すでに使っている単位である。この決定は、今の形を明文にし、シェルとの境の換算を1か所にまとめるものである。

確かめていない点は、次のとおりである。

- iOSから`client-shell-embedded`の換算の関数を呼ぶ形が、キーを押すたびに呼んでも遅くならないか。遅いときは、iOSに限って標準の関数で書いてよい。その場合も、サロゲートペアの途中は後ろに寄せる決まりを守り、テストで確かめる。
- coreが書記素の境に寄せるとき、`unicode-segmentation`の区切り方と、各OSのテキスト欄の区切り方が、絵文字で食い違わないか。食い違っても、位置がずれるのは1つの書記素の中に限られる。
- Web版、macOS、Windowsを`ShownTextTouched`に移すと、表示の文字の位置を取る処理が、各シェルに要る。iOSとAndroidで作った形が、ブラウザ、AppKit、WinUIにも合うかは、まだ試していない。

次のときは、この決定を見直す。

- APIの利用者の多くが、UTF-16で数える道具になったとき。
- コードポイントでは数えない新しいシェル（たとえば、UTF-8のバイトで数えるTUIのツールキット）を加えるとき。
- 書記素の区切り方が、Unicodeの版の間で大きく変わり、寄せる処理が問題を生むとき。

## Consequences

良い結果は、次のとおりである。

- 位置の単位が、モジュールの間で1つになる。core、サーバー、Emacs、REST、MCPの間で、換算を書かずに済む。
- UTF-16の換算の決まりが、Rustの1か所になる。macOS、Windows、iOSの自前の換算は消える。iOSのサロゲートペアの食い違いも消える。
- どのシェルも、表示の文字の位置を`ShownTextTouched`でcoreに送る。Web版、macOS、Windowsで、リンクや強調の記号の分だけカーソルがずれる問題が直る。
- coreが決めた位置で、絵文字が2つの項目に割れることがなくなる。

悪い結果は、次のとおりである。

- macOS、Windows、iOSは、カーソルを換算するたびに、Rustの関数を境越しに呼ぶ。
- `client-core`が、`unicode-segmentation`に依存する。wasmの大きさが少し増える。
- Web版、macOS、Windowsに、表示の文字の位置を取る処理を新しく書く。

中立的な結果は、次のとおりである。

- Androidは、標準の関数で換算を続ける。換算の決まりは、Rustの関数と同じである。
- UTF-8のバイトの位置は、Rustの中で文字列を切るときに使い続ける。ただし、バイトの位置で切る所は、文字の途中で切らないことを確かめる。週のジャーナルの名前を切り出す`extract_journal_name`は、ファイル名をバイトの位置で切っている。`-W`の前に日本語などがあるとパニックするので、直す。
- サーバーの中では、検索の抜粋の長さを、1つは200文字、もう1つはtantivyの100バイトで数えている。どちらもサーバーの外に出ないので、この決定の対象ではない。
- 次の作業をplansに積む。
  - 換算の関数をcoreに置き、Web版、macOS、Windows、iOSで使う。Web版のキーの再生も、この関数で動かす。
  - Web版、macOS、Windowsを`ShownTextTouched`に移す。今の「（開発者が望めば）」の項目を、この決定で確定させる。
  - coreが決めた位置を、書記素の境に寄せる。
  - `extract_journal_name`を、文字の境で切るように直す。
  - 保留したキーの再生で、複数のコードポイントでできた1文字（異体字セレクタやZWJ付きの絵文字）が捨てられる問題を直す。
