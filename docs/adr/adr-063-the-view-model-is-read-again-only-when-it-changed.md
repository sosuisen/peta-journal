# ADR 063: The View Model Is Read Again Only When It Changed

## Status

Accepted

## Context

ADR 024は、ネイティブのシェルが`ViewModel`の全体を、描画のたびにbincodeで受け取ると決めた。
4つのネイティブのシェル（SwiftUI、WinUI、iOS、Android）は、どれも1つのキーで`ViewModel`を2回読む。

1. シェルは、イベントをコアへ送った直後に読む（macOSの`Shell.send`、`typed`、`pressed`など）。
   描画の依頼を待つと、テキストの欄が古い文字を読み戻し、打ったキーが消えるためである。
2. 同じイベントでコアが出した`Render`が、メインスレッドに届いたときに、もう一度読む。

2回目の読み取りでは、`ViewModel`は1回目と同じである。
2回目は、何も変わっていないものを、Rustでシリアライズし、シェルで読み直している。

2026-11-11に、`stickies-mac`の`TypingSpeedTests`で、1000項目のページの入力を測った（M1のMacBook Air）。
`ViewModel`を1回読むのに約4.9msかかる（Rustの側が約2.6ms、Swiftの側が約2.3ms。344KB）。
描き直しを合わせると、1つのキーでメインスレッドを約14ms使う。
画面の1コマ（16.7ms）に対して、余裕は小さい。

`Render`を待って読み、呼び出しの直後には読まない呼び出しもある。
macOSとWinUIの`open`、クリップボードを尋ねられたときの答え（`resolve`）、iOSとAndroidの`sync`である。
これらは、`Render`で描き直されることに頼っている。

## Decision

`client-native-bridge`の`NativeShell`に、`ViewModel`が前に読まれてから変わったときだけ全体を返す`view_if_changed()`を足す。
変わっていなければ、空のバイト列を返す。
シェルは`Render`を受けたときに`view_if_changed()`を呼び、空なら読み取りと描き直しを飛ばす。

### 変わったかどうかの印

`NativeShell`は、「変わった」の印を1つ持つ。
コアがイベントか答えを処理するたびに、`NativeShell`は印を立てる。
シェルからの呼び出し（`update`、`press`、`typed`、`drag`、`open`、`back`、`forward`、`resolve`）と、Rustの中のレーン（`Api`、`Sse`、`Timer`）が答えたときの両方である。
`view()`と`view_if_changed()`は、全体を返したときに印を下ろす。
印を立て始める時点は、`NativeShell::new`である。
最初の読み取りは、いつも全体を返す。

### シェルの約束

- シェルが`ViewModel`を読む時点は、今のままにする。
  呼び出しの直後に読む所は`view()`を使い、`Render`で読む所は`view_if_changed()`を使う。
- `view()`の意味は変えない。
  いつも全体を返す。
- `client-shell-http`と`client-shell-embedded`のFFIに、`view_if_changed()`を足す。
  4つのシェルの`Border`にも、同じものを足す。

### 1つのキーの流れ

1. シェルが`typed`を呼ぶ。
   コアがイベントを処理し、`NativeShell`が印を立てる。
   コアが出した`Render`は、今のままシェルへ送られる。
2. シェルが`view()`で全体を読む。
   `NativeShell`は印を下ろす。
3. `Render`がメインスレッドに届く。
   シェルが`view_if_changed()`を呼ぶ。
   印は下りているので、空が返る。
   シェルは何もしない。

2と3の間にサーバーの答えが届けば、レーンが答えたときに印が立つ。
3では全体が返り、シェルは描き直す。

## Alternatives

### Alternative 1: 呼び出しの中で出た`Render`を送らない

`NativeShell`が、シェルからの呼び出しの中で出た`Render`をシェルへ送らない。
crux_coreの`EffectRouter::update`は、コアが出した要求を呼び出しと同じスレッドで処理するので、呼び出しの中かどうかは見分けられる。
サーバーの答えは別のスレッドで出るので、呼び出しの中かどうかはスレッドごとに見る必要がある。
シェルは、どの呼び出しのあとでも`ViewModel`を読む約束にする。
`open`、`resolve`、`sync`のあとにも、読む処理を足す。
選ばなかった。
読み忘れた呼び出しでは画面が古いままになり、テストでしか気づけないためである。
`sync`は別のスレッドから呼ぶので、そこで出た`Render`を止めると、メインスレッドで読む処理が別に要る。

### Alternative 2: 呼び出しが「描き直しが要る」を返す

`update`、`typed`、`press`、`open`、`resolve`などが真偽値を返し、シェルは真のときだけ読む。
選ばなかった。
2つのFFIと4つのシェルで、呼び出しの形がすべて変わるためである。
`Render`との二重の読み取りも、別に止める必要がある。

### Alternative 3: 変わった部分だけを境界に通す

`ViewModel`の差分を作り、シェルに渡す。
選ばなかった。
ADR 024が全体を通すと決めた理由（差分はシェルのUIの仕組みに任せる）は、今も変わっていない。
1000項目でも1回の読み取りは数msで、2回を1回にすれば足りる。

## Confidence Level

高い。
印を立てる所と下ろす所が`NativeShell`の中で閉じており、シェルが読む時点は変わらない。
印を立て忘れた所があっても、困るのは`Render`での描き直しだけで、呼び出しの直後の読み取りは今のまま全体を返す。

次のときに見直す。

- コアが、イベントも答えも処理せずに`ViewModel`を変える道を持ったとき。
  たとえば、コアの外から`Model`を書き換える処理を足したとき。
- 1つのコアの`ViewModel`を、2か所以上が読むようになったとき。
  印は1つなので、一方が読むと、もう一方の`view_if_changed()`が空を返す。
- 1回の読み取りでも、画面の1コマに収まらなくなったとき。
  そのときは、Alternative 3（差分）を考え直す。

## Consequences

### 良い結果

- 1つのキーで、`ViewModel`のシリアライズと読み取りが1回になる。
  1000項目のページで、1つのキーのメインスレッドの時間が約4.9ms減る見込みである（2026-11-11の測定から）。
- シェルが`ViewModel`を読む時点の約束は変わらない。
  `Render`を待って描き直す呼び出しも、今のまま動く。
- 速さの理由で2回目を読まない、という判断を、4つのシェルが別々に持たなくて済む。

### 悪い結果

- `view_if_changed()`は、ただ読むだけの関数ではない。
  印を下ろすので、呼ぶ順で答えが変わる。
- 4つのシェルの`Render`を受ける所に、空なら飛ばす処理を1つずつ足す。
- 印を立て忘れた道があると、その道での`Render`は画面を描き直さない。
  テストで、レーンの答え（`Api`、`Sse`、`Timer`）のあとの`Render`で描き直されることを確かめる必要がある。

### 中立的な結果

- `shell-leptos`と`shell-emacs`は`Core`を直接呼ぶので、変わらない。
- `Render`の数は変わらない。
  減るのは、シェルが`Render`を受けたあとの読み取りだけである。
