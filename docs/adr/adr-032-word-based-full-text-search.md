# ADR 032: Word-Based Full-Text Search

## Status

Accepted

## Context

PetaJournalの全文検索は、tantivyとlindera（辞書はIPADIC）で作っている。索引は、項目の本文を辞書で語に切り、動詞と形容詞を基本形に直し、助詞や記号を捨てる。問い合わせも、同じ切り方で語にする。検索は、語が一致した項目を返す。この作りは、Java版のサーバーが使っていたLuceneの`JapaneseAnalyzer`に合わせたものである。

2026-11-12に、Androidのアプリで「語の一部で探すと見つからない」ことに気づいた。項目は「富士山に登りました。」である。索引だけの検索と、Androidのコアを通した検索の両方で測ると、結果は次のとおりだった。

| 検索の語 | 結果 | 理由 |
|---|---|---|
| 富士山 | 見つかる | 索引の語と同じである |
| 登る | 見つかる | 索引は「登り」を基本形の「登る」に直している |
| 登りました | 見つかる | 問い合わせも「登る」になる |
| 富士 | 見つからない | 「富士」は「富士山」とは別の語である |
| 山 | 見つからない | 同じ理由である |
| 登り | 見つからない | 単独では名詞の「登り」になる。文の中では動詞の「登る」である |

これは、索引と問い合わせで切り方が違う不具合ではない。語の単位で合わせる検索の性質である。PCのサーバーでも、Androidでも、同じ結果になる。

語の切り方は辞書が決めるので、利用者には予想しにくい。たとえば、「東京都」は「東京」と「都」に切られるので、「東京」で見つかる。「富士山」は1語なので、「富士」では見つからない。

ページの名前の検索は、これとは別である。名前は、語が一致しないときに、部分一致でも探す。この問題は、本文の検索だけにある。

## Decision

本文の全文検索は、今の語の単位の検索のままにする。語の一部で探しても見つからないことは、直さない。

部分一致で補う仕組みも、2文字ずつの索引（bigram）も、今は足さない。理由は3つある。

- 語をそのまま打てば、見つかる。動詞は、活用した形でも基本形でも見つかる。ふだんの検索は、これで足りている。
- 語の検索は、関係のない項目を拾いにくい。「山」で探して、「富士山」や「山田」のすべての項目が出ることはない。
- 索引と問い合わせは、PCのサーバーとAndroidで同じ`journal-core`を使う。検索を変えると、両方の結果と索引が変わる。困っている場面が1つだけの今、その変更は大きすぎる。

見つからないときは、利用者が語を変えて探す。たとえば、「富士」ではなく「富士山」、「登り」ではなく「登る」と打つ。

この性質は、不具合として扱わない。`docs/plans.md`の未完了のタスクは消し、このADRを参照する1行に置き換える。

## Alternatives

### Alternative 1: 語の検索で見つからない分を、部分一致で補う

SQLiteの本文を`LIKE`で探し、語の検索の結果のあとに足す。索引は変わらず、作り直しも要らない。変更は小さい。

短所は、項目が増えると遅くなることである。`LIKE`は、すべての項目の本文を読む。また、結果に2つの並び方が混ざる。語の検索は点数の順で、部分一致には点数がない。

困っている場面が少ないので、選ばなかった。直すことになったら、最初に試す案である。

### Alternative 2: 2文字ずつの索引（bigram）を足す

本文を2文字ずつに切った索引を、語の索引の横に持つ。どの部分で探しても、速く見つかる。

短所は、索引が大きくなることと、すべての索引を作り直すことである。1文字の検索は、これでも見つからない。関係のない項目も拾いやすくなる。変更が大きいので、選ばなかった。

### Alternative 3: 語の切り方を変える

linderaの設定を変えて、「富士山」を「富士」と「山」に切る。または、長い語とその部分の両方を索引に入れる。

短所は、切り方が辞書とlinderaの版に左右されることである。「登り」と「登る」の違いは、これでは直らない。品詞の判定が、文の中と単独とで変わるためである。一部しか直らないので、選ばなかった。

### Alternative 4: 問い合わせを前方一致にする

問い合わせの語の終わりに`*`を付けて、その語で始まる語を探す。「富士」で「富士山」が見つかる。

短所は、「山」で「富士山」が見つからないことである。「登り」も見つからない。索引の語は「登る」で、「登り」で始まらないためである。これも一部しか直らないので、選ばなかった。

## Confidence Level

確信度は中程度である。

語の検索の性質そのものには、確信がある。索引だけの検索と、Androidのコアを通した検索の両方で測り、同じ結果を得た。

直さないという判断は、今の使い方に合わせたものである。気づいた場面は、テスト用の1つの項目だけである。実際のノートで、どれほど困るかは測っていない。

次のどれかが起きたら、この決定を見直す。

- 実際のノートで、語の一部で探して見つからないことが、何度も起きる。
- 辞書にない語が増える。たとえば、新しい製品の名前や、人の名前である。辞書にない語は、切り方が予想できない。
- Androidでの検索が主な使い方になる。指で打つときは、語を最後まで打たずに探すことが多い。

見直すときは、Alternative 1（部分一致で補う）から試す。

## Consequences

良い結果は、次のとおりである。

- 検索のコードと索引は、変わらない。PCのサーバーとAndroidで、同じ結果が出続ける。索引の作り直しも要らない。
- 検索は、関係のない項目を拾いにくいままである。
- 「見つからない」という報告が来たときに、不具合かどうかを、このADRの表で判断できる。同じ調査を繰り返さずに済む。

悪い結果は、次のとおりである。

- 語の一部で探しても、見つからない。利用者は、語を変えて探す必要がある。
- 語の切り方は辞書が決めるので、どの語で見つかるかを、利用者は予想しにくい。「東京」で「東京都」は見つかるが、「富士」で「富士山」は見つからない。
- 動詞の連用形と同じ形の名詞では、見つからない。たとえば「登り」である。

中立的な結果は、次のとおりである。

- ページの名前の検索は、今までどおり、部分一致でも探す。本文とは、合わせ方が違うままである。
- `docs/plans.md`の未完了のタスクは消える。代わりに、このADRを参照する1行が残る。
- 利用者向けの説明には、まだこの性質を書いていない。書くかどうかは、別に決める。
