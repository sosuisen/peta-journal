# ADR 006: Item-Level Last-Writer-Wins for Folder Sync

## Status

Accepted

## Context

PetaJournalは、Markdownファイルのフォルダを介して複数のPCを同期する。同期はDropboxなどのクラウドフォルダに任せる。サーバー間の通信はなく、トランザクションもない。各PCが受け取れるのは、フォルダに届いたファイルだけである。

これまでは、ページの`modified`で競合を判定していた。ファイルが新しければ、ファイルの項目でDBの項目を丸ごと置き換えた。DBが新しければ、ファイルを`.conflict`に退避し、DBで上書きした。そのため、PC Aが項目Xを、PC Bが同じページの項目Yを編集すると、片方の編集がDBから消えた。残るのはconflicted copyと`.conflict`のファイルだけで、人が拾い直す必要があった。

解決には、3つの制約がある。第一に、Markdownファイルを正本のまま保ち、人が読んで手で編集できるようにする。第二に、ファイルを受け取っただけでは、相手の状態が分からない。ある項目がファイルにないとき、相手が消したのか、相手がまだ見ていないのかを、日付の比較だけでは区別できない。第三に、Dropboxは同じパスの2つの版を合流しない。片方を正とし、もう片方をconflicted copyとして別の名前で残す。この2つのファイルが各PCに届く順序も決まっていない。

2台が同じ隙間に項目を足すと、`idx`が同じ値になることもある。`(page_id, idx)`にはUNIQUE制約がある。

## Decision

項目ごとのLast-Writer-Winsを採用する。規則の詳細は`docs/folder-sync-future.md`に書き、ここでは後から変えにくい決定だけを記録する。

**ファイル形式。** ページのファイルのメタデータ行に、項目の更新日`modified`を書く。アトラスのファイルと木のエクスポートには書かない。`modified`のない古い形のファイルは、ページの`modified`をすべての項目の日付として扱う。

**両方にある項目。** `modified`の新しい方を採る。日付が同じで中身が違う項目は、手で編集されたものとみなす。ファイルの中身を採り、`modified`を今の時刻にして、すぐに書き戻す。プロパティの変更でも`modified`を進める。`idx`の変更だけでは進めない。

**片方にだけある項目。** ここだけにある項目は、ファイルより後に変えたか、まだ書き出していなければ残す。それ以外は、相手が消したとみなして消す。ファイルだけにある項目は足す。ただし、ユーザーがここで、項目の`modified`より後に消した項目は足さない。

**消した項目の記録。** DBに表`deleted_items(id, deleted_date)`を置く。記録するのは、ユーザーが消した項目だけである。取り込みで消えた項目は記録しない。conflicted copyから戻せるようにするためである。この表はそのPCだけのもので、ファイルには書かない。

**`idx`が同じ項目。** `(page_id, idx)`のUNIQUE制約は保つ。取り込みのときに項目idの順で並べ、後ろの項目の`idx`を前後の間で計算し直す。

**conflicted copy。** もう1つの版として合流し、合流後に消す。コピーは項目を消さない。コピーの編集が負けて失われるときは、消す前に`.conflict`へ残す。内容がこのPCの書いたファイルと同じコピーは、ファイルが差し替わるまで待つ。

**アトラス。** 今までどおりページ単位で決める。各PCが自分のページから書くファイルなので、項目の日付を持たせるとファイルが揃わないためである。

## Alternatives

### Alternative 1: 本物のCRDT（AutomergeやYrs）

操作の履歴や各デバイスの状態ベクトルを持ち、数学的に収束させる。同時編集を文字単位で合流できる。一方で、履歴をバイナリで持つ必要があり、Markdownファイルは正本ではなく投影になる。人が手で編集できるファイルを正本に保つという狙いから外れるので、選ばなかった。

### Alternative 2: ページ単位のLast-Writer-Winsのまま

これまでの方式である。コードは最も単純で、ファイル形式も変わらない。しかし、同じページの別の項目を2台で編集すると、片方の編集がDBから消える。解決したい問題そのものなので、選ばなかった。

### Alternative 3: 日付の比較だけで削除を判定する

`deleted_items`を置かず、項目、ページ、前回の同期の日付を比べて「ここで消した項目」を推定する。スキーマが変わらない利点がある。しかし、2台がそれぞれ書き出したあとにファイルが届くと、まだ見ていない項目を消した項目と誤認し、項目を失う。実装の途中でこの穴を見つけたので、選ばなかった。

### Alternative 4: 消した項目の記録をファイルに書く

消した項目の記録をMarkdownファイルにも書き、相手のPCへ伝える。削除を確実に伝播でき、「相手が消したとみなす」推定が要らなくなる。しかし、ファイルに本文以外の記録が増え続け、手で編集するときの妨げになる。記録をいつ消してよいかを決める手順も要るので、選ばなかった。

### Alternative 5: `idx`のUNIQUE制約を緩める

UNIQUE制約を`(page_id, idx, id)`に緩めるか外し、同じ`idx`のまま項目idの順で並べる。`idx`を計算し直さずに済む。しかし、スキーマの変更が大きくなり、`idx`が一意であることを前提にしたコードも見直す必要がある。計算し直しても並びが同じなら同じ値になり、両側で揃うので、選ばなかった。

### Alternative 6: conflicted copyを無視し、人が拾う

これまでの扱いである。コードは増えない。しかし、2台が書き出して行き違ったときに、負けた版の編集と項目が自動では戻らない。項目単位の規則で残る隙間がここに残るので、選ばなかった。

## Confidence Level

確信度は中程度である。

規則そのものには、高い確信がある。2台の状態を作ってファイルを受け渡すテストと、ミューテーションテストで確かめた。一方で、実際のDropboxと2台のPCでは試していない。conflicted copyの実際の名前と、ファイルの差し替えとコピーの作成の順序は、確かめられていない。日本語版の`競合コピー`の形は、記憶に基づいている。

次の状況になったら、この決定を見直す。

- 実際のDropboxで、コピーの名前や届く順序が想定と違っていたとき。
- 2台の時計のずれで編集が消え、実際に困ったとき。この場合は、ハイブリッド論理時計を検討する。
- 相手が消したとみなした項目が、conflicted copyもできずに失われたとき。この場合は、削除の記録をファイルで伝える方式を検討する。
- Dropbox以外の同期サービスを使うとき。conflicted copyの作り方が違うためである。
- `deleted_items`の行数が問題になったとき。

## Consequences

### 良い結果

- 同じページの別の項目を2台で編集しても、両方が残る。
- 2台が書き出してファイルが行き違っても、負けた版の編集と項目はconflicted copyから自動で戻る。人が拾い直す場面が減る。
- 2台が同じ隙間に足した項目は、どちらのファイルが先に届いても同じ順に並び、`idx`も揃う。
- Markdownファイルは正本のままで、人が読んで手で編集できる。

### 悪い結果

- 2台の時計がずれていると、古い編集が新しい編集に勝つことがある。
- 2台が同じ項目を互いに見ずに編集すると、片方しかDBに残らない。負けた編集は、取り込みで失うと判定したときだけ`.conflict`に残る。
- `.conflict`のファイルが、失われない編集でも増えることがある。コピーの古い内容と本当の編集を、日付だけでは区別しきれないためである。
- `deleted_items`の行は増え続ける。今は消す手順がない。
- ここだけにある項目を「相手が消した」と推定する規則は残る。conflicted copyができない場面では、まだ見ていない項目を失うことがある。
- 取り込みの規則が増え、`ItemMerger`の理解に2台の場面を考える必要がある。

### 中立的な結果

- ファイルのメタデータ行に`modified`が増える。古い形のファイルも読める。ファイルが書き換わるのは、そのページを次に書き出すときである。
- スキーマは版2に上がる（ADR 005の方式）。古いサーバーは版2のDBを開けない。
- アトラスはページ単位のまま残るので、同期の規則が2種類になる。
- conflicted copyの合流は、Dropboxのファイル名の形に依存する。
