# ADR 066: Work Items in GitHub Issues, and Only the TDD Test List in `docs/plans.md`

## Status

Accepted

## Context

### 今の`docs/plans.md`

`docs/plans.md`は、tddスキルが使う作業用のtodoである。
1行目にギアを書き、その下にタスクを書く。
tddスキルは、このファイルを「使い捨てのtodo」と定めている。

ところが今の`docs/plans.md`は、336行ある（2026-11-19）。
中身には、性質の違うものが混ざっている。

- TDDのタスク
- 機能向上の案
- バグの調査メモ。日付つきの記録が、項目の下に積み上がっている
- 開発者が手で行う後片付け。たとえば、`~/.peta-journal/`にある控えを消す作業である
- 手元の環境だけで落ちるテスト。たとえば、手元のMacで落ちる`tests/it/watch.rs`である
- 実機が要るテスト。たとえば、AndroidとiOSとMacの付箋紙のテストである
- リファクタ、CI、道具の更新

そのため、次の問題が起きている。

- ファイルが長く、今のPRのテストリストがどれかを読み取りにくい。
- 使い捨てのはずのファイルが、PRをまたいで残り続ける。
- 並行して動く複数のセッションが、別々のブランチで同じファイルに書き足す。
  マージのときにコンフリクトが起きる。
  ブランチの上で足した項目は、マージするまでほかのセッションに見えない。
- 個人のノートの中身や、手元のパスが、リポジトリに入る。

### 並行セッション

このプロジェクトでは、複数のClaude Codeのセッションが、worktreeとブランチを分けて並行して動く。
PRを積み重ねることもある。
ADRの番号は、ほかのセッションとぶつかることがある。
作業の一覧は、作った時点で、どのセッションからも見える必要がある。

### パーソナルな文書

開発者は、パーソナルな文書をPetaJournalに置く。
PetaJournalのページは、Dropboxの同期で、どのPCからも読める。

## Decision

作業の一覧をGitHub Issuesに置き、`docs/plans.md`には今のPRのTDDのテストリストだけを書くことを採用する。

### 置き場所

| 置き場所 | 入れるもの | 終わり方 |
|---|---|---|
| `docs/plans.md` | ギアの行と、今のPRのTDDのテストリスト | PRがマージされたら、ギアの行だけに戻す |
| GitHub Issues | PRで閉じられる作業。バグ、機能向上、調査、リファクタ、CI、道具の更新、実機が要るテスト | PRの`Closes #N`で閉じる |
| ADR | 決めたことと、その理由 | 実装は、ADRごとに1つのissueにする |
| PetaJournal | パーソナルな文書。手元のパスや控え、個人のノートの中身、開発者が手で行う作業、まだ育っていない思いつき | 形になったら、issueに移す |

ADRの実装の作業は、issueにする。
issueの本文には、ADRへのリンクを書く。
決めたことと理由はADRに書き、issueには書き写さない。
2か所に同じ内容を書くと、片方だけが古くなるためである。

### issueの書き方

1つのissueには、1つのPRで閉じられる大きさの作業を入れる。
大きい作業は、本文のタスクリストか、sub-issueに分ける。

本文には、次の3つを書く。

- 何をするか。
  バグなら、再現の手順を書く。
- 関係するADRへのリンク。
- 完了の条件。

調べた結果は、日付つきのコメントとして足していく。
本文には、分かっていることの要約だけを残す。

個人のノートの中身と、手元のパスは、issueに書かない。
どうしても要るときは、PetaJournalのページIDだけを書く。
リポジトリはprivateだが、ノートの中身もタイトル名もGitHubに出さない方が安全だからである。

### ラベル

ラベルは、`docs/issue-labels.md`に従う。
ラベルの一覧は変わっていくため、ADRではなくdocsに置く。
ADRは探すのに手間がかかるためでもある。

### 流れ

1. issueを1つ選ぶ。
2. ブランチを作り、`docs/plans.md`にギアの行と、そのissueのテストリストを書く。
3. TDDを回す。
   途中で見つけた別の問題は、`docs/plans.md`ではなく、新しいissueにする。
4. PRの本文に`Closes #N`と書く。
5. PRがマージされたら、issueが閉じたことと、変更が`origin/main`に入ったことを確かめる。
   PRを積み重ねているときは、MERGEDになっても`main`に入っていないことがあるためである。
6. `docs/plans.md`を、ギアの行だけに戻す。

### 今の`docs/plans.md`から移す

今の`docs/plans.md`の項目は、次の手順で移す。

1. ラベルを作る。
2. 項目を、移す先ごとに分けた一覧にして、開発者に見せる。
   トップレベルのチェック項目1つを、issue 1つにする。
   子のチェックボックスは、issueの本文のタスクリストにする。
   開発者が手で行う作業と、個人のノートの中身は、PetaJournalに移す。
3. 開発者が一覧を確かめたら、`gh issue create`でissueを作る。
4. `docs/plans.md`を、ギアの行だけにする。

## Alternatives

### Alternative 1: 今の`docs/plans.md`を続ける

長所は、移す手間がないことである。
短所は、Contextに書いた問題がすべて残ることである。
特に、並行セッションの間で、足した項目がマージまで見えない。
そのため採らない。

### Alternative 2: issueをMarkdownファイルにしてリポジトリに置く

`docs/issues/*.md`を自作する方法と、Backlog.mdを使う方法がある。
長所は、AIがGrepとReadで読めることである。
バグを直すコミットで、issueも一緒に閉じられる。
短所は、ブランチの上で作ったissueが、マージするまでほかのセッションに見えないことである。
連番を使うと、ADRと同じように番号がぶつかる。
同じissueに2つのブランチから書き足すと、コンフリクトが起きる。
並行セッションが多いので採らない。

### Alternative 3: git-bug

issueを`refs/bugs/`のrefに、操作の記録として持つツールである。
長所は、コンフリクトが起きず、IDがハッシュなので番号がぶつからないことである。
短所は、ファイルではないので、AIがGrepやReadで読めないことである。
GitHubの画面にも出ない。
1.0になっておらず、版によってコマンドの名前が変わる。
`git bug push`と`git bug pull`を忘れると、ほかのセッションから見えない。
そのため採らない。

### Alternative 4: git-issue

issueを`.issue/`の別のGitリポジトリに、普通のファイルとして持つツールである。
長所は、AIがファイルとして読めることである。
本体のブランチから切り離されているので、マージを待たずに書ける。
短所は、`.issue/`が本体のフォルダに1つだけあり、worktreeのセッションからは絶対パスで見に行く必要があることである。
別のPCとの共有には`git issue push`と`git issue pull`が要る。
画面はCLIだけで、スマホからは見られない。
そのため採らない。

### Alternative 5: ローカルの無視するファイル

`.gitignore`に入れた`docs/local.md`などに書く方法である。
長所は、手元のパスや個人のノートの中身を書いても、リポジトリに入らないことである。
短所は、PCごとに別のファイルになることである。
パーソナルな文書はPetaJournalに置くので、この置き場所は要らない。
そのため採らない。

## Confidence Level

確信度は高い。
GitHub Issuesは、作った時点でどのセッションからも見える。
PRとのつながりも、`Closes #N`で保てる。

次の場合は見直す。

- GitHubから離れることになったとき。
- オフラインで作業する場面が増えたとき。
- AIが`gh`でissueを読む手間が、作業の妨げになったとき。
  そのときは、Alternative 4のgit-issueを考え直す。

## Consequences

### 良い結果

- `docs/plans.md`が短くなり、今のPRのテストリストだけを読めばよくなる。
- 並行セッションが、作った時点でほかのセッションのissueを見られる。
- `docs/plans.md`のコンフリクトが減る。
  ブランチごとに、テストリストだけを書くためである。
- 調査の記録が、日付つきのコメントとして残る。
  issueを閉じたあとも、PRと結び付いたまま読める。
- 個人のノートの中身と手元のパスが、リポジトリに入らなくなる。

### 悪い結果

- AIがissueを読むには、`gh`を使う必要がある。
  GrepやReadでは読めない。
- 作業の一覧が、GitHubに依存する。
- 今の`docs/plans.md`の項目を、issueとPetaJournalに移す手間がかかる。

### 中立的な結果

- tddスキルとgeneric-coding-rulesスキルに、issueを使う流れを書き足す必要がある。
  全プロジェクトに共通する考え方はスキルに書き、このプロジェクトのラベルなどはこのADRに残す。
- ADRの実装の作業は、これまで`docs/plans.md`に書かなかった。
  これからは、ADRごとに1つのissueにする。
