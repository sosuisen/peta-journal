# ADR 047: Property Types Taken from Key Names

## Status

Accepted

## Context

ADR 046 で、ユーザー定義のキーの定義は、`settings/properties.json` で端末の間を同期するようになった。
同じキーの定義が端末ごとに違えば、日時の新しいほうが勝つ。
そのため、キーの型が途中で変わることがある。
型が変わっても DB の値は変えないので、新しい型に合わない値が残る（ADR 046 の例 3）。

Web 版は、値の文字列を型に合った入力欄に入れて見せる。
ブラウザがその文字列を型として読めないと、欄は黙って空になる。
`number` のキーの `many` は空の数の欄に、`checkbox` のキーの `yes` は印のないチェックボックスに見える。
DB には値が残っているのに、ユーザーには値がないように見え、上書きすれば値は黙って消える。

型に合わない値が端末の DB に入るのは、今は次のときである。

- 定義を消して、同じ名前を別の型で足し直したとき。
  ADR 046 はこれを認めている。
- 2 つの端末が互いを知らずに、同じキーを別の型で定義したとき。
- REST や MCP で定義のないキーに値を書いたとき。
  そのとき送った型で、本物の定義ができる（ADR 046 の PR 3c）。
  AI が日付を `text` として送れば、そのキーは `text` になる。
- REST や MCP で `date` や `datetime` のキーに書いたとき。
  ADR 046 は「型に合わない値は 400 で断る」としているが、サーバーが確かめているのは `number`、`checkbox`、`bounds` だけである。
- ページのファイルを手で書き換えたとき。

ユーザーが使っているうちにキーの型を変えたくなることは、まずない。
キーの型は、キーが何を表すかで決まるからである。
変えたくなるのは、名前のほうである。
型を変えたくなるのは、定義したときに型を間違えたときだけである。
そのときに型が間違うのは、上の REST や MCP の書き込みで、型を決めずに定義ができるからである。

キーを消すと、消した端末の DB からは、そのキーの値がすべて消える。
ほかの端末では、消したことが届いても値は残り、定義は仮の定義になる。
消したことを知らずに、その端末で書いた値かもしれないからである（ADR 046）。

## Decision

**プロパティの型は、キーの名前の接尾辞から決める。**
接尾辞と型の対応は、次の表のとおりとする。

| 接尾辞 | 型 |
|---|---|
| `_n` | `number` |
| `_d` | `date` |
| `_dt` | `datetime` |
| `_cb` | `checkbox` |
| `_list` | list（今のまま） |
| なし | `text` |

型は名前だけで決まるので、どの端末も通信せずに同じ型を出せる。
そのため、型の衝突は起きない。
消したキーを同じ名前で足し直しても、同じ型に戻る。
システムのキーは、今のとおり `SYSTEM_KEYS` の表で型を決める。

**接尾辞はユーザーに見せない。**
ユーザーが入力するのは名前の本体だけである。
接尾辞は、選ばれた型から自動で付く。
画面には本体だけを表示する。
接尾辞が見えるのは、`.md` ファイルの中だけである。

**名前の本体が予約の接尾辞で終わることは認めない。**
本体が `rating_n` のときに、完全な名前が `rating_n_n` になるのを防ぐためである。
予約の接尾辞は、`_n`、`_d`、`_dt`、`_cb`、`_list` である。
GUI と REST/MCP は、このような本体を拒む。
`.md` から読み込むときは、最後の接尾辞だけで型を決める。
接尾辞は小文字だけを認める。
`_N` は本体の一部として扱い、`text` になる。

**型を変えることは、別のプロパティにすることである。**
定義ファイルには型を書かない。
ページ用かどうかなど、型以外の情報だけを残す。
ADR 046 のマージは、型に関わらなくなる。

**`settings/properties.json` は、型以外の定義を同期するために残す。**
ファイルが伝えるのは、キーがあること、ページ用かどうか、キーを消したことの3つである。
キーは、接尾辞の付いた完全な名前で書く。
マージは ADR 046 のとおり、`modified` と `deleted` の新しいほうが勝つ。
仮の定義は、今のとおりファイルに書かない。

**REST/MCP は、定義のないキーへの値と、型に合わない値を 400 で拒む。**
型に合うかは、`date` と `datetime` も含めてサーバーが確かめる。
`.md` からの読み込みだけが、仮の定義を作る。

**`.md` に型に合わない値があれば、文字列のまま保ち、消さない。**
印を付けるかどうかは、あとで決める。

## Alternatives

### Alternative 1: 型は定義するときだけ決め、定義ファイルで同期する

型は定義ファイルに書き、ADR 046 のとおり新しいほうが勝つ形でマージする。
この形は、Obsidian の `types.json` と同じである。

- 長所: キーの名前に制約がない。
- 短所: オフラインの端末どうしが同じ名前を別の型で定義すると、負けた側の値が型に合わなくなる。消したキーを他の端末より先に足し直すと、古い型が戻ることがある。これを防ぐには、削除のときにユーザーへの注意が要る。
- 選ばなかった理由: 衝突をユーザーの注意で防ぐことになり、仕組みでは防げない。

### Alternative 2: 型を値に含める

DynamoDB の `{"N": "35"}` や RDF の `"12"^^xsd:integer` のように、値ごとに型を持たせる。

- 長所: スキーマが要らない。
- 短所: front matter に型の印が入り、読みにくくなる。同じキーがページごとに別の型を持てる。
- 選ばなかった理由: 同じキーがページごとに別の型を持て、型の衝突がなくならない。

### Alternative 3: 消した名前を型とともに予約する

Protocol Buffers の `reserved` のように、削除の墓標に型を残す。
同じ名前は、同じ型でだけ足し直せる。

- 長所: 型の衝突を防げる。
- 短所: 定義ファイルの形式が変わる。誤った型で作ったキーは、同じ名前で作り直せない。
- 選ばなかった理由: 名前から型を決めれば、同じ効果が墓標なしで得られる。

### Alternative 4: スキーマの版の間を変換する

Cambria のように、書き込みに版を付け、読むときに lens で変換する。

- 長所: 型を変えても、古い値を新しい型で読める。
- 短所: 実装が重い。スカラーから配列への変換では値が失われる。
- 選ばなかった理由: ユーザーは型を変えたいと思わないので、変換は要らない。

### Alternative 5: 型に合わない値に警告の印を付ける

型の衝突を許し、合わない値を画面で示す。

- 長所: 今の仕組みのまま足せる。
- 短所: 衝突は起き続け、ユーザーが直すことになる。
- 選ばなかった理由: 衝突の原因を除くほうがよい。

### Alternative 6: 長い接尾辞を使う

接尾辞を `_num` や `_date` にする。

- 長所: `.md` の中で型が読み取りやすい。
- 短所: ユーザーが本体に使いそうな語なので、予約語として禁じると困る場面がある。
- 選ばなかった理由: 接尾辞は画面に出さないので、短く、使われにくい語を選んだ。

## Confidence Level

この決定の確信度は高い。

Solr の dynamic fields と Elasticsearch の dynamic templates は、名前のパターンから型を決める方式を長く使ってきた。
このアプリの `_list` も、同じ規則で問題なく動いている。
また、型が名前だけで決まるので、どの端末も同じ型を出せる。
この点は、同期の方式にかかわらず成り立つ。

この決定は、`.md` を手で編集する場面は多くない、という仮定に立つ。
接尾辞が見えるのは `.md` の中だけなので、ユーザーはふだん接尾辞を意識しない。
この仮定は、ADR 048 に記録する。

確信が下がる点は、接尾辞を画面に出さない GUI を、どの端末でもまだ作っていないことである。

次のどれかが起きたら、この決定を見直す。

- ユーザーが、一度作ったプロパティの型を変えたくなる場面が、繰り返し出てきた。
- 予約の接尾辞を、ユーザーが名前の本体に使いたくなった。たとえば、`_d` で終わる語である。
- 型の種類が増え、短い接尾辞では区別しきれなくなった。
- `.md` を手で編集する場面が多いという前提に変わった。
- 他のアプリと `.md` を共有するようになり、接尾辞付きの名前が相手の側で困ることになった。

## Consequences

### 良い結果

- 型の衝突が起きなくなる。オフラインの端末どうしが同じ名前のキーを定義しても、型は同じになる。
- 消したキーを足し直しても、同じ名前なら同じ型に戻る。削除のときにユーザーへ注意を出す必要がない。
- 定義ファイルから型がなくなる。ADR 046 のマージは、型以外の情報だけを扱う。
- `.md` から仮の定義を作るときに、型を名前から決められる。今は `text` か list にしているが、`number`、`date`、`datetime`、`checkbox` も正しく仮の定義にできる。
- 今あるユーザーのキー（`lang`、`slug`、`test`）は、どれも `text` である。名前を変えずに、そのまま使える。

### 悪い結果

- すべての端末の GUI で、名前の本体と接尾辞を分けて扱う必要がある。入力では型から接尾辞を付け、表示では接尾辞を外す。Web、Emacs、iOS、Android のそれぞれに作業が要る。
- サーバーは、予約の接尾辞で終わる本体を拒み、`date` と `datetime` の値を確かめる必要がある。REST/MCP の書き込みで定義を作る `define_in` も外す。
- MCP からは、新しいキーを作れなくなる。AI が新しいキーを使うには、定義を作るツールを MCP に足す必要がある。足すかどうかは、別に決める。
- 定義ファイルの形式が変わる。今の版は、`type` のない項目を読み飛ばす。そのため、古い版の端末は、新しい版が書いた定義を知らないままになる。すべての端末を同じ時期に更新し、更新が終わるまでは定義を足したり消したりしない。移行の手順は、実装の PR で示す。

### 中立的な結果

- システムのキーは、接尾辞なしのまま `SYSTEM_KEYS` の表で型を決める。名前から型を決める規則には、この例外が1つ残る。
- 接尾辞は `.md` の中では見える。
- 型に合わない値の印は、この決定では付けない。
- `.md` を手で編集する場面は多くないという仮定を、ADR 048 に記録する。
