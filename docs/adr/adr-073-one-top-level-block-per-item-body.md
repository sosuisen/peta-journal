# ADR 073: One Top-Level Block per Item Body

## Status

Accepted

## Context

Flat Markdownは、Markdownのトップレベルのブロックごとに、ページを項目に分ける（flatmarkdownの`SPEC.md`の「ブロックによる項目の区切り」）。
1つのブロックが1つの項目になる。

一方で、journal-coreは、項目の本文が持つブロックの数を確かめずに保存する。
本文の保存（`item_service.rs`の`update_item_in`）が確かめるのは、閉じていないブロックがないことだけである（ADR 050）。
このため、シェルの編集画面で`# H1`、空行、`Para 1`と打つと、DBには1つの項目として入り、画面にも1つの項目として表示される。

journal-coreは、この項目をページのファイルに、メタデータ行と本文の順で書く（`flat_markdown_serializer.rs`）。

```markdown
<!-- @@ <id> idx="..." modified="..." -->
# H1

Para 1
```

journal-coreがこのファイルを読み戻すと、flatmarkdownの`parse_page`は2つの項目を返す（`import_service.rs`、`outline_parser.rs`）。
`# H1`は、元の項目のid、レベル、プロパティを持つ。
`Para 1`はメタデータ行を持たないので、`item_merger.rs`が新しいidを振る。
レベルは1になり、プロパティは付かない。
元の項目のレベルが2でも、`Para 1`はレベル1になる。
別の端末がこのファイルを取り込むと、その端末のDBで項目が増える。

ADR 070は、この問題のうち、本文の途中の空行を扱った。
シェルの本文の空行を、ファイルでは`\`だけの行として書く。
`\`だけの行は空行ではないので、段落の中の空行で項目が分かれなくなる。
しかし、空行がなくてもブロックの境目になる組み合わせがある。
flatmarkdownで確かめると、次の本文は`\`だけの行を入れても2つの項目に分かれる。

| ファイルの本文 | 読み戻した項目 |
|---|---|
| `a`、`\`、`b` | 1つ：`a`、`\`、`b` |
| `# H1`、`\`、`Para 1` | 2つ：`# H1`と、`\`、`Para 1` |
| `Para 1`、`\`、` ``` `、`code`、` ``` ` | 2つ：`Para 1`、`\`と、コードブロック |

見出しは1行で終わり、コードフェンスは段落を中断するためである。

貼り付けは、この規則に一部だけ従っている。
`paste.rs`の`plan`は、貼り付けた文を`FlatMarkdownSplitter`で断片（`Piece`）に分ける。
カーソルの前の本文を最初の断片の頭につなぎ、カーソルの後ろの本文を最後の断片の末尾につなぐ。
`item_service.rs`の`paste`は、最初の断片を元の項目に書き、2つ目以降の断片を新しい項目として下に作る。
しかし、つないだ後の断片は分けない。
たとえば、本文`# H1`と改行の後ろに`Para`を貼ると、断片は1つで、本文は`# H1\nPara`になる。
この本文は見出しと段落の2つのブロックを持つが、1つの項目として保存される。
本文を書くほかの経路は、この規則に従っていない。

journal-coreの`docs/adr/`にも、flatmarkdownのリポジトリにも、複数のブロックを持つ本文の扱いを決めた記録はない。

## Decision

### 1つの本文は、トップレベルのブロックを1つだけ持つ

項目の本文は、トップレベルのブロックを1つだけ持つものとする。
ブロックの数は、ADR 070の変換をした後の本文、つまりファイルに書く形の本文で数える。
段落の中の空行は`\`だけの行になるので、段落は1つのブロックのままである。
ADR 070の規則を、この規則より先に当てる。

### 2つ目以降のブロックを、新しい項目にする

本文が2つ以上のブロックを持つとき、journal-coreは本文を分ける。
最初のブロックは、元の項目の本文になる。
元の項目のid、レベル、プロパティは変わらない。
2つ目以降のブロックは、それぞれ新しい項目になる。
新しい項目は、元の項目と同じレベルで、元の項目のすぐ下に、ブロックの順で並ぶ。
新しい項目は、元の項目のプロパティを引き継がない。
これは`paste`が2つ目以降の断片を項目にするときと同じ形である。

GFMのタスクの接頭辞（`- [ ] `）は、最初のブロックの本文に付いたまま残る。
新しい項目は、本文が接頭辞で始まるときだけタスクになる。

本文を分けることと、項目を作ることは、1つのトランザクションで行う（ADR 004、ADR 011）。
本文の更新の応答は、元の項目と、新しく作ったすべての項目を返す。

### 分けるのはjournal-coreである

本文を分けるのは、journal-coreの本文を書く処理である。
シェルからの保存も、RESTとMCPからの更新も、同じ処理を通る（ADR 060）。
どの経路から入った本文も、同じ規則で分かれる。

本文を書くほかの経路も、同じ規則に従う。
対象は、分割（Enter）、結合、移動、拡張が書く項目である。
たとえば、`merge_item`は2つの本文を`format!("{}{}", ...)`でそのままつなぐ。
`# H1`と`Para\nmore`をつなぐと`# H1Para\nmore`になり、見出しと段落の2つのブロックになる。
この本文も、保存するときに2つの項目に分かれる。

### 貼り付けと共通の処理

本文を項目に分ける処理は、貼り付けとほかの経路で共通にする。
journal-coreに、次の2つの処理を置く。

1. 本文を断片に分ける処理。
   ファイルに書く形の本文を受け取り、flatmarkdownの関数で`Vec<Piece>`に分ける。
   今の`paste.rs`の`split_into_pieces`を元にする。
2. 断片を書く処理。
   最初の断片を元の項目に書き、2つ目以降の断片を、元の項目のレベルに`Piece`の`level`を足したレベルで、下に作る。
   今の`item_service.rs`の`paste`の中のループを取り出したものである。

本文の更新、分割、結合、移動、拡張は、本文をファイルに書く形にしてから、1と2を順に通す。
貼り付けは、貼り付けた文を1で断片に分け、カーソルの前後の本文をつなぐ。
つないだ後の各断片を、もう一度1に通してから、2で書く。
つないだ後の本文も、トップレベルのブロックを1つだけ持つようにするためである。

共通にするのは、ファイルに書く形の本文を項目に分けることである。
入ってくる文をファイルに書く形に直す仕方は、入口ごとに違う。

| 入口 | ファイルに書く形への直し方 |
|---|---|
| シェルで打った本文 | ADR 070の書く向きの変換。空行は`\`だけの行になり、項目を分けない |
| 貼り付けた平文（`PasteMode::Auto`、`PasteMode::Flat`） | そのまま。空行はブロックの境目になり、段落ごとに項目になる |
| 貼り付けたツリーのMarkdown（`PasteMode::Auto`） | `tree_markdown_to_flat_markdown` |
| そのまま貼り付けた文（`PasteMode::Raw`） | シェルで打った本文と同じく、ADR 070の書く向きの変換。空行は`\`だけの行になり、項目を分けない |
| RESTとMCPの本文 | そのまま。ADR 070のとおり、`\`だけの行を含む形で受け取る |

貼り付けた平文の空行で項目が分かれるのは、今の動作のままである。
ほかのアプリから複数の段落を貼ったとき、段落ごとに項目になる。
`PasteMode::Raw`は、貼り付けた文を項目に分けずに、そのまま本文に入れるためのものである。
そのため、`PasteMode::Raw`で貼った文は、シェルで打った文と同じに扱う。
貼った文の空行は、ADR 070のとおり`\`だけの行になり、段落ごとに項目が分かれることはない。
ただし、見出しやコードフェンスのように、空行がなくてもブロックの境目になるものは、ほかの経路と同じく1で分かれる。
閉じていないブロックの中に貼る`PasteMode::Auto`も、貼り付けた文を1つの断片のままつなぐ。
ブロックの中の空行はブロックの境目にならないので、ADR 070の変換の対象にもならない。
どちらの場合も、つないだ後の断片は、ほかの貼り付けと同じく1に通す。

### 判定と分割の関数は、flatmarkdownに置く

本文のブロックを数える関数と、本文をブロックごとに分ける関数を、flatmarkdownのクレートに置く。
分割は、`parse_page`がページを項目に分けるのと同じ読み方で行う。
ファイルを読み戻したときの分かれ方と、保存のときの分かれ方が必ず一致するためである。
ADR 070が変換の関数をflatmarkdownに置いたのと同じく、知識を1か所に置く。

### 自動保存は、編集を終えるまで待つ

client-coreは、シェルの本文が2つ以上のブロックを持つ間は、自動保存を送らない。
ブロックの数は、ADR 070の書く向きの変換をした後の本文で、flatmarkdownの関数を使って数える。
項目は保存待ちのまま残り、編集を終えるときに保存される。
保存したときにjournal-coreが本文を分け、client-coreは応答の項目を画面に表示する。
打っている途中で項目が分かれ、カーソルのある項目が変わるのを防ぐためである。
これはADR 050で、閉じていないブロックを持つ本文の自動保存を待たせるのと同じ扱いである。

### トランスクルージョン

トランスクルージョンに打った本文は、元の項目の本文として保存される。
分けてできた新しい項目は、元の項目のページで、元の項目のすぐ下に作る。
ADR 017で、トランスクルージョンへの貼り付けが元の項目のページに入るのと同じである。

### 既存の本文

すでにDBにある、2つ以上のブロックを持つ本文は移行しない。
ユーザーがその項目を次に編集して保存したときに分かれる。
ファイルを読み戻したときは、これまでどおり`parse_page`が分ける。

## Alternatives

### Alternative 1: 2つ以上のブロックを持つ本文の保存を断る

ADR 050と同じく、journal-coreが保存を断る。
- 長所：本文を書き換えないので、仕組みが単純である。
- 短所：ユーザーは見出しの下に段落を書けず、断られた理由も分かりにくい。結合も、多くの場合に断られる。
- 選ばなかった理由：Flat Markdownでは、別の項目にすれば書ける内容である。断るより、項目にした方が書く人の手間が少ない。

### Alternative 2: そのまま許す

複数のブロックを持つ本文をDBにそのまま保存し、読み戻したときに分かれることを受け入れる。
- 長所：コードを変えなくてよい。
- 短所：DBとファイルの項目が食い違う。分かれた項目は、新しいidとレベル1を持ち、プロパティを失う。別の端末で項目が増える。
- 選ばなかった理由：ファイルを正本とするADR 006の前提と合わない。

### Alternative 3: 自動保存のたびに分ける

client-coreが自動保存を待たせず、保存のたびにjournal-coreが分ける。
- 長所：本文がすぐにファイルと一致する。
- 短所：打っている途中で項目が分かれ、カーソルのある項目が変わる。空行を打っただけで分かれることもある。
- 選ばなかった理由：編集の途中の本文は、まだ書きかけである。

### Alternative 4: 空行も含めて、ブロックの境目で分ける

ADR 070の変換をせず、空行で区切った段落も別の項目にする。
- 長所：規則が1つになり、ADR 070の変換が要らない。
- 短所：本文の中で空行を使って区切りたいという意図を表せない。ADR 070のAlternative 2と同じ短所である。
- 選ばなかった理由：ADR 070の決定を優先する。

### Alternative 5: ファイルに書くときに、1つのブロックに包む

複数のブロックを持つ本文を、ファイルでは`>>>`の引用などに包み、1つのブロックにする。
- 長所：DBの項目は1つのまま、読み戻しても1つの項目になる。
- 短所：ほかのMarkdownビューアでは引用として表示される。本文の意味が変わる。
- 選ばなかった理由：ファイルを人が読める形に保つ（ADR 048）。

## Confidence Level

中程度である。
`parse_page`が見出しやコードフェンスの前後で項目を分けることは、flatmarkdownで確かめた。
`\`だけの行が段落を1つに保つことも、同じく確かめた。

次のことは、まだ確かめていない。
- 結合でできた本文が分かれるとき、ユーザーが予想しない形にならないか。
- ADR 070の変換とブロックの判定を、編集のたびに行う時間が、長い本文で体感できるほど長くならないか。

次の場合は見直す。
- 結合や分割で、ユーザーが意図しない分かれ方が多く起きた場合。
- 1つの項目に複数のブロックを持たせたいという要望が多い場合。
- ADR 070の決定が変わった場合。

## Consequences

### 良い結果

- DBの項目と、ファイルを読み戻した項目が一致する。
- 別の端末がファイルを取り込んでも、項目が増えない。分かれた項目が、idやレベルやプロパティを失わない。
- 編集画面で書いた本文、REST、MCP、貼り付けが、同じ規則で項目に分かれる。
- ブロックの判定と分割の規則が、flatmarkdownの1か所にまとまる。

### 悪い結果

- 編集を終えると、1つの項目に書いたつもりの本文が、複数の項目に分かれる。ユーザーは、見出しの下に段落を書くと別の項目になることを知る必要がある。
- 結合で、つないだ本文がまた分かれることがある。
- 本文の更新の応答が、1つの項目ではなく、項目のリストになる。client-coreと、RESTとMCPの利用者は、応答の形の変更に合わせる必要がある。
- client-coreは、自動保存のたびに本文を1回多く解析する。

### 中立的な結果

- flatmarkdownに新しいリリースが要る。`flatmarkdown`、`flatmarkdown-ast`、`flatmarkdown-ast2html`のバージョンを同じにそろえる（ADR 020）。
- ADR 070の実装が、この決定の前提になる。ADR 070の変換の関数がなければ、段落の中の空行でも項目が分かれる。
- `docs/features.md`の自動保存、編集の終わり、結合、REST、MCPの記述を更新する必要がある。
