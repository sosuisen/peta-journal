# ADR 016: 50MB Limit for Asset Uploads

## Status

Accepted

## Context

画像は、サーバーの`/api/assets/upload`へ送って保存する。axumは、リクエストの大きさを既定で2MBまでに制限する。2MBでは、大きなスクリーンショットが送れないおそれがある。

サーバーとシェルは、ファイル全体をメモリに読む。そのため、大きなファイルを受けるほど、メモリを多く使う。

Emacs版は、アップロードの答えを待つ間、キーを止める。待つのは最長3秒である。

## Decision

`/api/assets/upload`の上限を、いったん50MBにする。

上限は、リクエスト全体の大きさに掛かる。上限を超えたリクエストは断り、ファイルを保存しない。他のAPIの上限は、2MBのまま変えない。

50MBは、大きなスクリーンショットや写真が収まる値として選んだ。使ってみて決めた値ではないので、いったんの値である。

## Alternatives

### Alternative 1: 2MBのままにする

axumの既定の値を変えない。変更は要らない。しかし、大きなスクリーンショットが送れないおそれがある。そのため、選ばなかった。

### Alternative 2: 上限をなくす

どの大きさの画像も送れる。しかし、サーバーとシェルはファイル全体をメモリに読む。上限がないと、使うメモリにも上限がなくなる。そのため、選ばなかった。

## Confidence Level

確信度は中くらいである。50MBは、使ってみて決めた値ではない。

Emacsからの実測は、次のとおりである（2026-11-08、同じPCのサーバー、デバッグビルド）。

| 大きさ | 結果 | かかった時間 |
|---|---|---|
| 3MB | 挿入される | 0.09秒 |
| 20MB | 挿入される | 0.24秒 |
| 49MB | 挿入される | 0.41秒 |
| 51MB | `Upload failed: 400`と表示され、本文は変わらない | 0.40秒 |

次のときに見直す。

- 50MBを超える画像を扱いたくなったとき。上限を上げるだけでなく、メモリに読まずに保存する形を検討する。
- 別のPCのサーバーへ送るようになったとき。待ち方を見直す。

## Consequences

良い結果は次のとおりである。

- 50MBまでの画像を貼り付けられる。同じPCのサーバーなら、49MBでも0.41秒で終わる。
- 上限があるので、1回のアップロードで使うメモリは限られる。

悪い結果は次のとおりである。

- 50MBを超える画像は断られる。Emacs版は`Upload failed: 400`と表示し、本文を変えない。
- 別のPCのサーバーへ送ると、3秒を超えることがある。Emacs版では、その間に打った文字が消えることがある。

中立的な結果は次のとおりである。

- 他のAPIの上限は2MBのままである。
