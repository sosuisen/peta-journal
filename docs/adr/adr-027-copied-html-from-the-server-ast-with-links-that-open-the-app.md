# ADR 027: Copied HTML from the Server AST, with Links That Open the App

## Status

Accepted

## Context

項目をコピーすると、クリップボードには、Markdownと、それをHTMLにしたものの2つが入る。

コピーの流れは、次のとおりである。コアが、選んだ項目のIDをサーバーに送る（`POST /api/items/export`）。サーバーは、3つのものを返す。ツリーの形のMarkdown（`treeMarkdown`）、Flat Markdown（`flatMarkdown`）、そしてツリーの形のMarkdownを解析したAST（`ast`）である。コアは、この3つを`TreeExport`で受け取る。

コアは、そのうちMarkdownだけをシェルに渡す。`UiOp::CopyMarkdown { markdown }`である。ASTは、渡さずに捨てている。

Webのシェルは、受け取ったMarkdownを、自分でもう一度解析する。`flatmarkdown::parse_body`でASTにし、`ast_to_html`でHTMLにする。サーバーがすでに済ませた解析を、ブラウザの中で繰り返している。

Webのシェルが`flatmarkdown`クレートに依存する理由は、この1か所だけである。ADR 026で、項目の表示は、サーバーのASTを`ast_to_html`に通すだけになった。`flatmarkdown`はパーサーであり、`comrak`と絵文字の表を連れてくる。それらが、コピーのためだけにwasmに入っている。ADR 020は、ASTだけを持つ側に`comrak`と絵文字の表が入らないことを、利点に挙げた。Webのシェルは、その利点をまだ受けていない。

クリップボードのHTMLは、外のアプリに書式つきで貼り付けるためにある。ワープロ、メール、チャットなどである。これらは、HTMLがあるとそちらを使い、リストの入れ子、見出し、太字、表を保つ。PetaJournalの中での貼り付けには、HTMLを使わない。コアが、コピーのときにFlat Markdownを覚えておき、それを使う。

今のHTMLでは、PetaJournalの中へのリンクが、貼り付けた先で開けない。`[[Other Page]]`は`href="Other Page"`に、`[note](./note.md)`は`href="./note.md"`になる。どちらも、貼り付けた先では行き先がない。`#topic`は、ただの文字になる。

2回の解析は、同じ結果にならない。サーバーは、リンクの解決を有効にして解析する。`#tag`はハッシュタグのノードになり、`./x.md`や`../x.md`への相対リンクは、ウィキリンクのノードになる。Webのシェルは、オプションなしで解析する。そのASTでは、`./x.md`へのリンクが、外のサイトへのリンクと同じ種類のノードになる。PetaJournalの中へのリンクかどうかを、見分けられない。サーバーのASTでは、見分けられる。

ほかのシェルは、次のとおりである。SwiftUIのシェルは、`CopyMarkdown`のMarkdownを、ただのテキストとしてクリップボードに書く。HTMLは作らない。Emacsのシェルは、`CopyMarkdown`を使わない。

`UiOp`は、コアとシェルの境界を越える型である。SwiftUIのシェルでは、Swiftの型がRustの型から生成される（ADR 024）。`UiOp`の形を変えると、Swiftの側のコードも合わせて直す必要がある。

## Decision

コピーしたHTMLは、サーバーのASTから作る。PetaJournalの中へのリンクは、貼り付けた先から開けるURLにする。

**コア。** コピーのときにサーバーから受け取ったASTを、Markdownと一緒にシェルに渡す。`UiOp::CopyMarkdown`に、`ast`のフィールドを足す。

```rust
CopyMarkdown {
    markdown: String,
    ast: String,
}
```

`ast`は、サーバーが`treeMarkdown`を解析したASTである。`TreeExport`の`ast`を、そのまま入れる。形は、項目のASTと同じJSONの文字列である。コピーするMarkdownが空のときは、空の文字列である。

**サーバー。** 変えない。`POST /api/items/export`の応答は、すでに`ast`を持っている。

**Webのシェル（`shell-leptos`）。** `CopyMarkdown`を受けたら、`ast`を`flatmarkdown_ast`で読む。`flatmarkdown::parse_body`は呼ばない。HTMLにする前に、ASTの中のPetaJournalへのリンクを、ふつうのリンクのノードに置き換える。

- ウィキリンクは、`<アプリのURL>/pages/<ページ名>`へのリンクにする。表示する文字は、今と同じである。
- ハッシュタグは、`<アプリのURL>/pages/<タグ用ディレクトリ><タグ名>`へのリンクにする。表示する文字は、`#`とタグ名である。

アプリのURLは、ブラウザが今開いているページのオリジン（`http://localhost:8080`など）である。ページ名とタグ名は、URLとして正しく符号化する。空白や日本語を含む名前でも、貼り付けた先で1つのURLとして読まれるようにする。行き先は、項目の表示でリンクが指す先と同じである（ADR 026）。

置き換えたASTを`ast_to_html`に通し、HTMLにする。読めないASTからは、空のHTMLを作る。外のサイトへのリンク、画像、そのほかのノードは、変えない。項目の表示と違い、画像の大きさをURLに戻すことはしない。

置き換えは、ASTからASTへの関数として書く。ブラウザなしでテストできる。

`flatmarkdown`クレートは、通常の依存から外し、テスト用の依存（`dev-dependencies`）にする。

クリップボードのテキストの側は、変えない。今までどおり、ツリーの形のMarkdownである。

**SwiftUIのシェル（`frontend-swiftui`）。** 動きは変えない。今までどおり、Markdownをただのテキストとしてクリップボードに書く。変えるのは、型に合わせる1か所だけである。`Sources/PetaBorder/Shell.swift`の`handle`の中で、`.copyMarkdown`を受ける`case`が、フィールドを1つだけ取り出している。

```swift
case .copyText(let text), .copyMarkdown(let text):
```

`./generate.sh`で型を作り直すと、`.copyMarkdown`は`markdown`と`ast`の2つを持つ。この`case`を、`markdown`を取り出して`ast`を捨てる形に直す。`UiOp`の形を確かめるテストがSwiftの側にあれば、それも合わせる。

**Emacsのシェル（`shell-emacs`）。** 変えない。`CopyMarkdown`を、中身を見ずに無視している。

次のことは、このADRでは決めない。

- SwiftUIのシェルが、HTMLもクリップボードに書くこと。書くなら、アプリのURLに当たるものを、ネイティブのシェルでどう決めるかも要る
- ほかのマシンから開けるURLにすること。オリジンが`localhost`なら、リンクは同じマシンでしか開けない
- クリップボードのテキストの側のリンクを変えること
- `CopyMarkdown`から`markdown`を外すこと

## Alternatives

### Alternative 1: 今のまま、Webのシェルが解析する

コアは`markdown`だけを渡し、Webのシェルが`flatmarkdown`で解析する。

長所は、何も変えずに済むことである。`UiOp`の形が変わらないので、SwiftUIのシェルも直さなくてよい。

短所は、PetaJournalの中へのリンクを、開けるURLにできないことである。オプションなしの解析では、`./x.md`へのリンクが、外のサイトへのリンクと見分けられない。シェルがリンクの解決を有効にして解析すれば見分けられるが、サーバーと同じオプションを、シェルにも持たせることになる。同じ解析を2回することも、`comrak`と絵文字の表がwasmに入ることも、変わらない。

サーバーのASTを渡すだけで済むので、選ばなかった。

### Alternative 2: サーバーがHTMLも返す

サーバーが`ast_to_html`を呼び、`POST /api/items/export`の応答に`html`を足す。コアは、それをシェルに渡す。

長所は、シェルがASTを読まなくてよいことである。SwiftUIのシェルも、HTMLをそのまま使える。

短所は、変える場所が増えることである。サーバーに`flatmarkdown-ast2html`の依存を足し、REST APIとMCPの応答を変える。コアの`TreeExport`と`UiOp`も変える。応答には、同じ内容がMarkdown、AST、HTMLの3つの形で入る。HTMLが要るのは、今はWebのシェルだけである。そのシェルは、表示のために`ast_to_html`をすでに持っている。開けるURLを入れるには、サーバーが自分のURLを知る必要もある（Alternative 6）。

ASTがすでに届いているので、選ばなかった。

### Alternative 3: コアがHTMLを作る

コアが`ast_to_html`を呼び、`UiOp::CopyMarkdown`に`html`を入れる。

長所は、どのシェルも同じHTMLを受け取ることである。

短所は、コアに`flatmarkdown-ast2html`の依存が入ることである。ADR 025とADR 026は、HTMLを作る場所をシェルの側に置いた。コアがHTMLを作る案は、どちらのADRでも選ばなかった。コピーだけを別の扱いにする理由がない。HTMLを使わないEmacsとSwiftUIのシェルでも、コピーのたびにHTMLを作ることになる。コアは、アプリのURLも知らない。

ADR 025とADR 026にそろえるため、選ばなかった。

### Alternative 4: Webのシェルが、サーバーに直接ASTを求める

コアを変えず、Webのシェルが、コピーのときに自分でサーバーを呼ぶ。

長所は、`UiOp`の形が変わらないことである。

短所は、シェルがサーバーと直接話すことである。サーバーとのやり取りは、コアの求めに応じて行うという作りが崩れる。同じ項目について、コアとシェルが別々にサーバーを呼ぶ。

コアがすでにASTを持っているので、選ばなかった。

### Alternative 5: PetaJournalの中へのリンクを、文字にする

ウィキリンクとハッシュタグを、リンクでないただの文字としてHTMLに出す。

長所は、押しても開かないリンクが、貼り付けた先に残らないことである。オリジンを知る必要がなく、どのシェルでも同じHTMLになる。別のマシンに送った文書でも、困らない。

短所は、リンクの情報が消えることである。同じマシンで使う文書でも、もとのページへ戻れない。

貼り付けた先から開けることを選んだので、採らなかった。

### Alternative 6: サーバーが、開けるURLを入れたASTを返す

サーバーが、コピー用のASTを作るときに、リンクを絶対URLにしておく。

長所は、シェルが置き換えを持たなくてよいことである。

短所は、サーバーが自分のURLを知らないことである。サーバーは、ブラウザがどのアドレスで開いているかを知らない。`localhost`かもしれず、ほかの名前かもしれない。それを知っているのは、ブラウザの中のシェルである。タグ用ディレクトリを足す処理も、項目の表示のためにシェルがすでに持っている。

アプリのURLを知っているのがシェルなので、選ばなかった。

## Confidence Level

確信度は、中程度である。

確信が高いのは、ASTを渡すことである。サーバーはすでにASTを返しており、コアはすでにそれを受け取っている。足すのは、`UiOp`の1つのフィールドと、それを入れる1行である。サーバーのASTは、PetaJournalの中へのリンクを、ノードの種類で区別している。開けるURLにするにも、文字にするにも、この区別が要る。

確信が低いのは、開けるURLの使われ方である。心配は4つある。

- 開ける範囲。オリジンが`localhost`なら、リンクは同じマシンで、サーバーが動いているときにしか開けない。メールで人に送った文書では、相手の側で開けない。それでも文字にするより役に立つかは、使ってみないとわからない。
- 貼り付けた先での扱い。HTMLのリンクを、貼り付けた先のアプリがどう扱うかは、アプリごとに違う。`localhost`へのリンクを消すアプリや、警告を出すアプリがあるかもしれない。まだ試していない。
- 符号化。日本語や空白を含むページ名を、どの形で符号化すれば、貼り付けた先とPetaJournalの両方で正しく読まれるかは、作って確かめる。
- SwiftUIのシェルの変更。このADRを書いた環境では、Swiftをビルドできない。型を作り直したあとの`case`の書き方は、Macで確かめる必要がある。

wasmの大きさも、測っていない。`comrak`と絵文字の表が外れて小さくなる見込みである。

次のときに、この決定を見直す。

- 貼り付けた先で、開けないリンクが邪魔になったとき。見直す先は、文字にする形（Alternative 5）である。ASTを渡すことは変えない。
- ほかのマシンからPetaJournalを開けるようになったとき。アプリのURLを、ブラウザのオリジンではなく、設定で決めることを考える。
- `http`のURLではなく、PetaJournalのアプリのURLスキームが要るようになったとき。貼り付けた先のリンクから、ブラウザではなくネイティブのアプリ（SwiftUI、WinUI3）でページを開きたい場合である。そのときは、リンクの形を、アプリのURLスキームにするか、`http`のURLと使い分けるかを決める。置き換えの関数は、行き先の作り方だけを差し替えられる作りにしておく。
- SwiftUIのシェルやWinUI3のシェルも、HTMLをクリップボードに書くことになったとき。ネイティブのシェルには、ブラウザのオリジンがない。アプリのURLをどこで決めるか、置き換えをどこに置くかを、シェルをまたいで決め直す。
- サーバーの応答から`ast`を外すことになったとき。このADRは、応答に`ast`があることに頼っている。

この決定は、元に戻せる。`UiOp`からフィールドを外し、Webのシェルに`flatmarkdown`の依存を戻せばよい。

## Consequences

### 良い結果

コピーしたHTMLを外のアプリに貼ると、PetaJournalの中へのリンクが、そこから開ける。ウィキリンク、ハッシュタグ、`.md`への相対リンクのどれも、同じマシンのPetaJournalのページを開く。今は、どれも開けない。

コピーの解析が、1回になる。Webのシェルは、サーバーが作ったASTを使う。表示とコピーが、同じ解析の結果から作られる。

Webのシェルから、`flatmarkdown`の依存が外れる。`comrak`と絵文字の表が、wasmに入らなくなる。ADR 020が挙げた利点を、Webのシェルも受ける。パーサーを持つのは、サーバーだけになる。

リンクの置き換えは、ASTからASTへの関数である。ブラウザなしでテストできる。

サーバーを変えない。REST APIもMCPも、今のままである。

### 悪い結果

コピーしたHTMLが、今と変わる。ハッシュタグは、ただの文字からリンクになる。`./x.md`へのリンクは、行き先が変わる。ウィキリンクも、行き先が絶対URLになる。今のHTMLに頼っている使い方があれば、影響を受ける。

リンクは、開ける場所が限られる。オリジンが`localhost`なら、同じマシンで、サーバーが動いているときにしか開けない。人に送った文書では、相手の側で開けないリンクになる。

HTMLに、サーバーのアドレスとポートが入る。文書を人に渡すと、それも渡る。

`UiOp`の形が変わる。SwiftUIのシェルは、型を作り直し、`Shell.swift`の`case`を直す必要がある。直すまで、SwiftUIのシェルはビルドできない。

コピーのたびに、ASTが境界を1回多く越える。サーバーからコアへは、今も届いている。増えるのは、コアからシェルへの分である。SwiftUIのシェルとEmacsのシェルは、使わないASTを受け取る。

Webのシェルが、リンクの行き先を2か所で作る。項目の表示（ADR 026）と、コピーである。行き先の作り方は、1つの関数にまとめ、両方から使う。

### 中立的な結果

クリップボードのテキストの側は、変わらない。ツリーの形のMarkdownのままである。PetaJournalの中での貼り付けも、変わらない。

Webのシェルのテストは、`flatmarkdown`を使い続ける。MarkdownからASTを作るためである。依存は、テスト用に移る。

構成図（`docs/frontend-architecture.svg`）のshell-leptosから、`flatmarkdown`の札を外す。

SwiftUIのシェルがHTMLをクリップボードに書くこと、ほかのマシンから開けるURLにすること、アプリのURLスキームを使うことは、それぞれ別に決める。
