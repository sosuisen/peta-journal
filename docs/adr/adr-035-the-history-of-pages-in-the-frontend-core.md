# ADR 035: The History of Pages in the Frontend Core

## Status

Proposed

## Context

スマホのシェル（Android、iOS）の上端のバーに、戻るボタンと進むボタンを置くことにした（2026-11-13）。そのためには、開いたページの履歴が要る。

今のフロントエンドのコア（`peta-core`）は、履歴を持たない。コアは、開いてほしいURLをシェルに頼むだけである（`NavigateOp { url, replace }`）。シェルがURLを受けて、コアに画面を伝える（`Event::Route`）。履歴の持ち方は、シェルごとに違う。

- `shell-leptos`は、ブラウザーの履歴を使う。戻る、進む、置き換え（`replace`）、戻ったときのスクロールの位置、再読み込みのあとの履歴は、ブラウザーが受け持つ。
- `shell-emacs`は、Rustのシェルの中に、URLの配列を持つ。戻るだけがあり、進むはない。
- SwiftUI、WinUI、Android、iOSのシェルは、履歴を持たない。

履歴をシェルごとに書くと、同じ規則をSwift、C#、Kotlinに3回書くことになる。3つの言語に共通するものはRustに寄せる、という方針がある（`docs/plans.md`）。

ブラウザーの履歴は、History APIで制御できる。そのため、コアの履歴を正とし、ブラウザーの履歴をその写しにすることもできる。しかし、`shell-leptos`には、そうして得るものがほとんどない。ブラウザーがすでに全部を受け持っているためである。写しを保つ仕組み（`history.state`の番号、`popstate`での位置合わせ、再読み込みのあとの手当て）のコストのほうが大きい。

## Decision

開いたページの履歴を、`peta-core`に持たせる。

最初の版は、ページを戻ることと進むことだけにする。持つのは、URLの並び、今の位置、件数の上限である。操作は、積む、置き換える、戻る、進むの4つである。戻れるかと進めるかを、ビューモデルに出す。スクロールの位置とカーソルの位置は戻さない。履歴は保存しない。

履歴を使うかどうかは、シェルが決める。Android、iOS、SwiftUI、WinUI、Emacsのシェルは使う。Emacsのシェルの自前の履歴は、コアの履歴に置き換える。`shell-leptos`は使わず、今のままブラウザーの履歴を使う。`shell-leptos`は履歴に積まないので、コアの履歴は空のままである。

履歴は、Cargoのfeatureにしない。コアにそのまま置く。`shell-leptos`のwasmに入る分は、数KB以下の見込みである。

コアは、今は、開いたのか戻ったのかを区別できない。`Event::Route`が、どちらでも同じ形で届くためである。スマホの「Today」とリンクのタップは、コアを通らずに、シェルが直接URLを開く。履歴を使うシェルでは、開く操作がコアに分かるようにする。その形は、実装のときに決める。`shell-leptos`の受け渡しは変えない。

## Alternatives

### Alternative 1: シェルごとに履歴を持つ

Swift、C#、Kotlinのそれぞれに履歴を書く。コアは変わらない。同じ規則を3回書くことになり、動きがずれる。選ばなかった。

### Alternative 2: `shell-native`に持つ

4つのネイティブのシェルが共有するRustのクレートに置く。コアとシェルの約束は変わらない。`shell-leptos`には1バイトも入らない。しかし、Emacsのシェルは別のままになる。戻れるかどうかは、コアのビューモデルの外から取ることになる。コアのテストの道具（`Harness`）でも確かめられない。選ばなかった。

### Alternative 3: コアの履歴を正とし、ブラウザーの履歴をその写しにする

`shell-leptos`も、コアの履歴を使う。History APIでできる。全部のシェルが同じになる。しかし、`shell-leptos`のユーザーに見える違いは出ない。2つの履歴を合わせ続ける仕組みが要り、合わなくなったときの不具合は見つけにくい。選ばなかった。

### Alternative 4: Cargoのfeatureにする

履歴をfeatureに置き、`shell-leptos`のビルドから外す。featureそのものは不自然ではなく、コアにも`facet_typegen`がある。しかし、履歴はイベントとビューモデルの形を変える。featureの有無で型の形が変わるのは、コアで最初の例になる。featureはワークスペースの中でまとめて有効になるので、`cargo test --workspace`では無効の状態を確かめにくい。テストも2通り要る。100行前後のコードには、割に合わない。選ばなかった。

## Confidence Level

中くらいである。置き場所には自信がある。大きさの見積もり（100行前後、数KB以下）は、測っていない。

次のときに見直す。

- 履歴に、大きくなるものを足すとき。戻ったときのスクロールやカーソルの位置、履歴の保存、項目ごとの状態である。これらはブラウザーがすでに受け持つので、足すほど`shell-leptos`での無駄が増える。そのときは、ブラウザーのないシェルだけが使う別のクレートに置くことを、featureより先に考える。
- `shell-leptos`のwasmに入る分が、見積もりを大きく超えたとき。
- `shell-leptos`の画面の中に、戻るボタンと進むボタンを置くことになったとき。Alternative 3を考え直す。

## Consequences

- 戻ると進むの規則が、Rustの1か所になる。5つのシェルが同じ動きになる。Emacsのシェルに、進むが加わる。
- 置き換え（戻るで飛ばすページ）が、ブラウザーのないシェルでも効くようになる。
- 履歴を、画面なしに、コアのテストで確かめられる。
- 履歴を使うシェルでは、開く操作をコアに分かるようにする変更が要る。Swift、C#、Kotlin、Emacsの受け渡しに及ぶ。
- `shell-leptos`には、使わないコードが少し入る。
- `shell-leptos`とほかのシェルで、履歴の持ち主が違う。戻ったときのスクロールの位置は、ブラウザーでは戻り、ほかのシェルでは戻らない。
