# ADR 033: Sign-In to Dropbox with the Browser on Android

## Status

Accepted

## Context

Androidのアプリは、Dropboxの公式のSDK（`dropbox-android-sdk`）でサインインする（ADR 030）。SDKは、端末にDropboxのアプリがあれば、そのアプリに許可の画面を出させる。なければ、ブラウザーで`dropbox.com`の許可のページを開く。どちらを使うかは、SDKが決める。SDKには、ブラウザーを選ばせる設定がない。

2026-11-13に、実機で次のことが起きた。

- 最初のサインインは、Dropboxのアプリで通った。
- サインアウトしたあとにサインインすると、Dropboxのアプリの許可の画面が出る。「許可」を押すと、必ず「Dropboxに接続できませんでした。ネットワーク接続を確認してから、もう一度お試しください。」と出る。ネットワークには問題がない。
- その画面で「別のアカウントでログイン」を選び、Webのフォームからサインインすると、`dropbox.com`の許可のページが出る。そこで許可すると、通る。

これとは別に、Dropboxのアプリ自体がサインアウトしているときも、同じ文言で失敗することが分かっていた。

原因は分かっていない。SDKのコードを読んだが、失敗の理由は見つからなかった。Dropboxのアプリの中で起きており、こちらからは見えない。アプリは、サインアウトのときにトークンを取り消す（`tokenRevoke`）。これが関係している疑いはあるが、確かめていない。

Android 11以降では、アプリは、マニフェストの`queries`で頼んだアプリしか見えない。SDKは、自分のマニフェストで`com.dropbox.android`を頼んでいる。SDKは、Dropboxのアプリが見えないときに、ブラウザーへ進む。

## Decision

Dropboxへのサインインは、いつもブラウザーで行う。Dropboxのアプリが端末にあっても、使わない。

そのために、アプリのマニフェストで、SDKが足す`queries`の`com.dropbox.android`を消す（`tools:node="remove"`）。アプリのマニフェストにあった同じ記述も消す。こうすると、Android 11以降では、アプリからDropboxのアプリが見えない。SDKは、Dropboxのアプリがないものとして、ブラウザーで許可のページを開く。

SDKは、そのまま使う。サインインの流れ（PKCE）、トークンの保存、サインアウトのときのトークンの取り消しは、変えない。

原因は調べ続けない。ブラウザーでのサインインが実機で通ることを、開発者が2026-11-13に確かめた。失敗はDropboxのアプリの中で起きており、こちらで直せる見込みが小さい。

## Alternatives

### Alternative 1: Dropboxのアプリでのサインインを残し、原因を調べる

Dropboxのアプリが使えれば、利用者はDropboxへのサインインをやり直さずに、1回の「許可」でサインインできる。

短所は、原因がDropboxのアプリの中にあり、こちらから見えないことである。調べても、直せないかもしれない。その間、サインアウトのあとのサインインは失敗し続ける。回り道（「別のアカウントでログイン」）は、利用者には見つけにくい。選ばなかった。

### Alternative 2: サインアウトで、トークンを取り消さない

トークンの取り消しが原因なら、取り消しをやめれば直る。端末からは、今までどおり認証情報を消す。

短所は2つある。1つは、原因だと確かめていないことである。もう1つは、消したはずのトークンが、Dropboxの側で有効なまま残ることである。Dropboxのアプリがサインアウトしているときの失敗も、これでは直らない。選ばなかった。

### Alternative 3: SDKのサインインを使わず、OAuthを自分で書く

ブラウザー（Custom Tabs）を開き、戻ってきたコードをトークンに換える処理を、アプリに持つ。どのブラウザーを、どう開くかを、アプリが決められる。Android 10以前でも、同じ流れになる。

短所は、認証のコードを自分で持つことである。PKCEの検証、状態の照合、戻り先の扱いを誤ると、安全でなくなる。SDKの更新にも、自分で追従する。マニフェストの1か所で済むことに対して、変更が大きすぎる。選ばなかった。

### Alternative 4: 失敗したときだけ、ブラウザーに切り替える

最初はDropboxのアプリで試し、失敗したらブラウザーでやり直す。

短所は、失敗をアプリが知る方法がないことである。エラーはDropboxのアプリの画面に出て、こちらには結果が返らない。SDKにも、サインインの途中で経路を変える方法がない。選べなかった。

## Confidence Level

確信度は中程度である。

ブラウザーでのサインインが通ることには、確信がある。失敗が起きていた実機で、開発者が確かめた。SDKが前から持つ、Dropboxのアプリがない端末のための経路でもある。

確信が下がる理由は2つある。

- 原因が分かっていない。Dropboxのアプリでの失敗が、このアプリの使い方のせいなのか、Dropboxの側の不具合なのかを、切り分けていない。
- この方法は、SDKの中の動き（Dropboxのアプリが見えなければブラウザーへ進む）に頼っている。SDKの決まりとして書かれたものではない。SDKが変われば、効かなくなるかもしれない。

次のどれかが起きたら、この決定を見直す。

- SDKを更新したあとに、サインインでDropboxのアプリがまた開く。または、ブラウザーでのサインインが通らなくなる。
- SDKに、ブラウザーを選ぶ設定が入る。そのときは、マニフェストの細工をやめて、その設定を使う。
- Dropboxのアプリでの失敗が直ったと分かる。そのときは、Dropboxのアプリでのサインインに戻すかを考える。
- ブラウザーでのサインインが面倒だという声が出る。たとえば、パスキーを使えない端末で、毎回パスワードを求められる場合である。
- Android 10以前の端末で使うことになる。この方法は、そこでは効かない。

## Consequences

良い結果は、次のとおりである。

- サインアウトのあとのサインインが通る。回り道を探す必要がない。
- Dropboxのアプリがサインアウトしているときの失敗も、起きなくなる。Dropboxのアプリの状態に、サインインが左右されない。
- Dropboxのアプリがある端末でもない端末でも、サインインの流れが同じになる。説明と確かめが、1通りで済む。
- 変更は、マニフェストの1か所である。SDKの使い方も、コードも、変わらない。

悪い結果は、次のとおりである。

- ブラウザーがDropboxにサインインしていなければ、ブラウザーでDropboxにサインインすることになる。Dropboxのアプリを通すより、手順が1つ増える。ただし、今のDropboxのサインインは、メールアドレスとパスワードではなく、端末のパスキーで行える。指紋認証などで済むので、手間は小さい。
- この方法は、SDKの中の動きに頼っている。SDKを更新するたびに、サインインがブラウザーで通ることを、実機で確かめる必要がある。
- Android 10以前では効かない。アプリが、ほかのアプリをいつも見えるためである。そこでは、Dropboxのアプリが開き、同じ失敗が起きうる。
- 原因は分からないままである。同じ失敗が、別の形でまた出るかもしれない。

中立的な結果は、次のとおりである。

- サインアウトは、今までどおりトークンを取り消す。
- ADR 030の「Dropboxのアプリがあれば、それでサインインする」という前提は、このADRで置き換わる。
- この確かめは、自動のテストにできない。エミュレーターにはDropboxのアプリがなく、サインインには本物のアカウントが要る。
