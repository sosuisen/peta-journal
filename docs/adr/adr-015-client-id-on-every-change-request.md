# ADR 015: Client ID on Every Change Request

## Status

Proposed

## Context

サーバーは、ページが変わるたびに`pagesUpdated`イベントをすべてのクライアントへ送る。APIでの変更には`source: "app"`が付く。

コアは、`source: "app"`のイベントではページを読み直さない。自分の変更の知らせで読み直すと、入力中の内容を古い内容で上書きするおそれがあるためである。

しかし、イベントには変更したクライアントを示す情報がない。そのため、ほかのクライアントの変更も自分の変更と区別できず、同じように無視される。Web版で変えたページをEmacs版で開いていても、開き直すまで古いままである。

クライアントは増えている。Web版（`shell-leptos`）、Emacs版（`shell-emacs`）、`ext-web-app/todo`、`ext-desktop-app/stickies`があり、WinUI3とSwiftUIのシェルも予定している。

## Decision

変更を送るクライアントは、自分のIDを`X-Client-Id`ヘッダーで必ず名乗る。サーバーはこれを強制する。

**クライアントのID**

クライアントは、起動のたびに新しいUUID（バージョン4）を作り、自分のIDにする。ブラウザのタブ1つ、シェルのプロセス1つが、それぞれ1つのクライアントである。IDは保存しない。ヘッダーには、ハイフン付きの36文字の形で書く。

**サーバーの強制**

サーバーは、`/api/`の下へのPOST、PUT、DELETEのリクエストに、このヘッダーを求める。ヘッダーがないリクエストと、値がUUIDとして読めないリクエストは、400 Bad Requestで断る。応答のメッセージには、`X-Client-Id`ヘッダーが必要であることを書く。サーバーは形だけを確かめ、UUIDのバージョンは確かめない。

データを変えないPOST（`/api/items/parse`など）にも、同じように求める。規則を「メソッドで決まる」の1つにするためである。

例外は2つある。GETのリクエストには求めない。`/api/sync/pending-deletes`へのPOSTにも求めない。これはサーバーが出すHTMLのフォームからの送信で、ブラウザはヘッダーを足せないためである。`/mcp`は`/api/`の下ではないので、対象外である。

**イベント**

サーバーは、`source: "app"`の`pagesUpdated`イベントに、変更したクライアントのIDを`clientId`として載せる。ほかの`source`のイベントには載せない。

**コア**

シェルは、起動時に自分のIDをコアに渡す。コアは、`source: "app"`のイベントの`clientId`が自分のIDと違うときに、表示中のページを読み直す。同じときは、今までどおり読み直さない。読み直しは、ファイルの変更のときと同じ処理を使う。編集中は待ち、編集が終わってから読み直す。

**ほかのオリジン**

サーバーのCORSの設定で、`X-Client-Id`ヘッダーを許す。

## Alternatives

### Alternative 1: 規約として必須にし、サーバーは断らない

ADRに「クライアントは必ずIDを送る」と書くだけにする。IDのない変更は、すべてのクライアントが読み直す。既存のクライアントは壊れない。しかし、IDを送り忘れたクライアントは、自分の変更の知らせで自分のページを読み直す。この不具合は、入力中の内容が時々古くなる形で静かに起きるので、見つけにくい。400で断れば、送り忘れは最初のリクエストで見つかる。そのため、選ばなかった。

### Alternative 2: HMTIDをIDにする

項目のIDと同じ形式を使う。コアは`hmtid::Generator`をすでに持つので、コアが自分でIDを作れる。しかし、乱数の部分は35ビットで、UUIDより弱い。Rust以外のクライアントは、HMTIDを作る実装が要る。C#やSwiftには、その実装がない。UUIDは、どのプラットフォームでも標準の関数で作れる。そのため、選ばなかった。

### Alternative 3: サーバーがIDを配る

SSEの`connected`イベントで、サーバーがIDを渡す。重ならないことをサーバーが保証できる。しかし、SSEをつなぐまで変更を送れない。再接続でIDが変わると、送信中の自分の変更を、ほかのクライアントのものと見誤る。SSEを使わないクライアントには、別の入手方法が要る。そのため、選ばなかった。

### Alternative 4: 手動のリロードだけを足す

Emacs版に、ページを読み直すコマンドを足す。変更は最も小さい。しかし、利用者が古い表示に気づいて操作する必要がある。気づかずに古い表示の上で編集すると、ほかのクライアントの変更を上書きする。そのため、選ばなかった。

## Confidence Level

確信度は高い。IDをヘッダーで名乗り、イベントで送り返す形は単純で、判定は文字列の比較だけである。

次のときに見直す。

- ヘッダーを足せないクライアントが、`/api/sync/pending-deletes`のほかにも必要になったとき。例外が増えるなら、規則そのものを考え直す。
- ほかのクライアントの変更のたびにページ全体を読み直すことが、遅さとして見えたとき。変わった項目だけを送る形を検討する。
- 認証を入れるとき。クライアントのIDは誰でも名乗れる値で、身元の証明には使えない。

## Consequences

良い結果は次のとおりである。

- ほかのクライアントがAPIで変えたページが、開き直さなくても新しくなる。
- IDを送り忘れたクライアントは、最初の変更で400を受け、メッセージから原因が分かる。
- コアは、「IDのない`app`のイベント」という場合を扱わなくてよい。

悪い結果は次のとおりである。

- これは互換性のない変更である。IDを送らない既存のクライアントは、変更をすべて断られる。`ext-web-app/todo`、`ext-desktop-app/stickies`、ベンチ、テストは、このADRと同じ変更の中で直す。リポジトリの外でAPIを使うスクリプトがあれば、それも直す必要がある。
- `curl`でAPIを試すときも、ヘッダーが要る。
- ほかのクライアントが入力を続けている間、開いているクライアントは、保存のたびにページを読み直す。

中立的な結果は次のとおりである。

- MCPからの変更は、今は`pagesUpdated`イベントを送らない。そのため、MCPで変えたページは、このADRのあとも自動では読み直されない。これは別の課題である。
- 編集中のクライアントは、編集が終わるまで読み直しを待つ。2つのクライアントが同じ項目を同時に編集すると、後から保存したほうが残る。これは今までと変わらない。
