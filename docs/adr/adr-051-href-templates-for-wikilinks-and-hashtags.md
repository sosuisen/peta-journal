# ADR 051: Href Templates for Wikilinks and Hashtags in flatmarkdown-ast2html

## Status

Accepted

## Context

`flatmarkdown-ast2html`の`ast_to_html`は、ASTだけを受け取り、出力を変える手段を持たない。wikilinkは`<a href="<ページ名>" data-wikilink="true">`、hashtagは`<a href="<タグ名>" class="hashtag">`になる。`href`には、ページ名やタグ名だけが入る。

ADR 026は、Webのシェルがこの出力から項目を描くと決めた。そのとき、`ast_to_html`は変えず、オプションも足さないことにした。足りないことはWebのシェルが補う。その1つがリンクの`href`である。描画のあと、`item_view.rs`の`point_links`が、DOMの`href`に`/pages/`とタグ用ディレクトリを付ける。ADR 026は、`ast_to_html`にリンクのオプションを足すかどうかを、先送りにした。

この補い方には、無理がある。タグ用ディレクトリは、設定で変えられる。変わると、書き換えがもう一度走る。そのときの`href`には、もう接頭辞が付いている。二重に付けないために、元の名前を`data-page`という属性に取っておいている。この属性は、後から書き換えるという方法のためだけにある。flatmarkdown側を変えずにこの属性を消す方法は、ない。HTMLの文字列は設定で変わらないので、leptosはDOMを入れ直さない。描画の前にASTを書き換えると、表示の文字か`class="hashtag"`の目印が変わってしまう。

同じ問題は、PetaJournalの外にもある。sosuisen.netは、`fm2html`で記事をHTMLにする。hashtagを`/tags/<タグ>`のページへつなぐため、描画したHTMLの文字列を書き換えている。

一方、hrefをそのままの名前で使うアプリもある。memoviewは、wasm版の`renderToHtml`で描く。クリックを横取りし、`href`をタグ名やページ名として読み、C#側に渡す。C#側は、クリックのたびにサーバーからタグ用ディレクトリを聞き、URLを組み立てる。「HTMLとしてコピー」（ADR 027）は、描画の前にASTのリンクを普通の`Link`に置き換え、URLをパーセント符号化する。どちらも、今の出力のままで困っていない。

## Decision

`flatmarkdown-ast2html`に、wikilinkとhashtagの`href`をテンプレートで決める設定を足す。設定は`HtmlOptions`という構造体で、`wikilink_href`と`hashtag_href`の2つの文字列を持つ。テンプレートの中の`{}`は、すべて置き換える。wikilinkならノードの`url`、hashtagならタグ名が入る。たとえば`/pages/tags/{}`は、`<a href="/pages/tags/Rust" class="hashtag">#Rust</a>`になる。テンプレートの後ろにも文字を置けるので、`/tags/{}.html`のような形も作れる。

設定を受け取る関数として、`ast_to_html_with(node, options)`を足す。`ast_to_html`は残し、既定の設定で`ast_to_html_with`を呼ぶ。既定のテンプレートは、どちらも`{}`である。既定の設定では、今と同じHTMLになる。そのため、既存の呼び出しは変えなくてよい。

`href`は、テンプレートに名前を入れたあとで、まとめてHTMLのエスケープをかける。表示の文字（`#Rust`やwikilinkの中身）と、目印の`data-wikilink`と`class="hashtag"`は変えない。

テンプレートに入れる名前は、パーセント符号化する（2026-11-18に改めた。下の「名前の符号化」）。最初の決定では、符号化しなかった。

wasm版（npmの`flatmarkdown-ast2html`）にも、同じ設定を足す（2026-11-18に改めた）。`renderToHtml`が、2つ目の引数で`wikilinkHref`と`hashtagHref`を受ける。引数を省くと、既定の設定になる。最初の決定では、足さなかった。wasm版を使うmemoviewが、`href`を名前として読んでいたためである。ADR 061で、memoviewも`href`をURLとして開く形に変えると決めた。同じ設定を渡せば、Rust版とwasm版は同じHTMLを出す（ADR 023）。

`HtmlOptions`に、3つ目の設定を足す（2026-11-18に改めた。下の「名前に`#`を含むページ」）。wikilinkの`url`のうち、ページの中の場所を指す部分の形を、正規表現の文字列で受ける。

3つのクレートは、そろって`0.9.0`に上げる（ADR 020）。符号化、wasm版の設定、3つ目の設定も、`0.9.0`に入れる。`0.9.0`は、2026-11-18の時点でまだ公開していない。そのため、符号化しない版と、`#`を符号化しない版は、公開されない。

### 名前の符号化

2026-11-18に、開発者が決めた。

テンプレートの`{}`に入れる名前を、パーセント符号化する。符号化するのは名前だけで、テンプレートの文字は変えない。順序は、名前の符号化、`{}`の置き換え、HTMLのエスケープである。

理由は、`%`や`?`を含むページ名のリンクが壊れるためである。たとえば`[[What?]]`は`/pages/What?`になり、ブラウザーは`What`というページを開こうとする。ADR 061で、サーバーが返す`url`も同じ関数で作ると決めた。そのため、符号化の規則は、テンプレートに名前を入れる関数の1か所に置く。

符号化する文字は、JavaScriptの`encodeURI`が符号化する文字と、`?`と`#`である。次の文字は、そのまま残す。

- 英字と数字
- `-` `_` `.` `!` `~` `*` `'` `(` `)`
- `;` `/` `:` `@` `&` `=` `+` `$` `,`

ほかの文字は、UTF-8のバイトごとに`%XX`にする。16進の英字は大文字である。空白、`%`、`?`、`#`、`"`、`<`、`>`、`[`、`]`、`\`、`^`、`` ` ``、`{`、`|`、`}`、制御文字、日本語などのASCIIでない文字が、これに当たる。

| 名前 | テンプレート`/pages/{}`の結果 |
|---|---|
| `Projects/Foo` | `/pages/Projects/Foo` |
| `What?` | `/pages/What%3F` |
| `100%` | `/pages/100%25` |
| `Other Page` | `/pages/Other%20Page` |
| `日記` | `/pages/%E6%97%A5%E8%A8%98` |
| `C#` | `/pages/C%23` |
| `a%20b` | `/pages/a%2520b` |

- `/`を残すのは、ページ名の中のフォルダーの区切りだからである。
- `#`を符号化するのは、名前に`#`を含むページへリンクするためである（2026-11-18に改めた）。最初は`#`を残し、名前に`#`を含むページへはリンクできないとしていた。`C#`のような名前はふつうにあるので、開発者が改めた。`[[Page#item]]`のようにページの中の項目を指す`#`は、名前の一部ではないので、符号化の前に分ける（下の「名前に`#`を含むページ」）。
- `%`を符号化するので、すでに`%20`のような文字を含む名前も、そのままの名前として扱われる。符号化したURLを1回だけ復号すると、元の名前に戻る。
- TypeScriptでは、`encodeURI`の結果の`?`と`#`を、`%3F`と`%23`に置き換える。「HTMLとしてコピー」（ADR 027）が今使っている規則とも、`?`と`#`のほかは同じである。

URLを読む側は、最初の`#`でURLを分け、前のパスと後ろを、それぞれ1回だけ復号する。名前の中の`#`は`%23`になっているので、URLに残る`#`は、ページの中の場所を指す1つだけである。読む関数は、ADR 061の`page-urls`が持つ。

### 名前に`#`を含むページ

2026-11-18に、開発者が決めた。

wikilinkの`url`の中の`#`には、2つの意味がありうる。
1つ目は、ページ名の一部である。`[[C#]]`や`[[C#入門]]`がこれに当たる。
2つ目は、ページ名と、ページの中の場所を分ける区切りである。PetaJournalの`[[Page#20260426035700_QZ998PX]]`がこれに当たり、後ろは項目のidである。
ここでは、区切りの`#`の後ろの文字を「フラグメント」と呼ぶ。

flatmarkdownは、2つの意味を、フラグメントの形で見分ける。
形は、アプリが正規表現の文字列で渡す。
flatmarkdownは、PetaJournalの項目のid（HMTID）の形を知らない。

`HtmlOptions`に、3つ目の設定を足す。
ここでは仮に`wikilink_fragment_pattern`と呼ぶ。名前は、flatmarkdownの側で決める。
wasm版の`renderToHtml`と`flatmarkdown-ast2react`も、同じ設定を受ける（仮に`wikilinkFragmentPattern`）。
既定では、この設定は空である。

wikilinkの`url`は、次の手順で、名前とフラグメントに分ける。

1. `url`の中の最後の`#`を探す。なければ、`url`の全体が名前である。
2. 設定が空なら、`url`の全体が名前である。
3. 最後の`#`の後ろの文字の全体が、設定の正規表現に一致すれば、`#`の前が名前で、後ろがフラグメントである。
4. 一致しなければ、`url`の全体が名前である。

`href`は、テンプレートに名前を入れた結果である。
フラグメントがあれば、その後ろに`#`と、符号化したフラグメントを付ける。
名前とフラグメントは、「名前の符号化」の規則で、別々に符号化する。

テンプレートが`/pages/{}`で、設定がHMTIDの形のとき、結果は次のとおりである。

| wikilink | 名前 | フラグメント | `href` |
|---|---|---|---|
| `[[C#]]` | `C#` | なし | `/pages/C%23` |
| `[[C#入門]]` | `C#入門` | なし | `/pages/C%23%E5%85%A5%E9%96%80` |
| `[[Page#20260426035700_QZ998PX]]` | `Page` | `20260426035700_QZ998PX` | `/pages/Page#20260426035700_QZ998PX` |
| `[[C##20260426035700_QZ998PX]]` | `C#` | `20260426035700_QZ998PX` | `/pages/C%23#20260426035700_QZ998PX` |
| `[[Page#item]]` | `Page#item` | なし | `/pages/Page%23item` |

設定が空のときは、どの`#`も名前の一部である。
`[[Page#20260426035700_QZ998PX]]`の`href`は、`/pages/Page%2320260426035700_QZ998PX`になる。
ページの中の場所を指すリンクを持たないサイトは、何も渡さずに、名前に`#`を含むページへリンクできる。

フラグメントは、テンプレートに名前を入れたあとで付ける。
そのため、`/tags/{}.html`のように後ろに文字を置くテンプレートでも、フラグメントはURLの最後に来る。

正規表現は、Rustの`regex`クレートと、JavaScriptの`RegExp`の両方が、同じ意味に読む書き方だけを使う。
後方参照と先読みは使わない。
一致は、フラグメントの全体で見る。部分の一致では、フラグメントとしない。
正規表現として読めない文字列を渡されたときの動きは、flatmarkdownの側で決める。

設定を関数ではなく文字列にするのは、Alternative 3と同じ理由である。
関数はJSONで渡せず、wasm版と`ast2react`に同じ設定を足せない。

flatmarkdownは、`url`を名前とフラグメントに分ける関数を公開する。
ここでは仮に`split_wikilink`と呼ぶ。
ADR 061の`page-urls`と、journal-coreがファイルに書くリンク（`page_link_converter.rs`）は、この関数を通る。
分ける規則を、flatmarkdownの1か所に置くためである。

表示の文字と、目印の`data-wikilink`は変えない。
ASTの`Wikilink`ノードの`url`も変えない。`url`には、今までどおり`C##20260426035700_QZ998PX`のような元の文字が入る。
hashtagの名前には`#`が入らないので、hashtagの`href`は変わらない。

Rust版とTypeScript版をそろえる表（JSON）には、設定の列を足し、上の表の行を入れる。

Rustの`ast2html`、wasm版、TypeScriptの`flatmarkdown-ast2react`は、同じ規則で符号化する。`ast2react`は、Rustの関数を呼べないので、同じ規則をTypeScriptで持つ。2つの規則は、同じ表でそろえる。名前、テンプレート、結果を並べた表（JSON）をflatmarkdownのリポジトリに置き、Rustのテストが読む。`ast2react`のリポジトリには、その写しを置き、`ast2react`のテストが読む。規則を変えるときは、表を先に変える。`ast2react`がwasm版の関数を呼ぶ方法は、採らなかった。wasmの読み込みが非同期で、`ast2react`の描画とtodoの起動が変わるためである。

Webのシェルは、`item_html`で`ast_to_html_with`を使う。wikilinkには`/pages/{}`、hashtagには`/pages/<タグ用ディレクトリ>{}`を渡す。タグ用ディレクトリが変わったら、HTMLを作り直す。描画のあとに`href`を書き換える`point_links`と、`data-page`の属性は消す。ADR 026が決めた補い方のうち、リンクの`href`の項目は、この決定で置き換える。画像の大きさとコードブロックの色付けは、ADR 026のまま残す。クリックの横取りは変えない。目印で選び、`href`をURLとして開くので、今のまま動く。

「HTMLとしてコピー」（ADR 027）は、変えない。コピーは、アプリのオリジンを付けた完全なURLを作る。テンプレートに置き換えるかは、ADR 061のとおり、あとで決める。memoviewは、ADR 061で、wasm版の設定を使う形に変える。

## Alternatives

### Alternative 1: 今のまま、アプリが後から`href`を書き換える

`ast_to_html`は変えない。Webのシェルは`point_links`と`data-page`を、sosuisen.netはHTMLの文字列の書き換えを続ける。

- 長所: flatmarkdownの公開APIが増えない。どのアプリも変えなくてよい。
- 短所: 後から書き換えるための工夫が、アプリごとに残る。Webのシェルの`data-page`は、この方法のためだけにある。

ADR 026が先送りした問題が、2つのアプリで同じ形で現れた。そのため、選ばなかった。

### Alternative 2: 接頭辞だけを設定する

テンプレートではなく、名前の前に付ける文字列だけを渡す。`/pages/tags/`を渡すと、`/pages/tags/Rust`になる。

- 長所: `{}`の決まりが要らず、より単純である。
- 短所: 名前の後ろに文字を付けられない。`/tags/Rust.html`や`/search?tag=Rust&lang=ja`は作れない。

今のPetaJournalとsosuisen.netは接頭辞で足りる。それでも、後ろに文字が要るサイトはよくある。そのため、`{}`の決まりが1つ増えるだけのテンプレートを選んだ。

### Alternative 3: 名前からURLを作る関数を渡す

`Fn(&str) -> String`を設定として渡す。

- 長所: パーセント符号化も含め、どんなURLでも作れる。
- 短所: 関数はJSONで渡せず、wasm版に同じ設定を足せない。Rust版とwasm版で、できることが違ってしまう（ADR 023）。

符号化の規則は、関数を渡さなくても、ライブラリの中に1つ置けば足りる（「名前の符号化」）。そのため、選ばなかった。

### Alternative 4: 名前を`data-`の属性に出す

`href`はそのままにして、`data-tag="Rust"`のように名前を別の属性にも出す。

- 長所: memoviewのように名前を読むアプリでは、`href`を名前として読む約束が要らなくなる。
- 短所: `href`は今のままなので、Ctrl+クリックや中クリックでは、行き先がずれたままである。Webのシェルの書き換えは消えない。

`href`を正しくするという目的に合わないので、選ばなかった。

### Alternative 5: 名前に`#`を含むページへは、リンクできないままにする

2026-11-18の最初の決定である。`#`は符号化せず、`#`の後ろはいつもページの中の場所として読む。

- 長所: 設定が増えない。分ける規則が要らない。
- 短所: `[[C#]]`が、`C`というページを開く。`C#`や`F#`のような名前は、ふつうにある。

開発者が、同じ日に改めた。

### Alternative 6: wikilinkの中で`#`をエスケープする

名前の中の`#`を、`[[C\#入門]]`のように書く。

- 長所: 規則が単純で、フラグメントの形を知らなくてよい。
- 短所: 書く人が、エスケープを覚える必要がある。忘れると、エラーにならずに、別のページへのリンクになる。

選ばなかった。

### Alternative 7: ページの中の場所を指す記号を変える

`[[Page#^id]]`のように、`#`ではない書き方にする。

- 長所: 名前の`#`と区切りが、書き方で見分けられる。
- 短所: 今ある`[[Page#id]]`の書き方が変わる。PetaJournalでは、同期している`.md`ファイルと、すべての端末のコードを、同時に変える必要がある。

選ばなかった。

### Alternative 8: flatmarkdownが、HMTIDの形を知る

設定を足さず、flatmarkdownの中にHMTIDの形を書く。

- 長所: アプリは何も渡さなくてよい。
- 短所: flatmarkdownが、PetaJournalのidの形に縛られる。sosuisen.netのような、項目のidを持たないサイトでも、HMTIDの形の文字が区切りになる。

開発者が、形は外から渡すと決めた。

## Confidence Level

確信度は高い。既定の設定では今と同じHTMLになるので、既存のアプリへの影響はない。Webのシェルとsosuisen.netの書き換えが消えることは、コードを読んで確かめた。

次のときは、見直す。

- 符号化の規則が合わないアプリが出たとき。たとえば、名前を`?tag={}`のようにクエリへ入れるサイトでは、`&`や`=`も符号化する必要がある。そのときは、テンプレートに符号化の設定を足すか、Alternative 3の関数を考え直す。
- Rustの`regex`クレートとJavaScriptの`RegExp`で、同じ正規表現の一致が違うと分かったとき。2026-11-18の時点で、HMTIDの形の正規表現を、両方で動かして確かめてはいない。
- 名前の最後が`#`とフラグメントの形で終わるページへ、リンクする必要が出たとき。たとえば、`Log#20260426035700_QZ998PX`という名前のページである。
- テンプレートで決めたい部分が増えたとき。たとえば、画像の大きさや、wikilinkとhashtag以外のリンクである。設定が増えるようなら、`HtmlOptions`の形を見直す。

## Consequences

良い結果：

- Webのシェルから、`point_links`と`data-page`の属性が消える。リンクの`href`は、描画の時点で正しくなる。
- sosuisen.netの`fm2html`から、hashtagの`href`を書き換える処理が消える。
- PetaJournalの外のサイトでも、`/tags/{}.html`のような形でリンク先を決められる。

悪い結果：

- flatmarkdown-ast2htmlの公開APIが、`HtmlOptions`と`ast_to_html_with`の2つ増える。設定を足すたびに、すべての描画関数へ設定を渡す必要がある。
- タグ用ディレクトリを変えると、Webのシェルはすべての項目のHTMLを作り直す。今は`href`だけを書き換えている。めったに変えない設定なので、受け入れる。
- 符号化の規則が、RustとTypeScriptの2か所にある。同じ表のテストでそろえるが、`ast2react`の側の表は写しである。
- 日本語のページ名のURLは、`%E6%97%A5…`の形になる。ブラウザーのアドレスバーは元の文字で見せるが、サーバーが返す`url`（ADR 061）は、そのままでは読みにくい。
- `HtmlOptions`の設定が3つになる。ページの中の場所を指すリンクを持つアプリは、3つ目を渡し忘れると、そのリンクが`%23`を含む名前のページを開く。
- flatmarkdown-ast2htmlが、`regex`クレートに依存する。2026-11-18の時点で、すでに依存しているかは確かめていない。
- 名前の最後が`#`とフラグメントの形で終わるページへは、リンクできない。

中立的な結果：

- 名前に`#`を含むページへ、リンクできる。`[[C#]]`は`/pages/C%23`になる。

- 3つのクレートの版が`0.9.0`になる。PetaJournalとsosuisen.netは、版を上げてから、新しい関数に切り替える。
- ADR 026の決定のうち、リンクの`href`を描画のあとに書き換える項目は、このADRで置き換わる。画像の大きさとコードブロックの色付けは、ADR 026のまま残る。
- 「HTMLとしてコピー」（ADR 027）は、今のまま変わらない。memoviewは、ADR 061で変える。
