# ADR 074: Empty Item Bodies Written as `&nbsp;` in Files

## Status

Accepted

## Context

journal-coreは、本文が空の項目を、ページのファイルにメタデータ行だけで書く（`flat_markdown_serializer.rs`の`append_item`）。
項目と項目の間には改行が1つ入るので、ファイルではメタデータ行の後に空行が続く。

```markdown
<!-- @ <id1> idx="..." modified="..." -->
a

<!-- @ <id2> idx="..." modified="..." -->

<!-- @ <id3> idx="..." modified="..." -->
b
```

flatmarkdownの`parse_page`は、メタデータ行の後に、次のメタデータ行かファイルの末尾まで空行しかないとき、そのメタデータ行を本文が空の項目として読む（flatmarkdownの`SPEC.md`の「記述位置」）。
journal-coreが書いたファイルは、すべての項目がメタデータ行を持つので、この規則で空の項目に戻る。

しかし、空の項目の下に、メタデータ行のないブロックが続くと、空の項目は戻らない。

```markdown
<!-- @ -->


# hello
```

flatmarkdownの`SPEC.md`は、メタデータ行と本文の間の空行を無視すると定めている。
このため、`parse_page`は、上のファイルを本文が`# hello`の1つの項目として読む。
書いた人が意図した「空の項目」と「`# hello`の項目」の2つにはならない。
メタデータ行のないブロックは、手で編集したファイルや、ほかのツールで書いたファイルに現れる（ADR 048）。
Markdownの整形ツールが、ブロックの間の空行を足したり減らしたりすることもある。

flatmarkdownの規則を変え、メタデータ行の直後の空行で空の項目を表すこともできる。
しかし、整形ツールがメタデータ行の後に空行を入れると、すべての項目が「空の項目」と「メタデータ行のない項目」に分かれ、idとレベルを失う。
今の「空行を無視する」規則は、この崩れを防いでいる。

ADR 070は、シェルの本文の空行を、ファイルでは`\`だけの行として書くと決めた。
本文の末尾の空行は、編集を終えるときに削る。
空行だけの本文は、空の本文になる。
ADR 070は、flatmarkdownの`SPEC.md`と`SPEC_ja.md`に、次の注釈を足すとも決めた。

> Flat Markdownでは、独自のコメント行`<!-- @ -->`を用いた場合に限り、通常のMarkdownと比べ、簡単に空行を表現することができる。
> ただし、この空行は通常のMarkdownビューアでは表示されない。

この注釈の空行は、メタデータ行だけで表す空の項目のことである。

## Decision

### flatmarkdownの規則は変えない

flatmarkdownの`parse_page`の規則は変えない。
メタデータ行と本文の間の空行は、これまでどおり無視する。

### journal-coreは、空の本文を`&nbsp;`と書く

journal-coreは、Flat Markdownを書くとき、本文が空の項目の本文を`&nbsp;`と書く。
対象は、`flat_markdown_serializer.rs`を通るすべての書き出しである。
ページのファイル、`export_service.rs`の書き出し、`tree_markdown.rs`の変換が、これに当たる。

```markdown
<!-- @ <id2> idx="..." modified="..." -->
&nbsp;
```

`&nbsp;`は段落のブロックになる。
メタデータ行のないブロックが下に続いても、`&nbsp;`の項目と、その下の項目は分かれる。
ほかのMarkdownビューアでは、`&nbsp;`は空いた行として表示される。

### journal-coreは、読むときに`&nbsp;`を外す

journal-coreは、Flat Markdownを読むとき、本文全体が`&nbsp;`だけの項目を、本文が空の項目として読む。
前後の空白は無視する。
対象は、ページのファイルの取り込み（`outline_parser.rs`）と、`PasteMode::Flat`の貼り付け（`paste.rs`）である。
本文の途中の`&nbsp;`（たとえば`a&nbsp;b`）や、`&#160;`、`&NBSP;`は外さない。

PetaJournalでは、本文が`&nbsp;`だけの項目は、空の項目と同じに見える。
ユーザーが、`&nbsp;`だけの本文を空の本文と区別して書く理由はない。
そのため、読むときに外しても、ユーザーの意図は失われない。

### 手で書くファイルでは、`&nbsp;`は要らない

`&nbsp;`は、journal-coreが書くときの規則である。
`.md`ファイルを手で書く人は、`&nbsp;`を書かなくてよい。
メタデータ行と次のメタデータ行の間に空行しかなければ、その項目は空の項目として読まれる。
ファイルの末尾のメタデータ行の後に空行しかない場合も、同じである。
これは、flatmarkdownの今の規則のとおりである。

```markdown
<!-- @ -->

<!-- @ -->
# hello
```

上のファイルは、空の項目と、本文が`# hello`の項目の2つとして読まれる。
空の項目の下の項目にもメタデータ行を書けば、空の項目は空行だけで表せる。
メタデータ行のないブロックが下に続くときだけ、空の項目に`&nbsp;`を書く必要がある。

```markdown
<!-- @ -->
&nbsp;

# hello
```

### 外すのは、ADR 006の比較より前である

journal-coreの`item_merger.rs`は、ファイルの本文とDBの本文を比べ、項目が手で編集されたかを決める（ADR 006）。
journal-coreは、`&nbsp;`を外してから、この比較をする。
外さずに比べると、空の項目がすべて手で編集されたとみなされ、`modified`が進み、ファイルへの書き戻しが起きる。

### 変換するのは、ファイルとの境目である

`&nbsp;`の変換は、journal-coreがFlat Markdownを書くときと読むときだけに行う。
DBには、空の本文を`""`として入れる。
シェル、REST、MCPが扱う空の本文も`""`である。

空の項目の多くは、journal-coreが自分で作る。
たとえば、Enterで本文の先頭から分けたときの上の項目（`split.rs`の`empty_above`）や、ページを空にしないための項目（ADR 021）である。
シェルとの境目で変換すると、DBに`""`と`&nbsp;`の2種類の空の本文が混ざる。

ADR 070の`\`は、シェルとの境目で変換する。
`\`は、シェルで打った本文の中身の空行を表す。
`&nbsp;`は、項目の本文が空であることを、ファイルの中で表す。
表すものが違うので、変換する境目も違う。

### 変換の順序

書く向きでは、client-coreがADR 070の変換をし、本文の末尾の空行を削って保存する。
journal-coreは、ファイルに書くときに、空の本文を`&nbsp;`にする。
読む向きでは、journal-coreが、本文が`&nbsp;`だけなら空にする。
本文が空でなければ、client-coreがシェルに渡すときにADR 070の読む向きの変換をする。

### ADR 070の「flatmarkdownのドキュメント」の節を置き換える

ADR 070が決めた注釈は、空の項目がメタデータ行だけで表されることを前提にしている。
この決定で、空の項目は`&nbsp;`で表され、通常のMarkdownビューアでも空いた行として表示される。
そのため、注釈の後半は成り立たない。

ADR 070の「flatmarkdownのドキュメント」の節を、次の決定で置き換える。
flatmarkdownの`SPEC.md`と`SPEC_ja.md`の共通の規則には、注釈を足さない。
flatmarkdownの規則は変わらないためである。
`SPEC_ja.md`の「PetaJournalにおけるFlat Markdownの運用」の節と、`SPEC.md`の「Flat Markdown in PetaJournal」の節に、次の3つを書く。

- 本文の先頭と途中の空行は、`\`だけの行として書く（ADR 070）。
- 本文が空の項目は、`&nbsp;`と書く。本文が`&nbsp;`だけの項目は、空の項目として読む（この決定）。
- 手で書くときは、`&nbsp;`は要らない。メタデータ行と次のメタデータ行の間に空行しかなければ、空の項目として読む。メタデータ行のないブロックが下に続くときだけ、`&nbsp;`を書く（この決定）。

ADR 070のStatusを`Accepted (amended by ADR 074)`にする。
ADR 070のほかの決定は変えない。

### 既存のファイル

既存のファイルは移行しない。
メタデータ行と空行だけで書かれた空の項目は、flatmarkdownの今の規則で、これまでどおり空の項目として読める。
journal-coreが次にそのページを書くとき、空の項目は`&nbsp;`で書かれる。

## Alternatives

### Alternative 1: メタデータ行と空行だけで書く

今の書き方を続ける。
- 長所：コードを変えなくてよい。ほかのビューアでは何も表示されない。
- 短所：空の項目の下に、メタデータ行のないブロックがあると、空の項目はそのブロックに飲み込まれる。
- 選ばなかった理由：手で編集したファイルや、整形ツールを通したファイルで、項目が崩れる。

### Alternative 2: メタデータ行の直後の空行で、空の項目を表す

flatmarkdownの規則を変え、メタデータ行は、すぐ次の行から始まるブロックにだけ付くとする。
- 長所：journal-coreの今の書き出しのままで、空の項目が戻る。
- 短所：flatmarkdownの破壊的な変更になる。整形ツールがメタデータ行の後に空行を入れると、すべての項目がidとレベルを失う。
- 選ばなかった理由：崩れたときの被害が、今の問題より大きい。

### Alternative 3: 空の本文を`\`だけの行で書く

ADR 070と同じ`\`だけの行で、空の本文を書く。
- 長所：ADR 070の読む向きの変換で、自然に空の本文に戻る。新しい目印が要らない。
- 短所：ほかのビューアで、文字の`\`が表示される。ADR 070が本文の末尾の`\`を避けたのと同じ理由である。
- 選ばなかった理由：`&nbsp;`は、ほかのビューアで空いた行として表示される。

### Alternative 4: 本文の途中の空行も`&nbsp;`の行で書く

ADR 070の`\`をやめ、本文の空行もすべて`&nbsp;`の行で書く。
- 長所：空行の目印が1つになる。`\`と`\\`のエスケープが要らない。
- 短所：`a`、`&nbsp;`、`b`は段落の継続行になり、ほかのビューアでは`a b`と1行につながって表示される。`\`なら強制改行になる。
- 選ばなかった理由：ほかのビューアでの見え方が、ADR 070より悪くなる。

### Alternative 5: client-coreとシェルの境目で変換する

ADR 070と同じ境目で、空の本文を`&nbsp;`にする。
- 長所：本文の変換が、すべてclient-coreにまとまる。
- 短所：journal-coreが作る空の項目は`""`のままなので、DBに2種類の空の本文が混ざる。ファイルに書くときに、結局`""`も直す必要がある。
- 選ばなかった理由：決まりを1か所にまとめられない。

## Confidence Level

中程度である。
`&nbsp;`だけの行が1つの段落のブロックになり、メタデータ行のない次のブロックと分かれることは、flatmarkdownで確かめた。
メタデータ行と空行だけの古い形が、空の項目として読めることも確かめた。

次の場合は見直す。
- ユーザーが`&nbsp;`だけの本文を、空の本文と区別して使いたいと分かった場合。
- ほかのツールが、`&nbsp;`を別の文字や空白に書き換えると分かった場合。
- flatmarkdownの、メタデータ行と空行の規則が変わった場合。

## Consequences

### 良い結果

- 空の項目の下にメタデータ行のないブロックがあっても、空の項目が残る。
- ほかのMarkdownビューアで、空の項目が空いた行として表示される。
- flatmarkdownの規則を変えずに済む。
- DB、シェル、REST、MCPの空の本文は`""`のままである。

### 悪い結果

- ユーザーが本文に`&nbsp;`だけを書くと、読み戻したときに空の本文になる。
- journal-coreの書き出しと読み込みに、変換が1つ増える。
- 既存のファイルは、次に書かれるときに`&nbsp;`の形に変わり、差分が出る。

### 中立的な結果

- 空行の目印が、本文の中の`\`（ADR 070、シェルとの境目）と、空の本文の`&nbsp;`（ファイルとの境目）の2つになる。
- flatmarkdownの`SPEC.md`と`SPEC_ja.md`の「PetaJournalにおけるFlat Markdownの運用」の節を更新する必要がある。
- `docs/features.md`の書き出しと取り込みの記述を更新する必要がある。
