# ADR 077: A View Mode and an Edit Mode in Emacs

## Status

Accepted

## Context

Emacs版（`client/apps/emacs/outliner`）は、ほかのシェルと違う形で項目を見せている。
ほかのシェルは、項目を表示の形で描き、1つの項目だけを編集欄にする。
Emacs版は、すべての項目の本文を、Markdownのまま1つのバッファーに並べる。
バッファー全体が、ふつうのテキストとして編集できる。
このADRは、Emacs版をほかのシェルと同じ形にするかを決める。
きっかけは#859の計測である。

### 今の形

Rustのプログラム（`outliner-emacs`）は、`client-core`の`ViewModel<()>`を使う。
本文の形を持たないので、Emacsに送る行（`protocol.rs`の`RowView`）は、本文をMarkdownの文字列で持つ。
Lisp（`lisp/peta-journal.el`）は、`peta-journal--font-lock-keywords`の約40の正規表現で、Markdownに色を付ける。
画像のリンクも、`peta-journal--image-link-regexp`などの正規表現で見つける。
ほかのシェルは、`client-core`の`RichText`（`rich_text/mod.rs`）を描く。
`RichText`は、Rustのパーサーが作るAST（ADR 041）から作られる。
Markdownを読む処理が、RustとLispの2か所にある。

打っている途中の本文は、Emacsが持っている。
シェルから行が届くと、`peta-journal--keep-typed-body`が、届いた本文を画面の本文に差し替える。
行の差分は、ADR 019のとおり、Lispが`cl-mismatch`で頭と末尾から比べて作る。
ほかのネイティブのシェルは、ADR 076の`changes()`で、Rustが作った差分を当てる。

### 個別のメンテナンス

方式が違うので、Emacs版だけの作業が続いている。
2026-11-07には、強調、コード、引用、表、見出し、リンク、絵文字などの色付けを、約10のコミットでLispに作った。
Rustのパーサーは、これらをすでに読めていた。
同じ日に、対になっていない強調の記号に色を付けない直しを入れた（`3546eeca`）。
2026-11-16には、リンクの文字に`[]`がある画像を表示する直しを入れた（`844e8613`）。
Lispの色付けが、RustのASTと同じ結果になるかを確かめるテストはない。
Markdownの書き方が増えるたびに、RustとLispの両方を直す必要がある。

### 計測

#859で、1000項目のページで1つのキーにかかる時間を測った（2026-11-22、AMD Ryzen 7 7700）。
文字を打つとき、Rustのプログラムは0.38msで、Emacsに行を送らない。
字下げで行が変わるとき、Rustのプログラムは0.68msで、120KBのJSONを送る。
Lispは、それを読んで書き直すのに4.28msかかる。
JSONを読むのは0.45msだけである。
残りのほとんどは、行の位置をバッファーの頭からたどる`peta-journal--nth-row`と、選択の色を全部の行に塗り直す`peta-journal--show-selection`である。
行の差分をRustで作るだけでは、Lispの書き直す処理は薄くならない。
差分の操作を当てる位置を探すのにも、行の位置が要るためである。

## Decision

Emacs版に、ほかのシェルと同じ表示モードと編集モードを持たせる。
項目は表示の形で描き、編集するのは1つの項目だけにする。

### 編集モードへの入り方

pointが入った項目を、自動で編集モードにする。
Lispは、pointが別の項目に移ったら、前の項目に`EditFinished`を、新しい項目に`EditRequested`を送る。
`C-n`や`C-p`で、今と同じように項目をまたいで動ける。
ほかのシェルで、項目の最初の行で↑を押すと上の項目の編集に移るのと同じ形である。
表示の文字の位置と、Markdownの文字の位置は違う。
たとえば、太字の`**`は表示されない。
編集モードに入るときの位置は、`RichText`が数えた表示の文字の位置（ADR 043、ADR 044）から、Markdownの位置に変える。

### 項目をまたぐ操作

項目をまたぐテキストの操作は手放す。
`query-replace`、項目をまたぐkill、矩形の操作がこれに当たる。
項目をまたぐ操作は、今ある選択モード（`peta-journal-selection-mode`）で行う。

### 表示の情報

Rustのプログラムは、`ViewModel<()>`をやめ、本文の形に`EmacsText`を使う。
`EmacsText`は、表示する文字列と、範囲ごとの見た目、リンク、画像を持つ。
型と作り方は、ADR 078で決める。
Lispは、見た目をEmacsの`face`にし、リンクを開けるようにし、画像を`display`で見せるだけにする。
Lispの`peta-journal--font-lock-keywords`と、Markdownを読む正規表現は消す。

### 編集中の項目

編集中の項目は、Markdownのまま見せ、色は付けない。
ほかのシェルの編集欄と同じである。

### 行の差分

行の差分は、ADR 078に従う。
Lispは、受け取った差分で、表示の行を置き換え、足し、消し、動かす。
特別な扱いが要るのは、編集中の1行だけである。

## Alternatives

### Alternative 1: 今の形のまま、Lispの遅い処理だけを直す

`nth-row`と`show-selection`を直せば、行が変わるときの約4msは消える見込みである。
作業は小さい。
しかし、Markdownを読む処理は2か所に残り、Emacs版だけのメンテナンスが続く。
そのため、選ばなかった。

### Alternative 2: 今の形のまま、行の差分だけをRustで作る

ADR 068の「差分を作るのはRustの1か所」にそろう。
しかし、Lispは差分の操作を当てる処理を新しく持つことになり、薄くならない。
打っている本文の扱い（`keep-typed-body`）も、差分の操作ごとに考える必要がある。
Markdownを読む処理は2か所に残る。
そのため、選ばなかった。

### Alternative 3: 編集モードに、キーではっきり入る

`RET`などのキーで編集モードに入る形である。
作りは簡単になる。
しかし、`C-n`や`C-p`で項目をまたいで動けなくなり、Emacsでの使い心地が大きく変わる。
そのため、選ばなかった。

### Alternative 4: 編集中の項目に、今のfont-lockの色を残す

編集中も、Markdownに色が付く。
しかし、Lispの正規表現が、編集中の1項目のためだけに残る。
2か所のメンテナンスが続くので、選ばなかった。

## Confidence Level

確信度は中くらいである。
共通化の効果は、コミットの履歴とコードから確かめた。
一方で、Emacsでの使い心地と速さは、まだ確かめていない。

次のときに見直す。

- pointが項目をまたぐたびに編集モードを切り替える形が、Emacsで使いにくいと分かったとき。
- 項目をまたぐテキストの操作が、選択モードでは足りないと分かったとき。
- 表示の文字列と見た目の範囲を送る形が、今より大きく遅いと分かったとき。

## Consequences

良い結果は次のとおりである。

- Markdownを読む処理が、Rustのパーサーの1か所になる。Markdownの書き方が増えても、Lispを直さなくてよい。
- Emacs版の表示が、ほかのシェルと同じ`RichText`から作られる。シェルごとに表示がずれることがなくなる。
- 行の差分が、ネイティブのシェルと同じ差分から作られる（ADR 078）。
- 打っている本文の扱いが、編集中の1行だけになる。

悪い結果は次のとおりである。

- Emacsで、項目をまたいでふつうのテキストとして編集することはできなくなる。
- Lispの多くと、ERTとE2Eのテストを作り直す。作業は大きい。
- pointの移動を、編集モードの切り替えに変える処理が新しく要る。表示の位置とMarkdownの位置の変換も要る。
- 見た目の範囲を送るので、ページを開くときにEmacsに送るJSONは大きくなる。1000行で見た目とリンクを付けるのに1.36msかかった（ADR 078）。ただし、キーを打つたびに送るのは、変わった行だけである。

中立的な結果は次のとおりである。

- 差分の置き場所、Emacsへの運び方、ADR 019の置き換えは、ADR 078で決める。
- Web版を差分の形にするかは、このADRでは決めない。#931で扱う。
