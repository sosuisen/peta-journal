# ADR 005: Schema Version in PRAGMA user_version

## Status

Accepted

## Context

サーバーは起動のたびに、`database_initializer.rs`の初期化をすべて走らせる。`CREATE TABLE IF NOT EXISTS`で表を作り、`migrate_tag_key_to_tags`と`migrate_bounds_value_type`がDBの中身を見て「古い形が残っているか」を判断し、`seed_system_keys`がシステムのキーを揃える。

DBは、自分がどの版まで更新済みかを知らない。そのため、マイグレーションはすべてべき等に書かなければならず、起動のたびに「古い形が残っていないか」を調べ直す。Javaサーバー時代のマイグレーションは、役目を終えたあとも半年以上この確認を続けていた（2026-11-03のPR #49で削除）。いつ消してよいかの判断も、DBの外の記録（`docs/plans.md`の日付）に頼っている。

版の記録として`versions.json`がある。設定フォルダに`{"schemaVersion": "0.1"}`を書き、サーバーに埋め込んだ値と違えば警告を出す。ただし、この値は一度も変わっておらず、読むのは`check_schema_version`だけである。DBファイルとは別のファイルなので、DBだけをコピーしたり設定フォルダだけを消したりすると、版がずれる。

SQLiteには`PRAGMA user_version`がある。DBファイルのヘッダーに入る32bitの整数で、SQLite自身は使わない。アプリが版の記録に使える。

## Decision

スキーマの版を`PRAGMA user_version`に記録し、マイグレーションを番号付きの列として順に適用する形を採用する。

- マイグレーションは、`database_initializer.rs`に関数の配列として並べる。配列の位置が版である。版1は今の形の`CREATE TABLE`であり、新しいDBもこの列を最初から通る。
- 起動時に`user_version`を読み、その版より後のマイグレーションだけを順に走らせる。1つのマイグレーションごとにトランザクションを開き、中で`user_version`を次の版に更新してcommitする。途中で落ちても、半分だけ済んだ版は残らない。
- 各マイグレーションは1回しか走らない。べき等に書かなくてよく、「古い形が残っているか」を調べる処理は書かない。
- `seed_system_keys`と`ensure_root_index`はマイグレーションではなく、起動のたびに走る初期化として今のまま残す。
- `user_version`がサーバーの知る版より大きければ、古いサーバーで新しいDBを開いている。エラーにして起動を止める。
- `versions.json`、`SCHEMA_VERSION`、`check_schema_version`は消す。設定フォルダに残った`versions.json`は読まなくなるだけなので、消しに行く処理は書かない。
- 引き継ぐ既存のDBは、開発機の1つだけである。他の機械のDBは消して、Markdownから再インポートする。開発機のDBはすでに最新の形なので、`items`表があって`user_version`が0なら、版を1に書くだけにする。この入口は、開発機のDBが版1になった時点で消す。
- 上の前提により、Rust時代のべき等なマイグレーション（`migrate_tag_key_to_tags`、`migrate_bounds_value_type`、`AtlasService::move_old_properties`）は、2026-12-03を待たずにこの移行で消す。
- ダウングレードは作らない。必要になった場面がないためである。

## Alternatives

### Alternative 1: 今のまま（べき等なマイグレーションを毎回走らせる）

変更がない。ただし、DBが自分の版を知らないので、マイグレーションはすべて「古い形が残っているか」を毎回調べる。役目を終えたあとも走り続け、消す時期はDBの外の記録に頼る。この問題を直すことが目的なので、選ばない。

### Alternative 2: `versions.json`を本当の版にする

設定フォルダの`versions.json`に整数の版を書き、それを見てマイグレーションを選ぶ。SQLiteの機能に依存しない。短所は、版がDBファイルの外にあることである。DBだけをコピーしたり設定フォルダだけを消したりすると、版と中身がずれる。ずれたときにどちらが正しいかはDBを見なければ分からず、結局DBの中に版が要る。選ばない。

### Alternative 3: マイグレーションの表（`schema_migrations`）をDBに作る

適用済みのマイグレーションの名前と日時を1行ずつ記録する表を作る。RailsやFlywayがこの形である。適用の履歴が残り、番号の衝突を名前で避けられる。短所は、表の作成そのものがマイグレーションの前に要ることと、1人で順に番号を振る開発では履歴の表が過剰なことである。`user_version`はDBのヘッダーに最初からあり、表を作らずに使える。選ばない。

### Alternative 4: マイグレーションのクレート（`rusqlite_migration`など）を使う

`user_version`を使った同じ仕組みを、ライブラリとして提供する。自分で書く量は減る。短所は、依存が1つ増えることと、仕組みが数十行で書けることである。トランザクションの扱いをADR 004と揃えたいので、自分で書く。選ばない。

## Confidence Level

高い。`user_version`でスキーマの版を管理する形は、SQLiteを使うアプリで広く使われている。マイグレーションは1人が順に番号を振るので、番号の衝突も起きない。

次の変化があれば見直す。

- 複数の開発者が同時にマイグレーションを足すようになり、番号が衝突する。そのときは、名前で記録する表（Alternative 3）を検討する。
- DBファイルを複数に分ける。そのときは、ファイルごとに`user_version`を持つか、1つの版で束ねるかを決め直す。
- 古いサーバーで新しいDBを開く場面が実際に起き、起動を止めるだけでは困る。そのときは、後方互換の範囲を決める。

## Consequences

良い結果

- マイグレーションは1回しか走らない。起動のたびにDBの中身を調べる処理がなくなり、起動が軽くなる。
- マイグレーションはべき等に書かなくてよい。「古い形が残っているか」の判定がなくなり、各関数は短くなる。
- 古いマイグレーションを消す時期が、DBの版で決まる。「版Nより古いDBはもうない」と言えた時点で、列の先頭を切り詰める。
- 古いサーバーで新しいDBを開いたことを、DB自身から判定できる。`versions.json`の警告は要らなくなる。
- 版の正本がDBファイルの中の1か所になる。DBだけをコピーしても版がついてくる。
- Rust時代のべき等なマイグレーション3つと、`versions.json`まわりのコードが、この移行で消える。

悪い結果

- 開発機以外のDBは消して再インポートする。インポートで再現できないDBの中身（アトラスのプロパティなど、Markdownに書き出されないもの）があれば、失われる。
- マイグレーションは一度適用すると書き換えられない。間違えたマイグレーションは、次の版で直す。
- 新しいDBも版1から順に全マイグレーションを通る。マイグレーションが増えると、新規作成に通る段数が増える。古い版を切り詰めることで抑える。

中立的な結果

- `seed_system_keys`と`ensure_root_index`は、版管理の外で毎回走る初期化として残る。「マイグレーション」と「毎回の初期化」の区別を、`database_initializer.rs`のコメントに書く。
- 開発機のDBを版1にする入口は、そのとき限りのコードである。版1になったら消す。
