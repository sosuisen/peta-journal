# ADR 014: flatmarkdown Builds Its AST with the flatmarkdown-ast Types

## Status

Accepted

## Context

ADR 012は、ASTを読む型を`flatmarkdown-ast`クレートとして公開すると決めた。2つのクレートの関係は、「`flatmarkdown`がJSONを作り、`flatmarkdown-ast`がそれを読む」である。`flatmarkdown`は、`serde_json`の値を手で組み立ててJSONを作る。`flatmarkdown-ast`の型は、その形を別に書き写したものである。2つが合っていることは、往復のテストで確かめる。このテストのために、`flatmarkdown-ast`は開発時だけ`flatmarkdown`に依存する。

2026-11-09に、公開の前の整理として、2つのクレートとASTの仕様（`SPEC_AST.md`）を突き合わせた。パーサーの出力は、属性については仕様と一致していた。しかし、型は仕様とずれていた。

- 型には、仕様にない項目が4つあった。`heading`の`setext`、`code_block`の`fenced`、`math`の`dollar_math`と`display_math`である。パーサーは、これらを出力しない。
- 型には、仕様にないノードが7種類あった。`image`、説明リストの4種類、HEExの2種類である。パーサーは画像を`embed`として出力し、残りの6種類は、拡張を有効にしていないので出力しない。
- 型をそのままJSONに書き出すと、子のないノードにも`children`が付き、`embed`には空の`props`が付く。仕様は、どちらも「ないときは省く」と定めている。

型は、TypeScriptの型定義を元に書かれた。ずれた項目とノードは、そこから持ち込まれた。往復のテストは、このずれを見つけられなかった。省かれた項目は既定値で読めてしまい、作られないノードはテストに現れないからである。

ずれは、使う側のコードにも及んでいた。PetaJournalの`fm-leptos`には、`display_math`が真のときの分岐と、`image`を描画する分岐がある。どちらも、実際のデータでは通らない。

仕様の側にも誤りが1つあった。`math`の節は、`` $$`formula`$$ ``をディスプレイ数式の書き方としている。実際には、この書き方は数式として解析されない。

パーサーの中にも、同じ形の無駄がある。`body_to_html`は、ASTをJSONの文字列にしてから、もう一度読み直してHTMLにする。HTMLを作るコードは、ノードの項目を文字列のキーで読む。キーを書き間違えても、コンパイラは見つけない。

`flatmarkdown-ast`は、まだcrates.ioに公開していない。型を変える費用は、今が最も小さい。公開したあとの型の変更は、破壊的な変更になる。

また、ADR 013のviewのプラグインは、項目の並び（`level`、`id`、`properties`、`body`、`ast`）を入力に受け取る。これは`page_to_ast`の出力の項目と同じ形である。しかし、`flatmarkdown-ast`にあるのは本文のノードの型だけで、ページと項目の型はない。

## Decision

`flatmarkdown`は、ASTを`flatmarkdown-ast`の型で作る。JSONは、その型をserdeで書き出して作る。`SPEC_AST.md`を正本とし、型は仕様にあるものだけを持つ。

**依存の向き**

`flatmarkdown`が`flatmarkdown-ast`に依存する。`flatmarkdown-ast`は、`flatmarkdown`に依存しない。開発時の依存も持たない。2つのクレートの関係は、「型を持つ側と、それを使って作る側」になる。ADR 012のうち、往復のテストがワークスペースの中の`flatmarkdown`を参照するという部分を、この決定で置き換える。ADR 012のほかの決定は変えない。2つのクレートの版は、これまでどおり常に同じにする。

公開の順序は、`flatmarkdown-ast`、`flatmarkdown`の順になる。

**型を仕様に合わせる**

- 仕様にない4つの項目を、型から消す。`setext`、`fenced`、`dollar_math`、`display_math`である。
- 仕様にない7種類のノードを、型から消す。`image`、`description_list`、`description_item`、`description_term`、`description_details`、`heex_block`、`heex_inline`である。
- `Unknown`は残す。知らない種類のノードを読むためのもので、仕様の外にあってよい。
- 子のないノードは`children`を書き出さない。`embed`は、空の`props`を書き出さない。
- ページと項目の型を足す。`page_to_ast`の出力である`page`と、その`items`の1件（`level`、`id`、`properties`、`body`、`ast`）を表す。viewのクレートは、この項目の型を入力に使う。

**パーサー**

- comrakの木から、`Node`を直接作る。
- 脚注、ハッシュタグ、リンクの後処理も、`Node`の上で行う。JSONにするのは、最後の1回だけである。
- `body_to_html`は、`Node`を直接読んでHTMLを作る。JSONの文字列を経由しない。
- comrakのノードのうち仕様にないものは、`Node::Unknown`にする。`insert`、説明リスト、HEExである。これらは、拡張を有効にしていないので、実際には現れない。パーサーは、入力によってパニックしない。
- `flatmarkdown-ast`に、子を書き換えるための`children_mut`を足す。後処理が使う。

**公開APIと出力**

`flatmarkdown`の公開する関数は変えない。`body_to_ast`と`page_to_ast`は、これまでどおりJSONの文字列を返す。

出力のJSONは、値としては変わらない。変わるのは、オブジェクトの中のキーの順序だけである。これまではアルファベット順だったが、`type`が先頭になる。JSONではキーの順序に意味がないので、読む側の結果は同じである。

**テスト**

- 往復のテストのうち、パーサーの出力を型で読めることを確かめるものは消す。型が保証するからである。
- JSONの形が仕様どおりであることは、`flatmarkdown`のテストで確かめる。型で読めることと、仕様に合うことは別だからである。
- `flatmarkdown-ast`には、単体で確かめられるテストを残す。知らない種類を許すこと、省かれた項目に既定値を入れること、壊れたノードをエラーにすることである。

**仕様の修正**

`SPEC_AST.md`と`SPEC_AST_ja.md`の`math`の節から、`` $$`formula`$$ ``をディスプレイ数式とする記述を消す。`math`ノードは、常にインラインの数式である。

**このADRで決めないこと**

- TypeScriptの型定義とレンダラーを仕様に合わせること。TypeScriptの側は、`image`を持ち、`embed`を持たない。これは別の課題とする。
- ディスプレイ数式を扱うこと。必要になったら、仕様の変更として別に決める。
- PetaJournalの移行の手順。ADR 012のとおりに進める。ただし、`fm-leptos`の`display_math`と`image`の分岐は、型から消えるので、移行のときに消す。

**作業の順序**

3つのPRに分ける。1つ目で、型を仕様に合わせ、仕様の`math`の記述を直す。2つ目で、パーサーと後処理を型で書き、往復のテストと開発時の依存を消す。3つ目で、HTMLを作るコードを型で書く。0.5.0の公開は、この3つが終わってから行う。

## Alternatives

### Alternative 1: 今の関係のまま、型だけを仕様に合わせる

パーサーは手でJSONを組み立て続け、型からは仕様にない項目とノードを消す。変更は最も小さい。依存の向きも公開の順序も変わらない。しかし、同じ形を2か所に書く状態は残る。次にずれが生じたとき、往復のテストは今回と同じ理由で見つけられない。原因を直さないので、選ばなかった。

### Alternative 2: HTMLを作るコードだけ、型で読む

`body_to_html`が`flatmarkdown-ast`の型でASTを読む。キーの書き間違いを、コンパイラが見つけるようになる。しかし、パーサーは手でJSONを作り続けるので、往復のテストは消せない。そのうえ、`flatmarkdown`が`flatmarkdown-ast`に依存し、`flatmarkdown-ast`が開発時に`flatmarkdown`に依存する形になる。2つのクレートが互いを指すので、選ばなかった。

### Alternative 3: comrakから型を作り、後処理はJSONの値のまま行う

comrakの木から`Node`を作り、すぐJSONの値に直して、脚注、ハッシュタグ、リンクの後処理は今のコードで行う。書き直す量は少ない。しかし、後処理は`hashtag`や`wikilink`のノードを手で組み立てる。出力が型どおりであるという保証が成り立たず、往復のテストも消せない。目的を果たせないので、選ばなかった。

### Alternative 4: 型を1つのクレートにまとめ、`flatmarkdown-ast`をなくす

型を`flatmarkdown`の中に置き、クレートを1つにする。依存の向きも公開の順序も考えなくてよい。しかし、ASTを読むだけの側も、Markdownのパーサーであるcomrakを依存に持つことになる。PetaJournalのフロントエンドとviewのクレートは、wasmで動く。ADR 012が`flatmarkdown-ast`を分けた理由がそのまま当てはまるので、選ばなかった。

### Alternative 5: パーサーが出力しない項目を、出力するように変える

`setext`、`fenced`、`dollar_math`、`display_math`を型に残し、パーサーがそれらを出力する。型とTypeScriptの型定義がそろう。しかし、仕様を変えることになる。`fenced`は、仕様がインデントのコードブロックを扱わないので、常に真である。`dollar_math`と`display_math`は、`$$`の書き方を有効にしていないので、常に偽である。意味のない項目を仕様に足すことになるので、選ばなかった。

### Alternative 6: 今の公開を先に行い、この変更をあとの版で行う

0.4.3の形のまま2つのクレートを公開し、PetaJournalの移行を先に進める。ADR 012の作業は早く終わる。しかし、型から項目とノードを消すことは、公開したあとでは破壊的な変更になる。公開した版は取り消せない。公開の前に直すほうが安いので、選ばなかった。

## Confidence Level

方向についての確信度は高い。作業の量についての確信度は中程度である。

型を仕様に合わせることと、パーサーが型で出力を作ることは、確信している。ずれの原因は、同じ形を2か所に書いていたことである。型を唯一の定義にすれば、この原因はなくなる。出力が変わる箇所は、2026-11-09に調べた。7つの本文をパーサーで解析し、その出力を型で読んで書き戻し、元と比べた。違いは、Contextに挙げたものだけだった。型を仕様に合わせれば、値としての出力は変わらない。

確かめていないことが4つある。

第一に、後処理を型の上で書き直す量である。脚注、ハッシュタグ、リンクの後処理は、合わせて約300行ある。`\#`を元に戻す処理は、今はJSONの中のすべての文字列を種類を問わずに書き換えている。型の上では、文字列を持つ項目を種類ごとに扱うことになる。書き方によっては、コードが今より長くなる。

第二に、キーの順序の影響である。PetaJournalのサーバーには、ASTの文字列どうしを比べる箇所は見当たらなかった。フロントエンドは、網羅的には調べていない。項目を丸ごと比べる箇所があれば、同じ本文でも古いASTと新しいASTが違うと判定され、余分な更新が1回起きるおそれがある。

第三に、確かめた入力の範囲である。7つの本文は、ノードの種類をひととおり含むように選んだ。しかし、すべての組み合わせを試したわけではない。既存のテストは、JSONの値を確かめている。これが通ることを、出力が変わらないことの根拠にする。

第四に、ページと項目の型の形である。viewのクレートは、まだ1つもない。最初の`timeline`を書いたときに、型の形を直したくなるかもしれない。

次のいずれかが起きたら、この決定を見直す。

- 後処理を型の上で書いた結果、コードが今より大幅に読みにくくなった。その場合は、後処理の入口と出口だけを型にすることを検討する。
- ASTの仕様に、パーサーの種類によって出力が変わる項目を足すことになった。型を仕様に合わせるという方針と、両立するかを確かめる。
- Rust以外のパーサーが、同じASTを作るようになった。その出力を`flatmarkdown-ast`で読めることは、型では保証されない。往復のテストに当たるものが、その実装の側に要る。
- TypeScriptの型定義を、Rustの型から生成することにした。型がさらに1つの定義に寄るので、2つのクレートの分け方を考え直す。

## Consequences

**良い結果**

ASTの形は、`flatmarkdown-ast`の型の1か所だけに書かれる。パーサーの出力は、型から作られる。同じ版の`flatmarkdown`が作ったASTを同じ版の`flatmarkdown-ast`で読めることは、テストではなく型が保証する。

型にある項目は、パーサーが必ず埋める。型に項目を足して、パーサーが出力し忘れるという形のずれは、コンパイルの時点で見つかる。

使う側は、実際に現れるノードだけを扱えばよい。`match`の分岐が、項目で4つ、ノードで7種類減る。PetaJournalの`fm-leptos`からは、通らない分岐が消える。

`flatmarkdown-ast`は、`flatmarkdown`への依存を持たなくなる。公開するパッケージからテストを除く必要もなくなる。テストは、パッケージからそのまま実行できる。

`body_to_html`は、JSONの文字列を作って読み直すことをやめる。HTMLを作るコードは、項目を型で読む。キーの書き間違いは、コンパイラが見つける。

viewのクレートは、入力の型を`flatmarkdown-ast`から得る。項目の形を、クレートごとに書き写さなくてよい。

**悪い結果**

`flatmarkdown`の依存に、`flatmarkdown-ast`と`serde`が加わる。

公開の順序が変わる。`flatmarkdown-ast`を先に公開しなければ、`flatmarkdown`を公開できない。READMEのリリースの手順を直す。

0.5.0の公開が遅れる。3つのPRが終わるまで、PetaJournalの移行（ADR 012）に進めない。

`flatmarkdown-ast`の公開APIが増える。`children_mut`と、ページと項目の型である。公開したあとは、変えにくい。

Rustの型とTypeScriptの型定義のずれが、はっきりする。Rustは`embed`を持ち、`image`を持たない。TypeScriptは、その逆である。TypeScriptの側を直すまで、2つは同じASTの型ではない。

後処理のコードは、書き直しになる。動作を変えない変更だが、量がある。書き直しの途中で動作を変えてしまうおそれは、既存のテストで防ぐ。

**中立的な結果**

出力のJSONは、キーの順序だけが変わる。PetaJournalのDBには、古い順序のASTが残る。値としては同じなので、読む側は区別しなくてよい。項目が更新されるたびに、新しい順序に置き換わる。

ADR 012のうち、往復のテストについての部分は、このADRに置き換わる。ADR 012のほかの決定は、そのまま有効である。

`flatmarkdown`の公開する関数と、その戻り値の型は変わらない。使う側のコードは、そのまま動く。

仕様の`math`の節が変わる。動作は変わらない。これまでも、`` $$`formula`$$ ``は数式として解析されていなかった。

`Node`に`#[non_exhaustive]`を付けないという決定（ADR 012）は変えない。ノードの種類を減らすことは、公開の前なので、破壊的な変更にならない。
