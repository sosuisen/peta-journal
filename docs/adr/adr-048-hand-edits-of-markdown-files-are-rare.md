# ADR 048: Hand Edits of Markdown Files Are Rare

## Status

Accepted

## Context

ADR 006 は、Markdown ファイルを正本に保ち、人が読んで手で編集できるようにすることを、フォルダ同期の制約とした。
手で編集したファイルは取り込まれ、項目の日付は新しくなる。

一方で、ふだんの編集は、Web、Emacs、iOS、Android、Windows のアプリで行う。
`.md` を直接開いて書き換える場面は、多くない。

プロパティは、今でも手で編集しやすい形ではない。
項目のプロパティは、項目ごとのメタデータ行に、HTML のコメントとして書かれる。
その行には、項目の id、並び順の `idx`、更新日時の `modified` も並ぶ。

```
<!-- @@ <id> idx="..." modified="2026-03-01T00:00:00Z" plan="2026-03-01" tags="a,b" zoom="1.5" -->
```

ページのプロパティは frontmatter に書かれるので、項目のものより読みやすい。
ただし、`id`、`created`、`modified` のように、アプリが管理するキーも並ぶ。

Obsidian や Logseq のように `.md` に保存するツールも、編集はツールで行う前提である。
ファイルを直接編集することは、副次的な使い方とされている。
たとえば Obsidian は、プロパティの型を `.obsidian/types.json` に置き、ツールの画面で決める。

設計では、手で編集できることと、アプリでの編集が食い違うことがある。
手で書きやすくすると、アプリの側の仕組みが複雑になったり、同期の衝突が増えたりする。
ADR 047 では、プロパティの型をキーの名前の接尾辞（`_n`、`_d` など）から決めた。
接尾辞は `.md` の中だけで見え、手で書く人には分かりにくい。
それでも採ったのは、手で書く場面が少ないと考えたからである。

この仮定は、これまで ADR ごとに暗に置かれてきた。
明文化しないと、将来の設計で、手で書きやすさをどこまで守るかが毎回ぶれる。

## Decision

**`.md` ファイルを手で編集する場面は多くない、と仮定して設計する。**
ふだんの編集は、Web、Emacs、iOS、Android、Windows のアプリで行うものとする。

**手で編集できることは保つ。**
ADR 006 のとおり、Markdown ファイルは正本のままとする。
手で書き換えたファイルは取り込む。
手で書いた内容が規則に合わなくても、黙って直したり消したりしない。
たとえば、型に合わない値は文字列のまま保つ。

**手での書きやすさは、ほかの目的より後に置く。**
ほかの目的とは、端末の間で衝突しない同期と、アプリの仕組みの単純さである。
手で書きやすくするために、これらを損なわない。
ファイルの中の名前や形式が手で書く人に分かりにくくても、アプリの画面で隠せるなら採ってよい。
ADR 047 の接尾辞が、その例である。

**ファイルは、人が読める形に保つ。**
手で書くための補助は、ファイルに置かない。
たとえば、型の印や、規則の説明である。

## Alternatives

### Alternative 1: 手で編集する場面が多いと仮定する

手での書きやすさを、同期と仕組みの単純さより先に置く。

- 長所: `.md` を開けば、名前や形式の意味がすぐ分かる。
- 短所: 型の印や長い名前など、手で書くための補助がファイルに増える。補助のために、端末の間の衝突を許す場面も出る。ADR 047 では、型を名前から決められなかった。
- 選ばなかった理由: 実際の編集のほとんどはアプリで行う。少ない場面のために、ふだんの同期を弱めることになる。

### Alternative 2: 手での編集を認めない

Markdown ファイルを、DB から書き出すだけの写しにする。
手で書き換えても取り込まない。

- 長所: ファイルの形式を、アプリの都合だけで決められる。手で書いた値の救済も要らない。
- 短所: ADR 006 の「Markdown ファイルを正本に保つ」が崩れる。アプリが壊れたときに、ファイルを直して救うことができない。
- 選ばなかった理由: 正本を人が読めて直せることは、このプロジェクトの前提である。

### Alternative 3: 仮定を書かず、ADR ごとに決める

今までどおり、それぞれの設計で、手での書きやすさをどこまで守るかを決める。

- 長所: 設計ごとに、事情に合わせて決められる。
- 短所: 判断が毎回ぶれる。同じ議論を、ADR ごとにやり直すことになる。
- 選ばなかった理由: ADR 047 で、この仮定が判断を分けた。今後も同じ場面が来る。

## Confidence Level

この決定の確信度は高い。

プロパティは、今でも手で編集しやすい形ではない。
それでも、手で編集できないことが問題になったことはない。
Obsidian や Logseq のような、`.md` に保存するツールも、ツールでの編集を前提にしている。

次のどれかが起きたら、この決定を見直す。

- ユーザーが、`.md` を直接編集する場面が増えた。たとえば、アプリのない端末で書く場面である。
- 別のエディタや AI が、`.md` を直接書き換えるようになった。MCP を通さずにファイルを書く道具が、その例である。
- アプリが壊れて、ファイルを手で直して救う場面が、繰り返し出てきた。

## Consequences

### 良い結果

- 手での書きやすさを、どこまで守るかの判断がぶれなくなる。将来の ADR は、この ADR を引いて決められる。
- ファイルの形式を、端末の間で衝突しない同期と仕組みの単純さに合わせて決められる。ADR 047 の接尾辞は、その最初の例である。
- 手で書き換えたファイルは、今までどおり取り込まれる。手で書いた内容は、規則に合わなくても失われない。

### 悪い結果

- `.md` を開いても、名前や形式の意味がすぐには分からないことがある。たとえば、`_n` や `_dt` の接尾辞である。
- 手で書いた内容が規則に合わないとき、アプリが受け止める処理が要る。型に合わない値を文字列のまま保つことが、その例である。

### 中立的な結果

- ADR 006 の「Markdown ファイルを正本に保つ」は変わらない。この ADR は、その上に、手で編集する場面の多さについての仮定を足す。
- 手で書くための補助をファイルに置かないので、規則の説明は `docs/properties.md` などの文書に書く。
