# ADR 011: One Request per Operation and Data-Only Events

## Status

Accepted

## Context

ADR-008は、コアの`Event::Continue(Thunk)`を維持すると決めた。`Thunk`は`FnOnce(&mut Model) -> Command`を運ぶので、`Event`はシリアライズできない。ADR-008は、見直す条件の1つに「SwiftやKotlinなど、CruxのFFIブリッジを通るシェルを作ると決めた」を挙げている。

2026-11-09に、WinUI3とSwiftUIの編集シェルを作る前提で、コアの方針を見直した。どちらのシェルもRustではなく、同じプロセスの中でコアを呼ぶ。Cruxの`Bridge`は、`Event`に`Deserialize`を、`ViewModel`に`Serialize`を求める。今の`Event`は、この条件を満たさない。

`Thunk`を作る呼び出しは、コアの19ファイルに78か所ある。`apply`が76か所、`cont`が2か所である。操作ごとに調べると、2種類に分かれた。およそ半分は、要求を1つ出して結果を受けるだけの操作である。ページの読み込み、検索、設定、折りたたみがこれにあたる。残りは、コアが複数の書き込み要求を順に出して、1つの操作を組み立てている。

後者の例を挙げる。テキストの貼り付けは、解析、1行目の更新、行ごとの作成で、N行につきN+2回の要求を出す。Enterによる分割は、更新と作成の2回である。結合と移動は、未保存の本文を先に保存してから、本体の要求を出す。Undoの同期は、記録された操作ごとに1回ずつ出す。日をまたぐ移動は、最大で4回の書き込みを出す。

この形には、`Thunk`とは別の問題がある。ADR-004により、サーバーはサービスの操作ごとに1つのトランザクションを開き、全部か無かを保証する。しかし、コアが複数の要求で1つの操作を組み立てると、この保証は利用者の操作の単位では成り立たない。貼り付けが途中で失敗すると、そこまでに作った項目がサーバーに残る。コアはUndoの記録を捨てるので、その項目はUndoで取り消せない。分割で片方の要求だけが成功すると、カーソルより後ろの文字が失われるか重複する。通知もcommitのたびに出るので、ほかのクライアントは要求の数だけページを読み直す。

サーバーには、1回の要求で済む操作がすでにある。`MergeItems`、`MoveItems`、`ShiftItemLevels`、`DeleteItems`である。貼り付け、分割、Undoの同期などが、コア側で要求を組み立てる形で残っている。この形は、移植元のAngular版から引き継いだ。Angular版のサービスは`await`の前後で状態を書き換えており、ADR-008は移植元との対応を保つために`Thunk`を導入した。

多段階の処理には、サーバーと関係のないものもある。エディターへのフォーカスの移動、確認ダイアログ、タイマーは、シェルの答えを待つ。これらは、要求を1つにまとめても残る。

## Decision

利用者の1つの操作を、サーバーへの書き込み要求1つで行う形を採用する。そのうえで、`Event::Continue(Thunk)`を廃止し、`Event`をシリアライズできるデータだけにする。

**操作を1要求にする**

- コアは、利用者の1つの操作につき、書き込み要求を1つだけ出す。サーバーは、その要求を1つのサービスの操作として、1つのトランザクションで処理する（ADR-004）。
- 貼り付け、分割、日をまたぐ移動などには、操作の意図を表す専用のAPIをサーバーに足す。項目の分け方や字下げの計算は、サーバーが受け持つ。
- Undoとredoの同期には、作成、更新、削除の列を原子的に適用する汎用のAPIを足す。任意の操作の列を送るので、専用のAPIにはしない。
- 未保存の本文は、要求に含めて送る。本体の要求の前に、保存の要求を別に出さない。
- 応答は、変更された項目をすべて返す。コアは、1つの結果でモデルを合わせ、Undoの記録を作る。
- この決まりは、項目やページへの書き込みに適用する。読み込みを続けて出すことは妨げない。画像のアップロードは項目を変えないので、この決まりの対象にしない。画像の貼り付けは、アップロードのあとに、本文を更新する要求を1つ出す。

**`Thunk`を外す**

- コマンドは、結果をデータの`Event`で返す。モデルを書き換えるのは、その`Event`を受けた`update`のハンドラだけである。
- コマンドは、複数のEffectを続けて待ってよい。フォーカスの移動や確認ダイアログのようにシェルの答えを待つ処理も、同じ形で書く。待ちの間にモデルを書き換える必要があるときは、段階ごとにデータの`Event`を定義する。
- 新しい操作では、`Thunk`を使わない。

**移行の順序**

- 一度にすべてを移さない。操作ごとに移し、進み具合は`docs/plans.md`に書く。移行中は、`Thunk`とデータの`Event`が共存する。
- 要求を1つ出して結果を受けるだけの操作は、サーバーを変えずに先に移せる。
- 多段階の操作は、サーバーにAPIを足してから移す。貼り付けから始め、Undoの同期、Enterの順に進める。
- 最後の`Thunk`を外したら、`Event::Continue`と`Thunk`の型を消す。

**このADRで決めないこと**

WinUI3とSwiftUIのシェルがコアを呼ぶ方式は、別のADRで決める。Cruxの公式のFFIブリッジを使うか、Rust側にシェルを置いて狭いインターフェースだけを見せるかの選択である。このADRは、どちらの方式も選べるように`Event`をデータにする。`shell-leptos`と`shell-emacs`は、これまでどおり`Core`を直接呼ぶ。

## Alternatives

### Alternative 1: `Thunk`を残し、シェルが送るイベントだけを公開用の型に分ける

ADR-008のAlternative 2である。78か所に触れずに、FFIを通せるようになる。作業は最も小さい。しかし、コアが複数の要求で1つの操作を組み立てる形は残る。途中で失敗したときの半端な状態も残る。`Thunk`の数は、操作を足すたびに増える。FFIの問題だけを解き、操作の原子性の問題を解かないので、選ばなかった。

### Alternative 2: サーバーを変えず、結果ごとにイベントを定義する

ADR-008のAlternative 1である。`Event`はデータになる。しかし、多段階の操作は、段階ごとのハンドラに分かれる。貼り付けのループは、イベントの連鎖になる。失敗の後始末も、段階ごとのハンドラに散る。1つ書き漏らすと、Undoが開いたまま残る。手間が大きいうえに、操作の原子性は直らないので、選ばなかった。

### Alternative 3: クロージャを、データの変種に置き換える

`apply`と`cont`に渡している78個のクロージャを、捕まえた値を持つenumの変種に変える。`async`の流れは今のまま残り、作業は機械的である。しかし、変種が78個増え、得るものは`Event`がデータになることだけである。操作の原子性は直らないので、選ばなかった。

### Alternative 4: すべての書き込みを、汎用のバッチAPIで送る

サーバーに足すAPIは1つで済む。コアは、作成、更新、削除の列を自分で組み立てて送る。原子性は得られる。しかし、項目の分け方や字下げの計算がコアに残る。RESTだけを使う外部アプリやMCPは、同じ動作を得られない。ADR-009は、動作をサーバーに寄せる方向を決めている。その方向と合わないので、Undoの同期にだけ使うことにした。

### Alternative 5: Cruxをやめ、コアを普通のRust crateにする

ADR-008のAlternative 3である。`Thunk`は不要になる。しかし、Rustでないシェルが2つ加わると、コアとシェルの間にデータの境界が要る。これは、Cruxの`Event`、`Effect`、`ViewModel`と同じものを作り直すことになる。テストの基盤である`harness.rs`も作り直しになるので、選ばなかった。

## Confidence Level

方向についての確信度は高い。細部についての確信度は中程度である。

操作を1つの要求にすることは、確信している。サーバーはすでに操作ごとに1つのトランザクションを開いており（ADR-004）、`MergeItems`や`MoveItems`という前例もある。`Event`をデータにすることは、Cruxの標準の書き方である。コアは項目のIDを自分で作れるので、応答を待たずに画面を変えることもできる。

確かめていないことが3つある。第一に、Enterの体感である。分割は、キーの引き継ぎとフォーカスの移動がからむ。1つの要求にしたあとも今と同じ速さで動くかは、作ってみないと分からない。第二に、シェルの答えを待つ処理の読みやすさである。フォーカスの移動を段階ごとの`Event`で書くと、操作が読みにくくなるおそれがある。第三に、作業の量である。78か所のうち、設計し直すとイベントがいくつになるかは、操作ごとに見ないと分からない。

次のいずれかが起きたら、この決定を見直す。

- WinUI3とSwiftUIの編集シェルを作らないと決めた。操作を1つの要求にする価値は残るが、`Thunk`を外す理由は弱くなる。
- Enterを1つの要求にした結果、入力の体感が悪くなり、直せなかった。
- 専用のAPIが増え、サーバーの保守が重くなった。汎用のAPIに寄せることを検討する。
- 段階ごとの`Event`が増え、操作の流れが追いにくくなった。
- Cruxの更新で、`Command`の書き方が使えなくなった。

## Consequences

**良い結果**

利用者の操作は、全部か無かになる。貼り付けや分割が途中で失敗しても、半端な状態がサーバーに残らない。Undoの1件は、サーバーの1つの操作に対応する。

要求の数が減る。N行の貼り付けは、N+2回から1回になる。通知も1回になり、ほかのクライアントの読み直しも1回で済む。

項目の分け方や字下げの計算は、サーバーに1つだけある。RESTを使う外部アプリやMCPも、同じ動作を得る。

`Event`はシリアライズできる。WinUI3とSwiftUIのシェルは、どの方式でもコアを呼べるようになる。結果を受けるハンドラは、待つ前に複製した値ではなく、今のモデルを読んで書き換える。

**悪い結果**

サーバーのAPIが増える。コアにある計算の一部はサーバーに移る。移行中は、同じ計算がコアとサーバーの両方にある。

コアのテストは、一部を書き直す。API呼び出しの列を確かめているテストは、新しいAPIに合わせて変わる。ハーネスの偽のAPIは、貼り付けや分割の応答を作る必要がある。偽のAPIがサーバーの動作とずれるおそれが増えるので、E2Eテストの役割が大きくなる。

`Event`の変種が増える。結果を表す内部の`Event`も同じ型に入るので、シェルから送れてしまう。

移行中は、`Thunk`とデータの`Event`が共存する。読み手は2つの形を見る。移行が終わるまで続く。

**中立的な結果**

ADR-008は、このADRに置き換わる。移植元のAngular版との行ごとの対応は、なくなる。

既存のAPIは消さない。`CreateItem`や`UpdateItem`は、外部アプリや拡張機能が使い続ける。

シェルが送る`Event`は変わらない。`shell-leptos`と`shell-emacs`は、ほぼそのまま動く。

WinUI3とSwiftUIのシェルがコアを呼ぶ方式と、`ViewModel`のシリアライズは、別のADRで決める。
