# ADR 022: Asset Files Named by HMTID

## Status

Accepted

## Context

画像などのファイルは、サーバーの`/api/assets/upload`へ送り、ノートの`assets`フォルダに保存する。本文には、`![文字](../assets/名前)`というリンクが入る。

これまでサーバーは、送られたファイルの名前を、そのまま保存する名前に使っていた。この形には、次の問題があった。

- 貼り付けた画像には、もとの名前がない。ブラウザもEmacs版も、仮に`image.png`という名前を付ける。そのため、`image-1.png`、`image-2.png`と、連番の名前が増え続けた。2026-11-10の時点で、`assets`の93ファイルのうち62ファイルが、この形の名前だった。
- ドロップしたファイルや、選んで挿入したファイルも、名前が重なると連番になる。`screenshot.png`や`IMG_0001.jpg`のような名前は、すぐに重なる。
- サーバーは、ASCIIの英数字と`.`、`_`、`-`以外の文字を`_`に替える。`構成図.png`は`___.png`になり、名前の意味が残らない。
- リンクの文字にも、保存した名前を使っていた。そのため、本文にも`image-3.png`や`___.png`が出ていた。

## Decision

2026-11-10に、ユーザーが次のように決めた。

1. サーバーは、送られたファイルを、**HMTIDと元の拡張子**でできた名前で保存する。例は`20261110090501_QZ998PX.png`である。貼り付けでも、ドロップでも、ファイルを選んでの挿入でも同じである。
2. **元の名前は、リンクの文字に残す。** 例は`![構成図.png](../assets/20261110090501_QZ998PX.png)`である。貼り付けた画像の文字は、`image.png`のままである。
3. **今あるファイルとリンクも、同じ形に変える。** HMTIDの日時には、ファイルの更新日時と作成日時のうち、古いほうを使う。手で実行するコマンドで行い、先に対応表だけを見られるようにする。

細かい決まりは、次のとおりである。

- HMTIDは、日時の部分を区切らずに書く。区切りは`_`である。ページや項目のIDは日時を`-`で区切るが、ファイルの名前は短いほうを選んだ。
- 拡張子は、元の名前の最後の`.`の後ろである。小文字にする。ないとき、またはASCIIの英数字だけでないときは、拡張子を付けず、HMTIDだけの名前にする。
- サーバーは、答えに、保存した名前（`fileName`）と元の名前（`originalName`）を入れる。リンクを作るのはコアである。
- コアは、元の名前の`[`、`]`、`\`の前に`\`を付けて、リンクの文字にする。リンクが途中で終わらないようにするためである。
- 名前が重なるかどうかは、確かめない。連番を付ける処理は消した。

## Alternatives

### Alternative 1: 日時だけの名前にする

`20261110-180501.png`のように、サーバーのローカルの日時を名前にする。短く、人が読みやすい。しかし、同じ秒に2枚を保存すると名前が重なり、連番が要る。2台のPCで同じ秒に保存しても重なる。そのため、選ばなかった。

### Alternative 2: 中身のハッシュを名前にする

同じ画像を2度貼っても、ファイルは1つで済む。しかし、名前から何も分からず、名前順に並べても貼った順にならない。そのため、選ばなかった。

### Alternative 3: 貼り付けた画像だけ名前を替え、名前のあるファイルは元の名前のままにする

変更は小さい。しかし、日本語の名前が`_`になる問題と、名前が重なると連番になる問題が残る。`assets`フォルダに、2通りの名前が混ざる。そのため、選ばなかった。

### Alternative 4: 日時と元の名前をつなぐ

`20261110-180501-photo.png`のようにする。名前に意味が残る。しかし、日本語の名前は`20261110-180501-___.png`になり、意味は残らない。名前も長くなる。そのため、選ばなかった。

### Alternative 5: サーバーの決まりを緩めて、日本語を名前に残す

名前の意味は残る。しかし、連番は残る。URL、OSの違い、フォルダの同期での扱いを、確かめ直す必要がある。そのため、選ばなかった。

### Alternative 6: 今あるファイルは、そのままにする

実際のノートを書き換えずに済む。しかし、古い名前と新しい名前が混ざり続ける。ユーザーは、今あるファイルも変えることを選んだ。

## Confidence Level

確信度は高い。HMTIDは、ページと項目のIDですでに使っている。

気がかりは、次の2点である。

- HMTIDの日時はUTCである。日本の朝8時に貼った画像は、名前では前の日の23時になる。ジャーナルの日付と、最大9時間ずれる。ページと項目のIDも同じである。
- 今あるファイルの日時は、ファイルの更新日時から作る。ファイルをコピーや同期で写したとき、更新日時が保たれていなければ、貼った日時にはならない。2026-11-10の時点では、93ファイルのうち48ファイルが2026-09-27にコピーされていたが、更新日時は元の値が残っていた。

次のときに見直す。

- `assets`フォルダを、人がファイルの名前で探すことが増えたとき。
- 画像でないファイル（PDFなど）を多く置くようになり、名前から中身が分からないことが困るとき。

## Consequences

良い結果は次のとおりである。

- 連番の名前がなくなる。保存する前に、同じ名前のファイルがあるかを調べる処理もなくなる。
- `assets`フォルダを名前順に並べると、保存した順になる。
- 日本語の名前が、リンクの文字として本文に残る。検索にもかかる。
- 2台のPCで別々に保存しても、名前は重ならない。

悪い結果は次のとおりである。

- エクスプローラーなどで`assets`フォルダを見たとき、名前から中身が分からない。
- 名前が長くなる。拡張子を入れて26文字である。
- 名前の日時がUTCなので、日本の時刻とは9時間ずれる。
- Emacs版は、リンクの文字に`[`か`]`がある画像を、画像として表示しない。リンクの文字のままになる。

中立的な結果は次のとおりである。

- アップロードの答えに`originalName`が加わる。古いシェルは、新しいサーバーの答えを読める。新しいシェルは、古いサーバーの答えを読めない。
- 今あるファイルの移行は、別のPRで行う。それまでは、古い名前と新しい名前が混ざる。
