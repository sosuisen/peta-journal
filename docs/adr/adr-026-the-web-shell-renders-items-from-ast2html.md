# ADR 026: The Web Shell Renders Items from the HTML of flatmarkdown-ast2html

## Status

Accepted

## Context

ASTを描くコードは、2つある。Webのシェルの`fm-leptos`は、ASTからブラウザのDOMを作る。`flatmarkdown-ast2html`クレートの`ast_to_html`は、ASTからHTMLの文字列を作る（ADR 020）。

ADR 025は、ネイティブのシェルが`ast_to_html`を通して項目を描くと決めた。Webのシェルを切り替えるかどうかは、決めなかった。このADRは、それを決める。

`fm-leptos`は、Angularのフロントエンドを書き換えたときに作った。Angularのレンダラー`flatmarkdown-ast2angular`と同じHTMLを出すことが、目標だった。Angularのフロントエンドは、もうない。`fm-leptos`が合わせている相手は、なくなった。

いま、`ast_to_html`を通らずにASTを描くのは、`fm-leptos`だけである。付箋紙アプリは`ast_to_html`のwasm版を使う（ADR 023）。SwiftUIのシェルは`ast_to_html`を使う（ADR 025）。Webのシェルも、「HTMLとしてコピー」では`ast_to_html`を使う。Webのシェルの中で、表示とコピーが、別のコードからHTMLを作っている。

ADR 025は、同じASTの内容が、どのシェルでも、もれなく表示されることを求めた。`fm-leptos`は、知らない種類のノードを描かない。`ast_to_html`は、知らない種類も中身を出す。Webのシェルだけが、この点で外れている。

2026-11-11に、26通りのMarkdownを`ast_to_html`に通し、`fm-leptos`のテストが期待するHTMLと比べた。段落、見出し、リスト、タスクリスト、脚注、リンクは、同じ形だった。違いは次のとおりである。

- ウィキリンクとハッシュタグ。`fm-leptos`は、シェルが渡した接頭辞とクラスを付ける。`ast_to_html`は、`href`にページ名やタグ名だけを入れる。目印は、ウィキリンクが`data-wikilink`、ハッシュタグが`class="hashtag"`である。
- 画像の大きさ。`fm-leptos`は、URLの`#w=300&h=240`を`width`と`height`にする。`ast_to_html`は、画像の`props`を意図して出さない。使い方がアプリごとに違うためである。
- アラート。`fm-leptos`は`<div>`で、`ast_to_html`は`<blockquote>`である。クラスは同じである。
- 表。`ast_to_html`は`<thead>`と`<tbody>`を付ける。
- 言語を書かないコードブロック。`fm-leptos`は`language-text`のクラスを付ける。`ast_to_html`は、クラスを付けない。
- 生のHTML。`fm-leptos`は、HTMLのノードを1つずつ`<span>`で包む。`ast_to_html`は、そのまま出す。

`ast_to_html`は、出力を変える手段を持たない。受け取るのはASTだけである。

Webのシェルには、`ast_to_html`の出力だけでは足りないことが3つある。第一に、リンクの`href`である。通常のクリックは、シェルが横取りしてページを開く。しかし、Ctrl+クリック、中クリック、右クリックのメニューは、ブラウザが`href`をそのまま使う。`href`がページ名だけだと、今のページからの相対で解決され、行き先がずれる。ハッシュタグの行き先は、設定のタグ用ディレクトリでも変わる。第二に、画像の大きさである。第三に、コードブロックの色付けである。highlight.jsは、言語のクラスがないと、言語を推測して色を付ける。

DOMを作る形から、HTMLの文字列を`inner_html`で入れる形に変えることについても、調べた。`fm-leptos`は、ASTが変わるたびに項目の表示を丸ごと作り直している。要素にイベントは付けていない。クリックは、外側の要素でまとめて受けている。生のHTMLは、今も`inner_html`で入れている。切り替えで失うものは、見つからなかった。

Webのシェルは、描画のあとにDOMを直す場所を、すでに持っている。highlight.jsを当てるところである。

コアは、別の作業で変更中である。このADRの実装では、コアを変えない。

## Decision

Webのシェルは、項目のASTを`flatmarkdown-ast2html`の`ast_to_html`でHTMLにしてから描く。HTMLの文字列は、項目の表示の要素に`inner_html`で入れる。ASTからDOMを直接作るコードは、持たない。

`fm-leptos`クレートは消す。`frontend-rust`のワークスペースから外し、フォルダごと削除する。

`ast_to_html`は変えない。オプションも足さない。Webのシェルに足りないことは、Webのシェルが補う。補う場所は、`shell-leptos`の項目の表示（`item_view.rs`）である。補うことは、次の3つである。

- リンクの`href`。描画のあと、ウィキリンク（`a[data-wikilink]`）とハッシュタグ（`a.hashtag`）の`href`に、接頭辞を付ける。ウィキリンクは`/pages/`、ハッシュタグは`/pages/`と設定のタグ用ディレクトリである。ブラウザが`href`をそのまま使う操作でも、正しいページが開く。
- 画像の大きさ。`ast_to_html`に渡す前に、ASTの画像のURLへ、`props`の`w`と`h`をフラグメントとして戻す。描画のあと、`<img>`の`src`のフラグメントを読み、`width`と`height`を付ける。数値でない値と0は、今と同じく無視する。
- コードブロックの色付け。highlight.jsは、言語のクラスがあるコードブロックにだけ当てる。言語を書かないコードブロックは、色を付けず、言語の札も出さない。

クリックの横取りとスタイルシートは、`ast_to_html`の出す目印に合わせる。ウィキリンクは`a[data-wikilink]`、ハッシュタグは`a.hashtag`で選ぶ。`wiki-link`と`hashtag-link`のクラスは、使わなくなる。

見た目は、できるだけ今のまま保つ。アラートが`<blockquote>`になっても、表に`<thead>`と`<tbody>`が付いても、今と同じに見えるように、スタイルシートを直す。

次の変化は、受け入れる。

- 生のHTMLは、`<span>`で包まれなくなる。`<b>太字</b>`のように開きと閉じを分けて書いたHTMLが、効くようになる。閉じ忘れたタグは、同じ項目の、それより後ろに及ぶ。項目の外には及ばない。
- 知らない種類のノードは、中身が表示される。
- 言語を書かないコードブロックから、`text`の札が消える。

コアは変えない。ビューモデルも変えない。項目のASTは、今と同じくJSONの文字列でシェルに届く。シェルは、それを`flatmarkdown_ast`で読み、`ast_to_html`に渡す。`flatmarkdown-ast2html`の版は、`flatmarkdown-ast`と同じ版に固定する（ADR 020）。

次のことは、このADRでは決めない。

- `ast_to_html`に、リンクや画像のオプションを足すこと
- SwiftUIのシェルで、画像の大きさを扱うこと
- 本文の中のタスクリストで、括弧の中の文字を区別して出すこと（ADR 025と同じ）

## Alternatives

### Alternative 1: `fm-leptos`を残す

今のまま、WebのシェルだけがASTからDOMを作る。

長所は、何も変えずに済むことである。リンクの接頭辞や画像の大きさを、描くときに直接付けられる。本文の文字はテキストノードになるので、エスケープを誤る余地がない。

短所は、ASTを描くコードが2つ残ることである。ASTに種類が増えるたびに、`fm-leptos`も直す。知らない種類を描かないので、ADR 025の「もれなく表示される」から、Webのシェルだけが外れ続ける。表示とコピーのHTMLも、別のコードから出続ける。合わせる相手だったAngularのレンダラーは、もうない。

残す理由が、すでにあることだけなので、選ばなかった。

### Alternative 2: `ast_to_html`にオプションを足す

`ast_to_html`が、リンクの接頭辞とクラス、画像の大きさを受け取るようにする。Webのシェルは、補う処理を持たずに済む。

長所は、シェルが単純になることである。描画のあとにDOMを直さなくてよい。

短所は、レンダラーにシェルの事情が入ることである。ハッシュタグの行き先は、設定のタグ用ディレクトリで変わる。画像の`props`の使い方は、アプリごとに違う。`ast_to_html`は、それを理由に`props`を出していない。オプションを足すと、出力の形が1つでなくなる。SwiftUIのシェルは、HTMLの形が決まっていることに頼って、文字列を置き換えている（ADR 025）。別のリポジトリの変更と、新しい版の公開も要る。

足りないことはシェルの側で補えるので、選ばなかった。

### Alternative 3: HTMLの文字列を置き換えて補う

描画のあとにDOMを直す代わりに、`inner_html`に入れる前のHTMLの文字列を置き換える。SwiftUIのシェルと同じやり方である。

長所は、ブラウザなしでテストできることである。置き換えは、文字列から文字列への関数になる。

短所は、もろさである。HTMLブロックには、書かれたHTMLがそのまま入る。そこに同じ形の文字列があると、置き換えが誤って当たる。Webのシェルには、DOMがある。要素を選んで属性を直すほうが、確かである。

SwiftUIのシェルが文字列を置き換えるのは、DOMがないためである。Webのシェルにはその制約がないので、選ばなかった。

### Alternative 4: コアがHTMLを作り、ビューモデルに入れる

ADR 025のAlternative 4と同じである。コアが`ast_to_html`を呼び、項目ごとのHTMLをビューモデルに入れる。

長所は、どのシェルも同じHTMLを受け取ることである。

短所も、ADR 025と同じである。ビューモデルが大きくなり、コアの変更が要る。コアは、別の作業で変更中である。

ADR 025と同じ理由で、選ばなかった。

## Confidence Level

確信度は、高い。

確信が高いのは、`ast_to_html`に切り替えることである。ASTを描くコードが1つになり、種類の網羅を、Rustのコンパイルが保証する。ネイティブのシェル、付箋紙アプリ、コピーが、すでに同じコードに頼っている。`inner_html`に変えて失うものも、見つからなかった。`fm-leptos`は、項目の表示を毎回作り直し、要素にイベントを付けず、生のHTMLをすでに`inner_html`で入れている。

確信がやや低いのは、補う処理の作りである。心配は3つある。

- 見た目の違い。HTMLを比べたのは、26通りのMarkdownである。実際のページを画面に出して比べては、まだいない。アラートや表で、スタイルシートの当たり方が変わるかもしれない。
- 画像の大きさ。URLのフラグメントに戻してから読む、という回り道をする。元のURLが自分のフラグメントを持つ画像で、正しく動くかは、作って確かめる。
- テスト。補う処理は、DOMを直す。`fm-leptos`の13件のテストは、ブラウザなしで動いていた。補う処理のテストは、ブラウザが要る。

次のときに、この決定を見直す。

- `ast_to_html`の出力に、DOMを直すだけでは補えない不足が見つかったとき。見直す先は、`ast_to_html`にオプションを足す形（Alternative 2）である。`fm-leptos`には戻さない。
- 補う処理が増え続けたとき。3つを大きく超えるなら、シェルごとに同じ補いを書いていないかを見る。同じものがあれば、`flatmarkdown-ast2html`の側に移すことを考える。
- 長いページで、表示が遅くなったとき。HTMLの文字列を作り、ブラウザに解析させる形は、DOMを1つずつ作る形より速い見込みである。しかし、測ってはいない。
- WinUI3のシェルが、HTMLを自分で読むことになったとき（ADR 025）。そのときに、画像の大きさをどこで扱うかを、シェルをまたいで決め直す。

`fm-leptos`を消しても、戻すことはできる。Gitの履歴に残る。ただし、戻すときは、ASTの今の版に合わせて直す必要がある。

## Consequences

### 良い結果

ASTを描くコードが、1つになる。`flatmarkdown`の版を上げてASTに種類が増えても、Webのシェルのコードを直さずに出る。知らない種類も、中身が出る。ADR 025の「もれなく表示される」に、Webのシェルも合う。

Webのシェルの表示と、「HTMLとしてコピー」のHTMLが、同じコードから出る。付箋紙アプリとSwiftUIのシェルとも、同じである。HTMLの出力を直すと、すべてに同時に届く。

`fm-leptos`クレートがなくなる。約400行のレンダラーと、13件のテストを、保たなくてよくなる。合わせる相手のないAngularの形も、なくなる。

`<b>太字</b>`のようなインラインのHTMLが、効くようになる。CommonMarkの本来の動きである。

`ast_to_html`は、1つの形のままである。SwiftUIのシェルの文字列の置き換えは、影響を受けない。

コアを変えない。ビューモデルも変えない。

### 悪い結果

Webのシェルが、補う処理を持つ。リンクの`href`、画像の大きさ、コードブロックの色付けの3つである。`ast_to_html`の出す目印（`data-wikilink`、`class="hashtag"`）が変わると、補う処理とスタイルシートが効かなくなる。

リンクの`href`は、描画の直後の一瞬、接頭辞のない値である。補う処理が動くまでの間である。

画像のURLに、大きさのフラグメントが付く。`<img>`の`src`が、ASTのURLと同じでなくなる。

エスケープを、`ast_to_html`に頼る。今は、本文の文字がテキストノードになるので、誤る余地がない。切り替えのあとは、`ast_to_html`のエスケープに誤りがあると、表示が壊れる。

閉じ忘れたHTMLのタグが、同じ項目の、それより後ろに及ぶ。今は、タグごとの`<span>`の中で終わる。

テストが、ブラウザを要するものに寄る。`fm-leptos`のテストは、ブラウザなしで動いていた。HTMLの形のテストは、`flatmarkdown-ast2html`の側にあるので、書き直さない。補う処理のテストは、新しく書く。

言語を書かないコードブロックから、`text`の札が消える。

### 中立的な結果

スタイルシートとクリックの横取りのセレクタが変わる。`wiki-link`と`hashtag-link`のクラスは、なくなる。表示のDOMに頼るE2Eテストは、直す。

アラートは`<blockquote>`に、表は`<thead>`と`<tbody>`を持つ形になる。見た目は、スタイルシートで今と同じに保つ。

`shell-leptos`は、`flatmarkdown-ast2html`にすでに依存している。依存は増えない。`fm-leptos`への依存がなくなる。

`docs/features.md`、`BUILD.md`、カバレッジの設定から、`fm-leptos`の記述を外す。構成図（`docs/frontend-architecture.svg`）も直す。

`ast_to_html`にオプションを足すこと、SwiftUIのシェルで画像の大きさを扱うことは、それぞれ別に決める。
