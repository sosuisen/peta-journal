# ADR 038: Atlas Folder with the Crate and the Scripts

## Status

Accepted

## Context

アトラスは、書く側と描く側の2つでできている。書く側は、クレート`peta-atlas`である。`index_atlas`のアウトラインを読み、シーンのJSONを書く。描く側は、`atlas.js`である。シーンのJSONを読み、PixiJSで描く。シーンのJSONは、この2つの間の約束である。

ADR 003は、クレートを`atlas-rust/`に置くと決めた。描く側は、Web版のシェルのクレートの中にあった。`atlas.js`は`src/components/`に、PixiJSなどのライブラリは`vendor/`にあった。

sosuisen.netは、アトラスをサイトに描くために、この2か所を使っている。クレートにはパス依存で頼り、`atlas.js`と`pixi.min.js`はシェルのクレートからコピーしている。2026年11月に、シェルのクレートの名前を`shell-leptos`から`client-shell-leptos`に変えた（ADR 037）。サイトのコピーは、古い場所を見ていたので止まった。

ここから、2つの問題が見える。1つ目は、サイトが、シェルのクレートの場所に頼っていることである。サイトが要るのはアトラスを描くスクリプトであり、シェルではない。2つ目は、約束の両側が別の場所にあることである。ADR 003は、クレートを将来別のリポジトリに切り出す前提を置いた。今の形で切り出すと、描く側はPetaJournalに残り、約束の片側だけが出ていく。

## Decision

フォルダー`atlas-rust/`を`atlas/`に改名し、アトラスを描くスクリプトを`atlas/web/`に置く。

- `atlas/src/`は、クレート`peta-atlas`のRustのコードである。場所は変えない。パッケージの名前も変えない。
- `atlas/web/atlas.js`は、シーンを描くスクリプトである。
- `atlas/web/pixi.min.js`、`atlas/web/pixi-ui.js`、`atlas/web/tweedle.umd.js`は、`atlas.js`が使うライブラリである。

`pixi-ui.js`と`tweedle.umd.js`は、アトラスの編集のためのもので、表示だけのページは使わない。それでも、`pixi.min.js`と一緒に置く。3つは版が組になっているためである。

（2026-11-29）`pixi-ui.js`と`tweedle.umd.js`は、置かなくなった。メニューはPixiJSだけで描き、テキストのダイアログは、キャンバスを描くページのHTMLになったためである（ADR 053、#1303）。`atlas/web/`のライブラリは`pixi.min.js`だけである。

`highlight.min.js`と`highlight-github.css`は、アトラスと関係がない。シェルのクレートの`vendor/`に残す。

Web版のシェルは、`index.html`から`../../../atlas/web/`のスクリプトを読む。Trunkは、クレートの外のスクリプトも、名前にハッシュを付けて`dist`に入れる。sosuisen.netは、`atlas/web/`からスクリプトをコピーする。

フォルダーの名前から`-rust`を取るのは、中身がRustだけではなくなるためである。

ADR 003の、クレートを独立した形に保つ決まりは、そのまま続く。切り出すときは、`atlas/`を履歴ごと新しいリポジトリにする。描く側も一緒に付いていく。

## Alternatives

### Alternative 1: スクリプトをシェルのクレートに残し、サイトのコピー元だけを直す

サイトの`ATLAS_SCRIPT_SOURCE_DIR`を、新しいクレートの場所に書き換える。変更は最も小さい。しかし、サイトは、シェルのクレートの場所と中の構成に頼り続ける。シェルを次に動かしたときに、また止まる。約束の両側が別の場所にある問題も残る。そのため選ばなかった。

### Alternative 2: スクリプトを`frontend-rust/assets/`のような共有のフォルダーに置く

シェルのクレートの外で、フロントエンドのワークスペースの中に置く。Trunkから読む道は短くなる。しかし、クレート`peta-atlas`は、フロントエンドのワークスペースの外にある。約束の両側は、やはり別の場所になる。切り出すときにも、描く側は付いていかない。そのため選ばなかった。

### Alternative 3: スクリプトをクレートに埋め込み、Rustから書き出す

`include_str!`で`atlas.js`をクレートに入れ、使う側が関数から受け取る。使う側は、クレートだけに頼ればよい。しかし、Trunkは`index.html`の`script`からファイルを読む。埋め込んだ文字列を渡す道がなく、ビルドの前に書き出す手順が増える。`pixi.min.js`は大きく、表示しない使い方（サーバー）のビルドにも入る。そのため選ばなかった。

## Confidence Level

高い。動かすのはファイルの場所だけで、コードの振る舞いは変わらない。Trunkがクレートの外のスクリプトを読めることは、ビルドして確かめた。

次の状況になったら見直す。

- アトラスのほかにも、PixiJSを使う画面がWeb版にできたとき。`pixi.min.js`がアトラスだけのものではなくなる。
- `atlas.js`をモジュールやnpmのパッケージとして配ることになったとき。`web/`の形を決め直す。
- クレートを別のリポジトリに切り出すとき。ADR 003と一緒に、このADRも見直す。

## Consequences

良い結果。シーンのJSONを変えるときに、書く側と描く側を同じフォルダーの中で、1つのPRで変えられる。サイトは、`atlas/`だけに頼る。シェルのクレートを動かしても、サイトは止まらない。切り出すときに、描く側も履歴ごと付いていく。

悪い結果。Web版のシェルの`index.html`が、ワークスペースの外のファイルを読む。シェルのクレートだけを見ても、スクリプトの場所は分からない。フォルダーの名前が変わるので、パス依存を持つ3つの`Cargo.toml`と、サイトの側の設定を直す必要がある。サイトの側を直すまで、サイトの`npm run sync`は道具をビルドできない。

中立的な結果。`atlas/web/`のファイルは、クレートのビルドには入らない。Cargoは`web/`を読まない。PixiJSを新しくする手順は、`BUILD.md`のアトラスの節に書く。ADR 003が書いた`atlas-rust/`というパスは、このADRで`atlas/`に変わる。ADR 003は、書いた時点の記録として書き換えない。
