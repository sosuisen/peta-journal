# ADR 021: The Server Keeps Every Page Non-Empty

## Status

Accepted

## Context

ページは、項目を1つ以上持つ。項目が0個のページには、カーソルを置く場所がない。画面は、項目のエディタに入力する作りなので、0個のページでは何も書けない。

この約束を守る処理は、これまでコアにあった。コアは、選択範囲の削除やUndoのあとに、画面のページの項目が0個なら、空の項目を1つ作る要求を別に出していた。

この形には、3つの問題があった。

- 約束を守るのが、Web版とEmacs版が使うコアだけだった。MCP、拡張アプリ、`curl`などのクライアントが最後の項目を消すと、0個のページがサーバーに残った。
- 削除と作成が、別の要求だった。削除が済んで作成が失敗すると、0個のページが残った。1つの操作は1つの書き込み要求で行う、というADR 011の決まりにも合わなかった。
- コアが見るのは、画面のページだけだった。トランスクルージョンの元のページのように、画面にないページが0個になっても、気づけなかった。

2026-11-10に、ユーザーが次のように決めた。「ページは項目を1つ以上持つ」は、データの約束である。守るのは、クライアントではなく、サーバーである。

## Decision

ページを空にしない約束は、サーバーが守る形を採用する。

- サーバーは、項目を消す入口のすべてで、項目がなくなったページに、空の項目を1つ作る。削除と同じトランザクションで作る（ADR 004）。
- 入口は、単体の削除（`DELETE /api/items/{id}`とMCP）、グループ削除（`POST /api/items/delete`）、バッチ（`POST /api/items/batch`）、日をまたぐ移動（`POST /api/journals/{date}/move`）である。
- バッチでは、削除だけでなく、移動で項目がなくなったページにも作る。バッチが触れたページをすべて見る。
- グループ削除とバッチは、作った項目を答えの`created`に入れる。コアは、画面のページに作られた項目だけを表示する。
- 単体の削除とMCPは、答えを変えない。開いているクライアントには、ページの変更の知らせが届く。
- コアは、空の項目を作る要求を出さない。0個かどうかも調べない。

## Alternatives

### Alternative 1: コアが守り続ける

コアが、削除のあとに空の項目を作る。サーバーは変えなくてよい。しかし、コアを使わないクライアントは約束を破れる。削除と作成が別の要求なので、片方だけが済むことがある。そのため、選ばなかった。

### Alternative 2: サーバーが、最後の項目の削除を断る

サーバーは、ページの最後の項目を消す要求を断る。約束は破れない。しかし、ページの文をすべて選んで消す操作ができなくなる。クライアントは、消す前に空の項目を作るか、最後の項目を空にする処理を、それぞれ持つことになる。そのため、選ばなかった。

### Alternative 3: 0個のページを認め、画面が空のページを扱う

約束そのものをやめる。サーバーは何もしなくてよい。しかし、シェルごとに、項目のないページへ入力する手段を作る必要がある。シェルは、Web版、Emacs版に加えて、WinUI3版とSwiftUI版を予定している。そのため、選ばなかった。

## Confidence Level

確信度は高い。データの約束を、データを持つ側が1か所で守る形である。

次のときに見直す。

- 項目を消す入口や、項目をほかのページへ動かす入口を、サーバーに足したとき。その入口でも、同じ処理を呼ぶ必要がある。
- 項目のないページを、画面で扱えるようにしたとき。

## Consequences

良い結果は次のとおりである。

- どのクライアントが消しても、0個のページは残らない。
- 削除と空の項目の作成が、1つのトランザクションになる。片方だけが済むことはない。
- 画面にないページが空になっても、サーバーが空の項目を作る。
- コアから、0個を調べる処理（`ensure_at_least_one_item`）と、そのための要求がなくなった。

悪い結果は次のとおりである。

- 項目を消した数と、ページから減った数が合わないことがある。最後の項目を消すと、項目は1個のままである。APIを使う側は、このことを知っている必要がある。
- 新しい入口を足すときに、この処理を呼び忘れると、約束が破れる。型では防げない。入口ごとのテストで守る。

中立的な結果は次のとおりである。

- 結合（`POST /api/items/merge`）は、受け取る項目が残るので、ページは空にならない。
- 別のページへの移動（`POST /api/items/move`）で元のページが空になる場合は、確かめていない。`docs/plans.md`に、未確認の点として書いてある。
- ページの項目をすべて消した直後に、残った空の項目へフォーカスを置く処理は、このADRの対象ではない。`docs/plans.md`のタスクである。
