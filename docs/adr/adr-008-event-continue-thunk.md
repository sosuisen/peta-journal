# ADR 008: Event::Continue(Thunk) for Rust Shells

## Status

Accepted

## Context

`frontend-rust`のコアはCruxで書いている。Cruxの`update`は同期処理で、非同期コマンドはモデルに触れない。公式ドキュメントは、これを意図的な設計と説明している。コマンドの結果は、`Event`で`update`に戻す。

一方、移植元のAngular版のサービスは、`await`の前後で状態を書き換える。分割や移動などの操作は、この順序に依存している。結果ごとに内部イベントを定義すると、1つの操作が複数のハンドラに分かれ、移植元との対応が追いにくくなる。そこで、移植では`Event::Continue(Thunk)`を導入した。`Thunk`は`FnOnce(&mut Model) -> Command`を運ぶ。コマンドはこれを`apply`で送り、`update`がその場で実行する。

この方式はデータ競合を起こさない。しかし、Cruxの流儀からは外れている。Cruxの想定する`Event`は起きたことを表すデータだが、`Thunk`は実行するコードそのものである。その結果、`Event`はシリアライズできない。Cruxの公式FFIブリッジはメッセージをシリアライズするので、SwiftやKotlinのシェルは今の`Event`をそのまま送れない。

2026-11-06の時点で、シェルは2つある。`shell-leptos`はRustから`Core`を直接呼ぶ。開発中の`shell-emacs`もRustプロセスで、`peta-core`に直接依存する。Emacsとの間は独自のJSON Linesでやり取りする。どちらもFFIブリッジを通らない。

## Decision

`Event::Continue(Thunk)`を維持する。コアの非同期コマンドは、モデルの更新を`apply`で`update`に送る。

シェルは、コアと同じRustプロセスに置き、`Core`を直接呼ぶ。コアとシェルの間にシリアライズの層を入れない。シェルが外部のプログラムと通信する場合は、そのシェルが独自の形式を定義する。`shell-emacs`のJSON Linesがこの例である。

新しい操作でも`Thunk`を使ってよい。API待ちをはさまない単純な更新は、これまでどおり通常の`Event`で書く。

## Alternatives

### Alternative 1: 結果ごとに内部イベントを定義する

Crux公式の書き方である。コマンドは結果をデータの`Event`で返し、`update`の各ハンドラがモデルを更新する。`Event`はシリアライズできるようになり、FFIブリッジも通せる。しかし、1つの操作が複数のハンドラに分かれ、移植元との対応が追いにくくなる。既存の操作をすべて書き直す作業も大きい。今のシェルはこの利点を必要としないので、選ばなかった。

### Alternative 2: シェルが送るイベントだけを公開用の型に分ける

シリアライズできる公開用のイベント型を別に作り、`Thunk`はコアの内部に残す。既存の操作を書き直さずに、FFIブリッジへの道を開ける。しかし、今はこの型を使うシェルがない。使われない層を保守することになるので、今は選ばなかった。FFIブリッジを通るシェルが必要になったら、この案を最初に検討する。

### Alternative 3: Cruxをやめ、コアを普通のRust crateにする

API用のtraitをコアに注入する。`Thunk`は不要になり、Effectの定型コードも減るはずである。同じ程度にテストもできる。しかし、移植は完了しており、置き換えても機能は増えない。テストの基盤である`harness.rs`も作り直しになる。費用に見合わないので、選ばなかった。

## Confidence Level

確信度は中程度である。

今の2つのシェルに実害がないことは、確信している。どちらも`Core`を直接呼び、シリアライズできない`Event`の影響を受けない。一方、`shell-emacs`はまだ開発中であり、最後まで問題が出ないことは確かめていない。また、`Thunk`の使用が増えたときの保守のしやすさも、まだ評価していない。

次のいずれかが起きたら、この決定を見直す。

- SwiftやKotlinなど、CruxのFFIブリッジを通るシェルを作ると決めた。
- Cruxの更新で、`Thunk`や`Command`の書き方が使えなくなった。
- `Thunk`のせいで、操作の順序に関する不具合やテストの書きにくさが繰り返し起きた。

## Consequences

**良い結果**

移植元の処理順を保ったまま、操作を1つの流れとして読める。既存の操作を書き直す必要がない。新しいRustシェルは、コアに手を入れずに`Core`を直接呼べる。`shell-emacs`はこの形で作れる。

**悪い結果**

`Event`をシリアライズできないので、CruxのFFIブリッジを通るシェルはそのままでは作れない。`Event`はデータとして比較できないので、`Thunk`の中身はイベントの値では検証できない。テストは`harness.rs`で操作を実行し、結果のモデルや要求されたEffectを確かめる必要がある。`Thunk`の実行前に別のイベントが処理されることはあるので、API待ちの前後でモデルが変わる可能性は、各操作が考慮しなければならない。

**中立的な結果**

シェルが外部のプログラムと通信する場合、形式はシェルごとに定義する。Crux公式の型生成は使わない。FFIブリッジを通るシェルが必要になったら、Alternative 2を新しいADRで検討する。
