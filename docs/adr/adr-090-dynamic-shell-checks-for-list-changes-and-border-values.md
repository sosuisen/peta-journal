# ADR 090: Dynamic Shell Checks for List Changes and Border Values

## Status

Accepted

## Context

### ADR 064の静的なチェックが見ない種類の問題がある

ADR 064は、シェルがコアに任せるべき処理を自分で行う問題を、3つの種類に分けた。

1. シェルが、`Event`を通らずに、コアの関数や型を直接使って判断する。
2. OSの部品が、ある操作を自分で処理し、シェルがそれを奪っていない。
3. シェルが、コアを一切使わずに、自前の値で判断する。

ADR 064は、これらをソースを読む静的なチェック（S1からS4）で確かめると決めた。

もう1つ、別の種類の問題がある。

4. シェルが、コアが送る値を、コアと違う意味で扱う。

たとえば、差分を当てる処理が、あるシェルだけ`Move`の向きを誤る。
生成された型の読み書きが、型の名前や形を変えたときに、あるシェルだけ壊れる。
種類4では、シェルはコアを通っているので、静的なチェックでは見つからない。
処理を実際に回し、結果をコアと比べる必要がある。

### 差分の型は、これから大きく変わる

ADR 088で、並びの差分の型を`list_change!`マクロで作り、アウトラインの行の差分を`ListChange`から`RowChange`にすると決めた。
続けて、見出し、最近のページとフォルダのページ、検索の結果を差分にする（#1200から#1203）。
#1200では、5か所にある差分を当てる処理を、要素の型を問わない形に書き換える。
書き換えの前に、どのシェルも同じ結果を返すことを確かめる仕組みが要る。

### 境界の値は、シェルの種類ごとに形が違う

境界の値の形は、次のとおりである。

| シェル | 境界 | 形 |
|---|---|---|
| Web | `client-web-bridge`の`Changes<HtmlBody>` | facetのJSON |
| Android、iOS、macOS、Windows | `client-native-bridge`の`Changes<RichText>` | bincode（`facet_generate`の`BincodePlugin`） |
| Emacs | `apps/emacs/outliner`のRustとLispの間 | facetのJSON Lines（ADR 078） |

EmacsのRustの部分は、コアのRustの型を直接使う。
Lispの部分は、Rustが送る行（`Outbound`）を、Rustの型から書いた関数で読む（`lisp/peta-journal-protocol.el`）。
Lispが送る行（`Inbound`）には、生成されたものがない。
Lispが、手書きのキーで行を作る。

## Decision

### shell-checkを、静的な系統と動的な系統に分ける

shell-checkのチェックを、2つの系統に分ける。

| 系統 | 確かめ方 | チェック | 効く種類 |
|---|---|---|---|
| S（静的） | シェルのソースを読む | S1 依存の許可リスト、S2 `Event`の参照、S3 OSの編集コマンド、S4 関数の分岐の数（ADR 064） | 1、2、3 |
| D（動的） | コアが作った例を、各シェルのテストで回す | D1 差分を当てた結果、D2 境界の値の読み書き | 4 |

D系統のチェックは、ADR 089の共通のテストとして置く。
例の作り方、各シェルの義務、テストのテスト、まだのシェルの`pending`は、ADR 089に従う。

### D1. 差分を当てた結果が、コアと同じ

コアは、差分の例を作る。
各例は、前の並び、差分、当てたあとの並びを持つ。
差分は、コアの`list_changes`で、前の並びとあとの並びから作る。
例には、`Insert`、`Remove`、`Move`、`Update`、`Reset`のそれぞれと、それらを続けて当てる組み合わせを含める。
並びの先頭、末尾、空の並びへの例も含める。

例の要素は、境界に出る本物の型にする。
今は`ListChange`（`Row`の差分）で、#1200のあとは`RowChange`、#1201から#1203のあとは`HeadingChange`、`PageChange`、`SearchChange`も加わる。
本物の型にするのは、Swift、Kotlin、C#の、型ごとの橋渡し（ADR 088）も一緒に確かめるためである。
並びの型ごとに、例のファイルの節を分ける。

各シェルは、自分の差分を当てる処理で、前の並びに差分を当て、あとの並びと同じかを確かめる。

### EmacsのD1. Lispが、行の差分をバッファに当てる

Emacsのシェルで行の差分を当てるのは、Lispである（#1215で決めた）。
Rustの部分は、コアの`list_changes`で差分を作り、`rows`の行としてLispへ送るだけである。
Lispは、差分を、自分の持つ行の並びと、バッファの両方に当てる（`peta-journal--apply-rows`）。

EmacsのD1は、共通のテスト`list-changes`をそのまま使い、`list-changes.json`の`emacs`の節を読む。
前の並び、差分、あとの並びは、コアの例（`row_examples`）のままである。
形だけを、Emacsの境界に合わせる。
Emacsに届く行は、`RowView`で、本文は`EmacsText`である（ADR 078）。
`web`の節の行（`HtmlBody`）も、`native`の節の行（bincode）も、Lispは読めないからである。

`emacs`の節を書くのは、`outliner-emacs`のRustである。
D2と同じく、境界の型を持つのが、このクレートだからである。
前の並び、差分、あとの並びは、それぞれ、Rustが実際に書く`rows`の行の文字列にする。
前の並びとあとの並びは、`native`の節と同じく、`Reset`にする。
節が古くなっていないかは、同じクレートの`cargo test`が確かめる。

LispのテストはERTで回る。
前の並びの行と、差分の行を、シェルのプロセスから届いたときと同じ入口（`peta-journal--read-output`）に渡す。
そのうえで、次の3つを、あとの並びと比べる。

- Lispが持つ行の並び（`peta-journal--rows`）。
- バッファの行のidの並び。行頭の印の文字のプロパティから読む。
- バッファの文字と、その見た目。あとの並びをその場で描いたものと比べる。

最後に、回した例のidの一覧が、ファイルの一覧と同じかを確かめる。

### D2. 境界の値を読んで書き直すと、元に戻る

コアは、境界の値の例を作る。
例は、`Changes`と`Event`の値を、境界の形にしたものである。
Webの境界はJSONで、ネイティブの境界はbincodeのバイト列である。
バイト列は、JSONのファイルの中に16進の文字列で書く。

各シェルは、生成された型で例を読み、書き直し、元と同じ形になるかを確かめる。
Webの例とネイティブの例は、別のファイルにする。
各シェルは、自分の境界の例のファイルを読む。

### EmacsのD2. Rustが送るすべての種類の行を、Lispが誤りなく読む

EmacsのD2は、Lispの部分が境界の値を読む処理を対象にする（#1230で決めた）。
Emacsの境界は、`client-web-bridge`の境界でも`client-native-bridge`の境界でもない。
そこで、Emacsだけの共通のテスト`border-emacs`を置き、例のファイルを`border-emacs.json`にする。

例を作るのは、コアではなく、`outliner-emacs`のRustである。
境界の型（`Outbound`）を持つのが、このクレートだからである。
例は、`Outbound`のすべての変種の行で、それぞれidを持つ。
行は、Rustが実際に書く文字列（`write_line`の結果）のまま、ファイルに書く。

例の値は、ほかの境界と同じく、コアの見本（`samples.rs`）から作る。
型の記述から作るので、`Outbound`に変種を足せば、その例が自動で加わる。
`Outbound`から届くすべての列挙型の、すべての変種も、例に入る。
例のファイルが古くなっていないかは、同じクレートの`cargo test`が確かめる。

ただし、数は、端の値ではなく、すべて1にする（`small_samples`）。
Lispは、読んだ行をその場でバッファに当てる。
端の値（`u32::MAX`など）は、どの行も、どの文字も指さないので、読み方が正しくても誤りになる。
1にするのは、2行以上の並びの中の位置になり、1から数える値（行のレベルなど）にもなるからである。
0では、行のレベルが0になり、字下げを作れずに誤りになった。
WebとネイティブのD2は、値を当てずに読んで書き直すだけなので、端の値のままにする。

文字は、ふつうの見本と同じものを使う（`TEXTS`の5つ）。
例のファイルは、この5つを`texts`の節に持つ。

LispのテストはERTで回る。
テストは、どの例も、`texts`の文字をidに持つ5つの行を表示したバッファから始める。
例の数（1）と文字が、ある行を指すようにするためである。
たとえば、`focus`と`scroll`の例のidは、この行のどれかを指し、ポイントが実際に動く。
そのうえで、例の行を、シェルのプロセスから届いたときと同じ入口（`peta-journal--read-output`）に渡す。
確かめるのは、次の3つである。

- 誤りが出ない。
- 行の種類の関数が、ちょうど1回呼ばれる。
- 行の値を見せる一覧（プロパティ、サイドバー、バックリンク、検索の結果）を、誤りなく描ける。

最後に、回した例のidの一覧が、ファイルの一覧と同じかを確かめる。

ほかのシェルのD2と違い、「読んで書き直すと元に戻る」は確かめない。
Lispは`Outbound`を書かないので、書き直すものがないからである。

### EmacsのD2は、Lispが送る行（`Inbound`）を対象にしない

Lispは、`Inbound`の行を、手書きのキーで作る。
Rustの型から生成されたものがLispの側になく、例と比べる相手がない。
Rustが`Inbound`の例を書いても、それを読むのはRustだけで、Lispの書く行は通らない。
Lispの書く行が正しいかは、ERTの各コマンドのテスト（送った行を確かめる）と、本物のシェルに行を送るE2Eのテストが見る。
`rules/core.toml`の`border-emacs`の説明に、この理由を書く。

ほかのシェルの`rules/<シェル>.toml`は、`border-emacs`を`excluded`にする。
自分のブリッジの境界を読み、EmacsのJSON Linesを読まないからである。

### 置き場所

- 例のファイルは、`client/tools/shell-check/common/`に置く。D1は`list-changes.json`、D2は`border-web.json`、`border-native.json`、`border-emacs.json`である。
- 例を作るのは、コアの側のコマンドである。`client-web-bridge`と`client-native-bridge`の、境界の型を持つクレートで作る。`border-emacs.json`と、`list-changes.json`の`emacs`の節は、同じ理由で`outliner-emacs`のクレートで作る。
- 例が古くなっていないかを確かめるテストは、例を作るクレートの`cargo test`に置く。
- `rules/core.toml`に、共通のテストとして`list-changes`、`border-web`、`border-native`、`border-emacs`を書く。
- shell-checkは、Emacsのシェルに限り、Lispのテストのファイル（`.el`）を共通のテストとして受け付ける。

### 順

D1とD2を、#1200（行の差分を`RowChange`にする）の前に入れる。
#1200で差分を当てる処理を書き換えても、全シェルの結果が変わらないことを、D1で確かめるためである。
#1200で生成される型の名前が変わっても、読み書きが壊れないことを、D2で確かめる。

## Alternatives

### Alternative 1: 種類4も静的なチェックで見る

たとえば、差分を当てる処理の分岐を、ソースから数える。
長所は、ADR 064のS系統と同じ形で、シェルのテストを書かなくてよいことである。
短所は、処理が正しいかは、ソースからは分からないことである。
種類4は振る舞いの問題なので、回して比べるほうを選んだ。

### Alternative 2: Webのe2eで確かめる

Playwrightのe2eで、アウトラインを実際に動かして確かめる。
長所は、画面まで通して確かめられることである。
短所は、Webのシェルしか見ないことと、今はCIで回らないことである（#1083）。
e2eは、`docs/verification.html`の「テスト」の列の話として、これとは分けて決める。

### Alternative 3: D2を置かず、D1だけにする

長所は、例のファイルとシェルのテストが半分になることである。
短所は、#1200のように生成される型の名前や形が変わったとき、読み書きの壊れを各シェルのほかのテストに頼ることである。
生成されたコードは各シェルのソースの外にあり、各シェルのテストが確かめているとは限らないので、D2も置く。

## Confidence Level

中くらい。
D1は、`list_changes`と、5か所の当てる処理がすでにあるので、作れることは確かである。
D2は、bincodeのバイト列を、各言語の生成されたコードで同じに書き直せるかを、まだ確かめていない。
EmacsのLispでは、D2をERTで回せた（#1230）。
ただし、EmacsのD2が見るのは、誤りと、関数に届いたかである。
Lispが値を読み違えても、誤りにならず、違う表示になるだけの場合は、見つからない。

次のときは見直す。

- D2で、生成されたコードの読み書きが元に戻らない例が、言語の性質（数の型、文字列の正規化）から避けられないと分かったとき。
- 種類4の問題が、D1とD2の外で見つかったとき。D3を足すかを決める。

## Consequences

### 良い結果

- #1200から#1203で差分を当てる処理を書き換えても、全シェルが同じ結果を返すことを確かめられる。
- 生成される型を変えたとき、読み書きが壊れたシェルのテストが落ちる。
- shell-checkの体系が、静的なS系統と動的なD系統に整理される。

### 悪い結果

- #1200の前に、6つのシェルのテストと、例を作るコマンドを足す作業が入る。
- 例のファイルが4つ、リポジトリに入る。コアや境界の型を変えるPRに、例の差分が混ざる。
- Emacsの例は、値のない場合（`page_id`のない`rows`など）を持たない。見本は、浅いところでは、省ける値に必ず値を入れるからである。
- Emacsの例の範囲は1から1までで、文字を含まない。見た目やリンクは、どの文字にも付かずに読まれる。
- EmacsのD1は、バッファの文字を、Lispの描く処理（`peta-journal--row-string`）の結果と比べる。描く処理の誤りは見つからない。
- EmacsのD1の例の行は、コアの例のとおり、日付の見出しも、タスクも、字下げも持たない。日付の見出しのある行は、バッファで2行になるが、その並びは例にない。

### 中立的な結果

- `docs/verification.html`の「shell-check」の表に、D1とD2の行を足す。
- `client/tools/shell-check/README.md`に、D系統と`common/`の説明を足す。
