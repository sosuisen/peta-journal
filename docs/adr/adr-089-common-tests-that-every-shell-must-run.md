# ADR 089: Common Tests That Every Shell Must Run

## Status

Proposed

## Context

### シェルは、同じ振る舞いをそれぞれの言語で書いている

`client-core`の上で、6つのシェルが動く。
Web（`outliner-react`、TypeScript）、Emacs（`outliner-emacs`、Rust）、Android（`outliner-android`、Kotlin）、iOS（`outliner-ios`、Swift）、macOSの付箋紙（`stickies-mac`、Swift）、Windowsの付箋紙（`stickies-win`、C#）である。
判断はコアが行う（ADR 057）が、コアが送る値を受けて扱う処理は、シェルがそれぞれの言語で書く。
たとえば、差分を当てる処理である（ADR 076、ADR 088）。
Webは`screen.ts`、Androidは`Applied.kt`、iOSとmacOSは`swift-shared`の`Applied.swift`、Windowsは`PetaBorder/ListChanges.cs`、Emacsは`apps/emacs/outliner/src/protocol.rs`に書いている。
生成された型の読み書き（ADR 078、ADR 080）も、言語ごとに生成されたコードが行う。

これらの処理は、どのシェルでも同じ結果にならなければならない。
同じ差分を当てて違う並びになれば、そのシェルの画面だけが壊れる。

### 今のテストでは、シェルの間の食い違いが見つからない

各シェルのテストは、そのシェルが自分で書いた例を使う。
たとえば、`screen.test.ts`、`AppliedTests.swift`、`AppliedTest.kt`、`AppliedTests.cs`は、それぞれ別の例で差分を当てている。
例が違うので、あるシェルだけが`Move`の扱いを誤っても、ほかのシェルのテストとは比べられない。
コアが差分の作り方を変えても、シェルの例は古いまま通り続ける。

ADR 064は、シェルがコアを通っているかを、ソースを読む静的なチェック（S1からS4）で確かめると決めた。
静的なチェックは、シェルが判断を持っていないかを見る。
シェルが、コアが送る値を正しく扱うかは見ない。

### 共通のテストには、テストのテストが要る

共通の例をコアが作り、各シェルがそれを回せば、食い違いを見つけられる。
しかし、例を回すテストは各シェルが書く。
次のときに、誰も気づかない。

- あるシェルが、そのテストを書いていない。
- テストはあるが、テストの段がシェルのジョブ（`scripts/checks.mjs`）から外れている。
- テストが、例の一部を飛ばしている。例のファイルを読めずに0件で終わったときも同じである。
- 新しいシェルを足したときに、共通のテストを書き忘れる。

## Decision

### 共通のテストを必須にする

どのシェルも自分で実装し、どのシェルでも同じ結果にならなければならない振る舞いには、共通のテストを置く。
すべてのシェルが、共通のテストを回すことを必須とする。
対象は、コアや境界が定める値を、シェルが受けて扱う処理である。
今の対象は、ADR 090が決める2つ（差分を当てる処理と、境界の値の読み書き）である。

### 例と期待する結果は、コアが作る

共通のテストの例と、期待する結果は、コアのRustが作る。
例は、テストごとに1つのJSONのファイルにし、リポジトリに入れる。
各例にはidを付ける。
ファイルの頭には、例のidの一覧を書く。

コアのテストは、例を作り直し、リポジトリに入れたファイルと同じかを確かめる。
コアを変えて例が古くなったら、このテストが落ちる。
例を書き直すのは、例を作るコマンドである。
手で書き直さない。

### 各シェルは、すべての例を回す

各シェルは、ふだんのテストの道具で、共通のテストを回す。
TypeScriptはvitest、SwiftはXCTest、KotlinはJUnit、C#はxUnit、EmacsはRustの部分の`cargo test`である。
テストは、例のファイルを読み、各例を自分の処理で回し、期待する結果と比べる。
最後に、回した例のidの一覧が、ファイルの頭の一覧と同じかを確かめる。
例を飛ばしたり、0件で終わったりすれば、そのシェルのテストが落ちる。
コアが例を足せば、どのシェルでも、シェルのコードを変えずに新しい例が回る。

iOSとmacOSのように、同じコードを共有するシェルは、共有のコードのテストで1回回せばよい。

### テストのテストを、3段で置く

1. **テストがあることを、shell-checkが確かめる。**
   共通のテストの一覧と、各シェルのテストのファイルを、shell-checkの`rules/`に書く（ADR 064）。
   共通のテストの一覧は`rules/core.toml`に、各シェルのテストのファイルは`rules/<シェル>.toml`に書く。
   shell-checkの`cargo test`（`tests/repository.rs`）は、`rules/`にあるすべてのシェルについて、次を確かめる。
   - 一覧の共通のテストごとに、テストのファイルが書かれていること。
   - そのファイルがあり、その共通のテストの例のファイルの名前を読んでいること。
   - そのファイルが、そのシェルのテストの道具が集める場所にあること。
   書かれていない共通のテストがあれば、テストは落ちる。
   新しいシェルの`rules/`を足したときも、共通のテストをすべて備えるまで落ちる。
   このテストはUbuntuで回り、6つのシェルのすべてを1回で見る。
2. **例をすべて回したことを、テスト自身が確かめる。**
   前の節のとおり、各シェルのテストが、回した例のidの一覧を確かめる。
3. **テストが回る道を、見張りのテストが確かめる。**
   `scripts/verification.test.mjs`は、各シェルのジョブ（`scripts/checks.mjs`）が、共通のテストを含むテストの段を持つことを確かめる。
   `guard`ジョブとして、どの変更でもCIで回る。

テストが落ちうることは、各シェルのPRの前のミューテーションテストで確かめる。
ミューテーションテストの道具がないシェルでは、捨てるブランチで処理をわざと壊し、共通のテストが落ちることを一度確かめて、issueに記録する。

### まだのシェルは、issueの番号と一緒に書けば通す

共通のテストを新しく足すとき、すべてのシェルに同じPRで入れなくてよい。
まだ入れていないシェルは、`rules/<シェル>.toml`に、そのテストを入れるissueの番号を書く。

```toml
[common.list-changes]
pending = 1234
```

shell-checkは、issueの番号が書かれたシェルを通す。
番号も、テストのファイルも書かれていなければ、落ちる。
このため、共通のテストを足すPRは、Ubuntuで回せるシェルだけで出せる。
macOSとWindowsのシェルは、あとのPRで入れられる。

共通のテストが要らないシェルは、S2の除外と同じく、理由を1行で書く。

```toml
[common.list-changes]
excluded = "the shell has no list of rows"
```

## Alternatives

### Alternative 1: 各シェルが、自分の例でテストを続ける

今のままにする。
長所は、仕組みが要らないことである。
短所は、シェルの間の食い違いと、コアの変更に古くなった例を見つけられないことである。
目的に合わないので、選ばなかった。

### Alternative 2: 共通のテストを置くが、テストのテストは置かない

例はコアが作り、各シェルが回すが、備えているかは確かめない。
長所は、shell-checkと`guard`に足すものがないことである。
短所は、書いていないシェル、回していないシェル、例を飛ばしたシェルに気づけないことである。
シェルが6つあり、テストの道具も言語ごとに違うので、人が見て回るのでは抜けが出る。

### Alternative 3: 共通のテストを足すPRで、すべてのシェルに入れる

`pending`を許さない。
長所は、抜けが一時もないことである。
短所は、1つのPRがUbuntu、Mac、Windowsにまたがり、出すまでが長くなることである。
`pending`にはissueの番号が要るので、抜けは追える。
開発者が`pending`を許すほうを選んだ（2026-11-26）。

### Alternative 4: 1つのテストの道具で、すべてのシェルの処理を回す

たとえば、各シェルの処理をコマンドとして起こし、Rustのテストから呼ぶ。
長所は、例を回すテストを1か所に書けることである。
短所は、シェルごとに、処理を外から呼ぶための入口を作ることである。
SwiftとC#の処理は、それぞれのOSでしかビルドできず、1つの機械では回せない。
ふだんのテストの道具で回すほうが、各シェルのCIのジョブにそのまま入る。

## Confidence Level

中くらい。
仕組みの形は、S2で`rules/`とshell-checkの`cargo test`を使った実績がある。
例をJSONで渡すことは、どのシェルの言語でもできる。
一方で、テストのファイルが例のファイルを読んでいるかを、文字列で確かめるだけで十分かは、まだ分からない。

次のときは見直す。

- テストのファイルが例の名前を書いているのに、実際には回していない、という抜けが見つかったとき。
- `pending`が長く残り、共通のテストを備えないシェルが増えたとき。
- 共通のテストの対象が増え、JSONの例では表せない振る舞い（時間や入力の順に頼るもの）が出てきたとき。

## Consequences

### 良い結果

- シェルの間で、コアが送る値の扱いが食い違えば、そのシェルのテストが落ちる。
- コアが値の作り方を変えれば、例が作り直され、全シェルが新しい例で確かめられる。
- 新しいシェルを足すときに、備えるべき共通のテストが、shell-checkの失敗として示される。

### 悪い結果

- 共通のテストを足すたびに、6つのシェルのテストと、`rules/`の書き足しが要る。
- Androidのテストは、今はCIで回らない（`docs/verification.html`）。Androidの2段目は、CIに入るまで手元でしか回らない。
- 例のファイルは生成物だが、リポジトリに入る。コアの変更のPRに、例の差分が混ざる。

### 中立的な結果

- shell-checkは、ADR 064の静的なチェックに加えて、共通のテストを備えているかも確かめる道具になる。
- `docs/verification.html`の「shell-check」の表に、共通のテストの行を足す。
