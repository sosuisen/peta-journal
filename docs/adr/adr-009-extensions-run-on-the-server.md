# ADR 009: Extension Functions Run on the Server with rquickjs

## Status

Accepted

## Context

拡張関数は、利用者が設定フォルダの`functions/`に置くプログラムである。今ある拡張は`auto-template`だけである。これは、ページを作ったときと、ページにタグを足したときに、テンプレートの項目を入れる。

2026-11-08の時点で、拡張関数はフロントエンドの中で動く。サーバーは`/api/functions`で拡張のファイルを配るだけである。コアは、拡張を動かす仕事をシェルに任せている。ページができると、コアは`UiOp::ExtensionPageCreate`をシェルに渡す。タグが足されると`UiOp::ExtensionPageTagAdd`を渡す。拡張から届いた`CreateItem`と`Confirm`はコアが処理し、答えを`UiOp::ExtensionReply`でシェルに返す。

`shell-leptos`は、拡張を隠れたiframeで動かし、`postMessage`で中継する。つまり、拡張の約束はブラウザを前提にしている。この前提から、次の3つの問題が生じている。

第一に、シェルごとにJSの実行環境が要る。ブラウザで動く`shell-leptos`には、はじめから実行環境がある。`shell-emacs`にはないので、`auto-template`は動かない。今は4つの`UiOp`を捨てている。将来はCruxを使ったWinUI3版のシェルも作る予定である。そのシェルでは、WebView2を隠して持つことになる。シェルを足すたびに、同じ仕組みを作り直すことになる。

第二に、拡張はフロントエンドを通って作られたページにしか効かない。MCPの`get_or_create_journal`などで作ったページには、テンプレートが入らない。外部アプリがAPIで作ったページも同じである。

第三に、テンプレートの項目は、空のページができた後に1つずつ届く。新しいページは空の項目を1つ持つので、テンプレートの前に空の行が残る。コアはこれを避けるために、最後に置く項目が空の1項目を上書きする処理を持っている。

サーバーは、どのフロントエンドも外部アプリもMCPも、共通して通る唯一の場所である。サーバーはすでに、ビルドでCのコンパイラを使っている。`rusqlite`の`bundled`が、SQLiteのCのソースをコンパイルしているからである。

## Decision

拡張関数をサーバーの中で動かす。サーバーに`rquickjs`（QuickJS）を組み込み、拡張はJSで書く。

サーバーは、ページを作る処理とタグを足す処理の中で、拡張を呼ぶ。呼び出しは、どのクライアントから作られたページでも同じである。ただし、フォルダ同期で取り込んだページでは呼ばない。取り込んだファイルには、利用者が書いた内容がすでにあるからである。

ページを作るときの拡張は、ページを返す前に同期して呼ぶ。クライアントには、テンプレートの入ったページが最初から届く。

拡張がサーバーの外に触れる手段は、サーバーが渡す関数だけにする。たとえば、項目を作る関数、Flat Markdownを項目に分ける関数、拡張のフォルダのファイルを読む関数である。ファイルやネットワークに直接触れる関数は渡さない。QuickJSのメモリと実行時間の上限も設ける。

拡張が利用者に確認を求めるときは、サーバーがSSEで問い合わせを送る。開いているフロントエンドが確認を表示し、答えをRESTで返す。確認の表示は、どのシェルもすでに`UiOp::Confirm`として持っている。

`auto-template`は、新しい約束に合わせて書き直す。テンプレートの形式と、パターンの判定は変えない。フロントエンドで拡張を動かす仕組みは消す。コアの`UiOp::LoadExtensions`、`ExtensionPageCreate`、`ExtensionPageTagAdd`、`ExtensionReply`と、`shell-leptos`のiframeの中継が対象である。

## Alternatives

### Alternative 1: 各シェルにJSの実行環境を持たせる

今の約束を保ち、`shell-emacs`に`rquickjs`などを組み込む。WinUI3版ではWebView2を使う。

コアと`script.js`を変えずに済む。しかし、シェルを足すたびに、実行環境と`fetch`や`postMessage`の代わりを作る必要がある。フロントエンドを通らないページに効かない問題と、テンプレートが後から届く問題も残る。そのため採らなかった。

### Alternative 2: 拡張を別のプロセスにする

拡張を独立したプログラムにする。拡張はSSEでイベントを受け、RESTで項目を作る。Todoアプリと同じ形である。

言語を選ばず、サーバーは拡張の実行に関わらない。しかし、イベントはページができた後に届くので、テンプレートが後から入る問題が残る。拡張のプログラムを起動し続ける仕組みも別に要る。そのため採らなかった。

### Alternative 3: auto-templateをコアかサーバーの標準機能にする

テンプレートは「ルールとテンプレート」というデータなので、Rustで実装して標準機能にする。

依存は増えない。しかし、拡張関数の仕組みそのものがなくなるか、見本のない仕組みが残る。利用者がテンプレート以外の処理を足す手段も失う。そのため採らなかった。

### Alternative 4: JS以外の組み込み言語を使う

Lua（`mlua`）、Rhai、WebAssembly（Extism）などを使う。

Luaは軽くて速く、閉じ込めやすい。しかし、拡張の中心になる処理で毎回手間がかかる。テンプレートの`pattern: /…/`はJSの正規表現で書かれているが、Luaのパターンは正規表現ではない。JSONの`null`や空の配列の扱いに癖があり、文字列はバイト単位で扱われる。Rhaiは利用者が少ない。WebAssemblyは、拡張を手直しするたびにビルドが要る。サーバーの中で小さな拡張を時々動かす用途では、JSの書きやすさが勝ると判断した。

NeovimやWezTermがLuaを選んだ事情は、ここには当てはまらない。Neovimが組み込みの言語を選んだ2010年代半ばには、小さく組み込めるJSエンジンがなかった。V8やSpiderMonkeyは巨大で、APIもよく変わった。QuickJSが出たのは2019年である。また、エディタの拡張はキーを押すたびに動くので、LuaJITの速さが要る。PetaJournalの拡張は、ページを作るときやタグを足すときにしか動かない。

### Alternative 5: JSのエンジンにboaかV8を使う

`boa`はRustだけで書かれていて、Cのコンパイラが要らない。しかし、サーバーはすでにCのコンパイラを使っているので、この利点は効かない。V8（`deno_core`）は速いが、バイナリが数十MB増え、ビルドも重くなる。小さな拡張にはQuickJSで足りる。そのため、どちらも採らなかった。

### Alternative 6: シェルごとの画面に合わせた拡張を用意する

Web版ではDOM、Emacs版ではバッファというように、シェルごとの画面を操作できる拡張の仕組みを、シェルごとに用意する。

拡張が、各シェルの画面に部品を足せる。しかし、シェルごとに別の仕組みと別のAPIを作り、保ち続けることになる。シェルを足すたびに、この仕事も増える。これは、拡張の実行をサーバーへ移す狙いに反する。そのため採らなかった。

画面を必要とする拡張は、サーバーと通信する外部アプリとして、自由に作ってもらう。Todoアプリ（`ext-web-app/todo`）とStickies（`ext-desktop-app/stickies`）が、その例である。外部アプリは、RESTで読み書きし、SSEで変更を受け取る。

シェルの画面そのものを変えたい利用者は、自分のシェルを作ればよい。コアはCruxで書かれていて、シェルは画面とOSとのやり取りだけを受け持つ。エージェントコーディングの時代には、利用者が自分のシェルを作ったり、今あるシェルを手直ししたりすることは、現実的な解の1つである。

## Confidence Level

中程度である。拡張の実行場所をサーバーに移すことには、確信が高い。シェルの数が増える予定があり、問題がシェルの数だけ増えるからである。一方、拡張に渡す関数の形と、確認をSSEで問い合わせる仕組みは、まだ実装して確かめていない。

次のときに見直す。

- 外部アプリでも自分のシェルでも実現できない、シェルの画面に組み込む拡張が必要になったとき。Alternative 6を見直す。
- 誰が書いたか分からない拡張を配って動かすようになったとき。より強い閉じ込めとして、WebAssemblyを検討する。
- 拡張の処理が重くなり、ページを作る応答が目に見えて遅くなったとき。同期の呼び出しをやめ、後から入れる形を検討する。
- `rquickjs`の開発が止まったとき。

## Consequences

良い結果は、次のとおりである。

- どのシェルも、拡張のための実行環境を持たなくてよい。`shell-emacs`と将来のWinUI3版で、そのまま拡張が効く。
- MCPや外部アプリで作ったページにも、テンプレートが入る。
- テンプレートの入ったページが最初から届く。コアの、空の1項目を上書きする処理は要らなくなる。
- 拡張が触れられる範囲を、サーバーが渡す関数で決められる。

悪い結果は、次のとおりである。

- 今の`auto-template`は動かなくなる。書き直しが要る。
- 利用者が自分で書いた拡張があれば、それも書き直しが要る。
- 拡張は画面を持てない。今の`index.html`の仕組みはなくなる。画面が要るときは、外部アプリとして作る必要がある。
- サーバーにJSのエンジンという大きな依存が増える。
- サーバーが利用者に確認を求める、新しい経路（SSEでの問い合わせとRESTでの答え）を作る必要がある。開いているフロントエンドがないときの扱いも決める必要がある。
- 拡張の不具合や遅さが、ページを作る応答に直接響く。

中立的な結果は、次のとおりである。

- 拡張がサーバーと同じプロセスで動くので、拡張のログはサーバーのログに出る。ブラウザの開発者ツールでは見られなくなる。
- フォルダ同期で取り込んだページを区別するため、ページを作る経路を、サーバーが知っている必要がある。
