# ADR 050: The Server Refuses Items With Unclosed Blocks

## Status

Accepted

## Context

Flat Markdownでは、Markdownのブロック要素として読めるものが、1つの項目になる。
ページの`.md`ファイルは、flatmarkdownクレートがcomrakで読む。
一番上のブロック1つが、項目1つになる。

ブロックの中には、開始記号と終了記号が行で対になるものがある。
flatmarkdownで有効にしている拡張では、次のブロックが当てはまる。

| ブロック | 開始 | 終了 |
|---|---|---|
| コードブロック | ` ``` `か`~~~` | 同じ記号の、同じ長さ以上の行 |
| 数式のブロック | ` ```math ` | ` ``` ` |
| 複数行の引用 | `>>>` | `>>>` |
| HTMLのブロックの一部 | `<pre`、`<script`、`<style`、`<textarea`、`<!--`、`<?`、`<!X`、`<![CDATA[` | `</pre>`などの対の記号、`-->`、`?>`、`>`、`]]>` |

開始記号だけがあって閉じていないブロックは、対の終了記号が現れるまで続く。
項目の本文がこのブロックを持つと、ページの残りが、その1つの巨大なブロックに飲み込まれる。
次にファイルを読み戻すと、後ろの項目は1つの項目につぶれ、元に戻せない。

HTMLのコメントでは、壊れ方が少し違う。
項目のメタデータ行も`<!-- @@ ... -->`の形である。
閉じていない`<!--`は、次の項目のメタデータ行の`-->`で閉じる。
そのため、次の項目のメタデータが本文に飲み込まれ、2つの項目が1つになる。

開始記号と終了記号は、本文のどの行にも現れうる。
最後の行に` ``` `が1つだけある本文も、閉じていないコードブロックになる。

この問題は、journal-serverだけのものではない。
Flat Markdownのページに項目を書くプログラムなら、どれも同じ問題に出会う。
どのブロックが行で対になるかは、flatmarkdownがcomrakのどの拡張を有効にするかで決まる。

coreには、` ``` `だけを扱う仕組みが、すでに3つある。
1つめは、Enterの判定である（`has_unclosed_code_fence`）。
` ``` `で始まる行が奇数個なら、項目を分けずに改行を入れる。
2つめは、打ったときの自動の閉じである（`auto_close`）。
行頭で` ``` `を打つと、その場で本文の最後に` ``` `を足す。
Web版とEmacs版のシェルが、これを使う。
3つめは、保存のときの自動の閉じである（`ensure_code_fence_closed`）。
自動保存も、ほかの保存も、送る前に` ``` `を足す。
サーバーも、分割、2つの項目をつなぐとき、移動、貼り付けで、同じように` ``` `を足して保存する（`close_code_fence`）。

どれも、行を数えるだけで、`~~~`、フェンスの長さ、`>>>`、HTMLのブロックは見ない。
2つめは、ユーザーが自分で閉じる記号を打つと、行が奇数個になり、さらに` ``` `を足してしまう。
閉じたつもりのブロックが、また開く。
サーバーの仕組みは、` ```\ncode\n``` `と`after`をつないだ` ```\ncode\n```after `を、閉じずに保存する。
` ```after `は閉じるフェンスにならないが、` ``` `で始まる行が偶数個なためである。

今のサーバーは、閉じていないブロックを持つ本文を、そのまま保存しうる。
項目の本文は、Web、Emacs、Windows、macOS、iOS、Androidのシェルからも、RESTやMCPからも届く。
一方、手で編集された`.md`ファイルから入ってくるものは、取り込むときに直しようがない。
ファイルの時点で、項目の区切りがもう決まっているためである。

## Decision

閉じていないブロックは、編集を終えるときに、coreが閉じる記号を補って保存する。
サーバーは、閉じていないブロックを持つ項目の保存を断る。
判定と補完は、flatmarkdownクレートに置く。

### 判定（flatmarkdown）

- flatmarkdownに、項目の本文が閉じていないブロックを持つかを判定する関数を足す。
- 判定は、本文の一番上で開いたまま終わるブロックを見る。開始記号があって、対になる終了記号がないブロックである。開始記号と終了記号は、本文のどの行にあってもよい。
- リストの項目や、ふつうの`>`の引用のように、終了記号のない入れ物の中のブロックは対象にしない。入れ物が終わると、中のブロックも閉じるためである。
- 終了記号が開始記号と違うブロックでは、終了記号だけがあっても、閉じていないとはしない。たとえば、`-->`や`</pre>`だけの本文は通す。
- 判定は、flatmarkdownがページを読むときと同じcomrakの設定で行う。対になるブロックの種類は、有効にした拡張から決まるためである。拡張を足したり外したりしても、判定は読み方とずれない。

### 補完（flatmarkdown）

入れ子になるのは、`>>>`の中にコードブロックかHTMLのブロックが入る2段だけである。
コードブロックとHTMLのブロックの中身はただの文字で、何も入れ子にならない。
`>>>`の中の`>>>`は、外の`>>>`を閉じる。
これは2026-11-15に、flatmarkdown 0.8.0で確かめた。

flatmarkdownに、補う関数を2つ足す。

- **後ろを補う関数**：本文の最後で開いているブロックに、内側から順に終了記号を足す。たとえば、` ``` `には同じ記号と長さの` ``` `、`>>>`には`>>>`、`<!--`には`-->`を足す。`>>>`の中で` ``` `が開いていれば、` ``` `、`>>>`の順に足す。
- **分ける関数**：本文と分ける位置を受け取り、補った前の部分と後ろの部分を返す。前の部分には、後ろを補う関数と同じく、終了記号を足す。後ろの部分には、分けた位置で開いていたブロックの開始行を、外側から順に前に足す。開始行は、情報文字列（` ```rust `）やフェンスの長さごと、元の行をそのまま写す。たとえば、` ```\ncode\n``` `を`co`と`de`の間で分けると、前は` ```\nco\n``` `、後ろは` ```\nde\n``` `になる。

シェルからの分割では、ブロックの中で分けることはない（「編集（core）」を参照）。
分ける関数を使うのは、RESTやMCPから分割を頼まれたときのサーバーである。

flatmarkdownの新しい版を出す。
ADR 020に従い、3つのクレートの版をそろえる。

### 編集（core）

- coreは、編集中の項目ごとに「閉じる記号がない」フラグを持つ。本文が変わるたびに、flatmarkdownで判定する。
- フラグが立っている間は、自動保存を送らない。自動保存は、予約したときではなく、送る時点でフラグを見る。フラグが立っていれば送らない。
- 本文が編集を離れるときは、後ろを補った本文を送る。表示モードへの切り替え、別の項目への移動、項目の選択、ページを閉じるときである。
- 開いたブロックの中でEnterを押すと、項目を分けずに改行を入れる。コードブロック、数式のブロック、`>>>`、HTMLのブロックのどれでも同じである。開いているかは、カーソルより前の本文をflatmarkdownで判定する。
- Enterの判定は、補完より先に、補う前の本文で行う。Enterは編集を離れる操作ではない。
- 開始記号を打ったとき、閉じる記号を自動で入れるのは、次の場合だけである。開始記号が行頭にあり、その後ろに本文が何もない場合である。つまり、新しいブロックを書き始めたときである。対象は、すべての開始記号である。それ以外の場合は、フラグと、編集を離れるときの補完に任せる。
  - 理由：自動の閉じは便利なので、ある方が望ましい。一方で、ブロックの構文は壊れやすい。すでにある本文の途中で閉じる記号を足すと、ほかのブロックの開始記号や終了記号と組み合わさり、思わぬ形になる。たとえば、ユーザーが自分で閉じる記号を打つと、自動で足した閉じる記号が、新しい開始記号に変わる。そのため、新しいブロックを書き始めたときだけに限る。
- この自動の閉じは、coreの決まりにする。Web版とEmacs版は、今も使っている。Windows、macOS、iOS、Androidのシェルにも入れることを推奨する。
- 今ある3つの仕組みを、この決定に置き換える。Enterの判定は、flatmarkdownの判定に置き換える。打ったときの自動の閉じは、上の決まりに置き換える。保存のときの自動の閉じは、編集を離れるときの補完に置き換える。`auto_close`のうち、`[[`の閉じは残す。ブロックとは関係がないためである。
- 6つのシェルは、coreを通して同じ動きになる。

### 拒否（journal-server）

- サーバーは、「項目」として入ってくるものすべてを判定する。本文の更新、項目の作成、貼り付け、Enterでの分割、2つの項目をつなぐとき、移動、Markdownの取り込みなどである。RESTでもMCPでも同じである。
- coreが補うので、シェルからの保存は断られない。この拒否は、RESTやMCPから直接書く経路を守る。
- 1つの要求に、閉じていないブロックを持つ項目が1つでもあれば、要求全体を断る。ADR 011のとおり、要求は全部書くか、何も書かない。
- 断るときのエラーの文は、「Markdownのブロック要素は、開始記号と閉じる記号が揃わない限り、保存できません。」である。
- サーバーが自分で` ``` `を閉じる今の仕組み（`close_code_fence`）は、なくす。分割、2つの項目をつなぐとき、移動、貼り付けで、作った本文が閉じていなければ、要求を断る。閉じる記号を足すと、本文の意味が変わるためである。たとえば、` ```\ncode\n``` `と`after`をつないだ` ```\ncode\n```after `に足すと、`after`がコードブロックの中身になる。
- 手で編集された`.md`ファイルから入ってくるものは、判定しない。ファイルの時点で、項目の区切りがもう決まっているためである。
- すでに保存されている、閉じていないブロックは扱わない。

## Alternatives

### Alternative 1: 判定をjournal-serverに置く

flatmarkdownは変えず、journal-serverの中で判定する。

- 長所：flatmarkdownのリリースが要らない。
- 短所：Flat Markdownを書くほかのプログラムが、同じ判定を書き直すことになる。flatmarkdownがcomrakの拡張を変えると、判定がずれる。

この問題はFlat Markdownでいつも関わるので、採らなかった。

### Alternative 2: サーバーが、書くときに閉じる記号を足す

断らずに、閉じていないブロックの後ろに終了記号を足して保存する。

- 長所：RESTやMCPからの書き込みも、断られない。
- 短所：サーバーには、ユーザーがまだ編集中かが分からない。入力の途中の自動保存のたびに、ユーザーが書いていない記号が本文に入る。2つの項目をつないだ本文のように、足すと意味が変わる本文もある。

本文を勝手に変えるので、採らなかった。
補うのは、編集を離れたことが分かるcoreで行う。

### Alternative 3: coreだけで守り、サーバーでは断らない

coreが補うので、シェルからは閉じていないブロックが届かない。
サーバーの判定は置かない。

- 長所：サーバーを変えずに済む。
- 短所：RESTやMCPから直接書く経路は止められない。ファイルを壊す経路が残る。

すべての経路を止めるには、サーバーで断る必要があるので、採らなかった。

### Alternative 4: 行ごとに記号を数えて判定する

comrakで読まずに、` ``` `、`>>>`、`<!--`などの行を数えて、対になっているかを見る。
今のcoreの`has_unclosed_code_fence`は、この形である。

- 長所：判定が速く、仕組みが分かりやすい。
- 短所：インデントやリストの中の記号、フェンスの長さ、`~~~`など、comrakの読み方との違いが出やすい。拡張を変えたときに、数え方も直す必要がある。

読み方とずれる恐れがあるので、採らなかった。

### Alternative 5: 打ったときの自動の閉じを、今の決まりのまま残す

行頭で` ``` `を打ち、` ``` `で始まる行が奇数個になったときに、閉じる記号を足す今の仕組みを残す。

- 長所：` ``` `のブロックは、打った時点で閉じる。フラグが立つことが少ない。
- 短所：ユーザーが自分で閉じる記号を打つと、さらに閉じる記号が足され、閉じたつもりのブロックがまた開く。

動きがおかしくなるので、採らなかった。
自動の閉じは、新しいブロックを書き始めたときだけに限って残す。

### Alternative 6: 自動保存では、補った本文を送る

フラグが立っている間も自動保存を送り、送る本文だけを補う。
エディタの中の文字は補わない。

- 長所：編集の途中でも、本文がサーバーに残る。
- 短所：サーバーの本文とエディタの本文が食い違う。ほかの端末には、ユーザーが打っていない閉じる記号が見える。

食い違いを生むので、採らなかった。

### Alternative 7: `>>>`とHTMLのブロックの中のEnterでは、項目を分ける

コードブロックの中だけ改行にし、ほかのブロックの中では項目を分ける。
分けるときに、前の部分と後ろの部分を補う。

- 長所：`>>>`の途中で、項目を2つにできる。
- 短所：ブロックによって、Enterの動きが違う。ユーザーが覚えることが増える。

どのブロックでも同じ動きにするため、採らなかった。

## Confidence Level

確信度は高い。
閉じていないブロックは、ページの残りを壊し、元に戻せない。
coreが編集を離れるときに補い、サーバーが最後に断ることで、どの経路からも壊れた本文は保存されない。
判定と補完はflatmarkdownと同じ読み方で行うので、どのブロックが閉じていないかを取り違えにくい。

フラグが立っている間は、自動保存を送らない。
そのため、編集を離れるまで本文はサーバーにない。
それでも受け入れられるのは、開始記号を打った時点で、閉じる記号が自動で入るからである。
ブロックを書き始めた時点で、本文はもう閉じている。
フラグが立つのは、ユーザーが閉じる記号を消したときや、本文の途中で開始記号を打ったときなどに限られる。

次のことが起きたら、この決定を見直す。

- flatmarkdownが、行で対になるブロックの拡張を新しく有効にしたとき。判定と補完が、その拡張でも正しく動くかを確かめ直す。
- comrakの版を上げて、ブロックの読み方が変わったとき。入れ子は2段だけという前提は、comrak 0.51を使うflatmarkdown 0.8.0で確かめたものである。
- 手で編集された`.md`ファイルからの取り込みでも、閉じていないブロックが問題になると分かったとき。ADR 048は、手での編集はまれだとしている。

## Consequences

良い結果は、次のとおりである。

- どの経路からも、閉じていないブロックを持つ本文は保存されない。ページの残りが1つのブロックに飲み込まれることがなくなる。
- 判定と補完は、flatmarkdownの1か所にある。6つのシェル、REST、MCPが、同じ決まりで動く。Flat Markdownを書くほかのプログラムも、同じ関数を使える。
- 開いたブロックの中のEnterは、どのブロックでも改行になる。ユーザーが覚えることが減る。
- 今ある2つの不具合が直る。1つは、打ったときの自動の閉じで、自分で閉じる記号を打つと、ブロックがまた開くことである。もう1つは、サーバーが` ```\ncode\n```after `のような本文を、閉じずに保存することである。

悪い結果は、次のとおりである。

- flatmarkdownの新しい版が要る。ADR 020に従い、3つのクレートの版をそろえて出す必要がある。
- フラグが立っている間は、本文がサーバーにない。ほかの端末にも届かない。自動の閉じがないシェルでは、この時間が長くなる。
- 2つの項目をつなぐ、貼り付ける、移動するといった操作で、作った本文が閉じていなければ、操作が断られる。ユーザーには、Backspaceなどが効かないように見える。
- RESTやMCPのクライアントには、新しいエラーが返るようになる。
- coreは、本文が変わるたびにflatmarkdownで判定する。長い本文では、打つたびの処理が重くなるかもしれない。

中立的な結果は、次のとおりである。

- 手で編集された`.md`ファイルから入ってくるものと、すでに保存されている閉じていないブロックは、今のまま扱わない。
- coreの`has_unclosed_code_fence`と`ensure_code_fence_closed`、`auto_close`の` ``` `の部分、サーバーの`close_code_fence`は、この決定に置き換わる。
- `docs/features.md`の「コードフェンスが閉じていなければ、閉じて保存する」の項目は、書き直しになる。
- Windows、macOS、iOS、Androidのシェルに、打ったときの自動の閉じを入れるタスクが、`docs/plans.md`に増える。
