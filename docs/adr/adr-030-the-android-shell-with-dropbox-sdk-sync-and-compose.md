# ADR 030: The Android Shell with Dropbox SDK Sync and Compose

## Status

Accepted

## Context

ADR 029で、Androidのシェルはジャーナルのコアをアプリに組み込むと決めた。`journal-core`の切り出しと、フロントエンドのコアの要求をアプリの中で行う`peta-embedded-journal`はできている。残っているのは、Androidに固有の決定である。

Markdownのフォルダーは、PCではDropboxアプリが同期している。Androidには、アプリのフォルダーを同期し続けるDropboxアプリの仕組みがない。そこで、アプリがDropboxのAPIでファイルを取る必要がある。

Androidは、裏に回ったアプリのスレッドを止める。PCのサーバーが回している定期の仕事（フォルダーの見回り、索引のコミット、書き出し）は、同じ形では回せない。

シェルはKotlinとJetpack Composeで書く。Rustとの境界には、SwiftUIとWinUIのシェルと同じくBoltFFIと`facet`の型の生成を使う（ADR 024、028）。捨てるブランチでの確かめで、次のことが分かった（2026-11-11と12）。

- `journal-core`はエミュレーターで動き、2000ページでも検索は17ms以下、メモリーは37MB以下である。
- Kotlinの型は、`facet_generate` 0.22.3で生成できる。ただし、`index`という名前の4つのフィールドを拒む。
- Composeの`AnnotatedString.fromHtml`は、文字の飾りとリンクは描けるが、コードブロック、表、画像は描けない。
- Dropbox SDK 8.0.2で、PKCEの認証、再帰の一覧、ダウンロードが通った。実際のフォルダーには764個のファイルがあり、そのうちMarkdownは655個、5.4MBである。一覧は8.2秒で取れた。ダウンロードは、1個ずつ順に取ると1個に約1秒かかった。

PCのサーバーは、ファイルが消えたページについて、ページも消すかをユーザーに尋ねる。Androidのコアには、尋ねる画面がない。

最初の版は、Dropboxからの取り込み、検索、ページの表示までである。編集とアップロードは次の版にする。

ギアは5速である。

## Decision

### 同期

Dropbox SDK（`dropbox-android-sdk` 8系）を採用する。認証はPKCEで、権限は読み取りの2つ（`files.metadata.read`、`files.content.read`）だけにする。Dropboxのアプリのアクセスの種類は、Full Dropboxである。PCが使っているMarkdownのフォルダーを、そのまま読むためである。

Kotlinが、再帰の一覧でMarkdownのフォルダーの変更を取り、アプリの中のフォルダーにダウンロードする。一覧のカーソルを保存し、次の回は変更だけを取る。最初の版は画像を描かないので、取るのは`.md`のファイルだけにする。最初の取り込みは数が多いので、何個かを同時に取る。

Dropboxで消えたファイルは、アプリの中からも消す。そのファイルのページは、ユーザーに尋ねずに消す。アプリの中のデータはDropboxの写しで、Dropboxから作り直せるためである。

App keyとフォルダーのパスは、ビルドのときに外から渡す。リポジトリには入れない。Dropboxの資格（リフレッシュトークン）は、アプリの専用の領域に保存する。

### 置き場所

Markdownは`filesDir/markdown`、DBと索引と設定は`filesDir/data`に置く。どちらもDropboxから作り直せるので、Androidのバックアップの対象から外す。Dropboxの資格も、バックアップの対象から外す。

`docs`、`journals`、`assets`のフォルダーは、Kotlinがダウンロードの前に作る。

### 定期の仕事

最初の版では、誰も回さない。Kotlinがダウンロードのあとに`sync()`を1回呼び、Rustがその場でスキャンして索引を確定する。ファイルが変わる時を知っているのは、Kotlinだからである。

### `Host`の置き場所

`frontend-rust/crates/shell-android`（`peta-shell-android`）に、`Host`の実装とBoltFFIの入口を置く。`shell-native`には足さない。

### Kotlinの型

`facet_generate` 0.22.3で生成する。0.22.3が拒む`index`という4つのフィールドは、Rustのフィールドの名前を変える。ほかのシェルも、新しい名前に合わせる。

### HTMLの描き方

項目の中の文字の飾りとリンクは、`AnnotatedString.fromHtml`で描く。コードブロックと表は、KotlinがASTを見て専用の部品で描く。画像は、最初の版では描かない。

### テスト

Rustの側は`cargo test`で確かめる。Kotlinの側は、エミュレーターの上のテストで確かめる。PCのJVMでのテストは、BoltFFIの`desktop_pack`がWindowsで通るようになるまで採らない。

### ビルド

Kotlinのプラグインは2.4系にする。Dropbox SDK 8.0.2が、Kotlin 2.4のライブラリを連れてくるためである。

## Alternatives

### Alternative 1: 別の同期アプリに、共有のフォルダーへ同期させる

Dropboxのフォルダーを端末の共有の領域に同期するアプリを、ユーザーが入れる。PetaJournalは、そのフォルダーを読む。

長所は、認証もダウンロードも書かずに済むことである。

短所は3つある。ユーザーが、別のアプリを入れて設定する。共有の領域のフォルダーを自由に読むには、強い権限（すべてのファイルへのアクセス）が要る。それを避けると、ファイルを`content://`のURIで読むことになり、Rustのスキャンがそのまま使えない。

選ばなかった。

### Alternative 2: DropboxのAPIを、Rustから呼ぶ

HTTPのクライアントをRustのライブラリに入れ、一覧とダウンロードをRustで書く。

長所は、ほかのシェルでも同じコードが使えることである。

短所は、認証の画面の行き来が、どのみちAndroidの側に要ることである。ライブラリには、HTTPとTLSの依存が増える。資格の更新も、自分で書く。SDKは、これらを持っている。

選ばなかった。ほかのシェルにも同期が要るようになったら、見直す。

### Alternative 3: アクセスの種類をApp folderにする

アプリは、Dropboxの`Apps/<アプリ名>/`の中だけを読める。

長所は、アプリが読める範囲が狭いことである。

短所は、PCのMarkdownのフォルダーを、その中へ移す必要があることである。

開発者は、Full Dropboxを選んだ。権限を読み取りの2つに絞ることで、書き込みは防ぐ。

### Alternative 4: 消えたファイルのページを残すか、ユーザーに尋ねる

PCのサーバーと同じ扱いである。

短所は、Dropboxで消したページが、検索に出続けることである。尋ねるなら、画面が1つ要る。最初の版はページを変えないので、アプリにしかない中身はない。消しても、失うものがない。

選ばなかった。編集を入れる版で、見直す。

### Alternative 5: 定期の仕事を、Rustの中のタイマーで回す

PCのサーバーと同じ形である。

短所は、Androidが裏に回ったアプリのスレッドを止めることである。タイマーは当てにできない。最初の版では、ファイルが変わるのはダウンロードのときだけなので、回す理由もない。

選ばなかった。

### Alternative 6: 項目を、WebViewで描く

`ast_to_html`のHTMLを、そのままWebViewに渡す。

長所は、コードブロックも表も画像も、Webのシェルと同じに描けることである。

短所は、項目ごとにWebViewを置くと重いことである。ページ全体を1つのWebViewにすると、一覧のスクロールや選択をComposeで扱えなくなる。

選ばなかった。

### Alternative 7: 最初の版では、コードブロックと表を`fromHtml`のまま出す

長所は、専用の部品を書かずに済むことである。

短所は、コードブロックの改行が消え、表のセルの文字がつながることである。読めない形で出る。

開発者は、専用の部品で描くほうを選んだ。

### Alternative 8: `index`のフィールドに、`#[facet(rename)]`を付ける

Rustのフィールドの名前は残し、生成する型でだけ名前を変える。

短所は、Rustと各シェルで名前が食い違うことである。

開発者は、Rustのフィールドの名前を変えるほうを選んだ。

## Confidence Level

確信度は、同期のほかは高い。同期は中程度である。

確かめたことは、次のとおりである。`journal-core`は、エミュレーター（`x86_64`、Android 15）の上のアプリで動いた。取り込み、日本語の検索、ビューモデルの復元ができた。Kotlinの型は生成でき、コンパイルが通った。`boltffi pack android`は、`arm64-v8a`と`x86_64`でビルドできた。Dropbox SDKは、認証、再帰の一覧、5個のダウンロードが通った。`fromHtml`が描けるものと描けないものも、実際に描いて確かめた。

確かめていないことは6つある。

第一に、最初の取り込みにかかる時間である。1個ずつ順に取ると、655個に約11分かかる計算である。同時に取ったときの速さは、測っていない。測ったのは、ソフトウェアで描くエミュレーターの上である。実際の端末では、違うかもしれない。

第二に、変更だけを取る2回目以降の同期である。カーソルは取れたが、使っていない。消えたファイルや、名前が変わったファイルが、一覧にどう出るかも見ていない。

第三に、資格の更新である。アクセストークンは数時間で切れる。リフレッシュトークンで続けられることは、SDKの説明で読んだだけである。

第四に、実際の端末（`arm64`）である。動かしたのは、エミュレーターだけである。

第五に、コードブロックと表の専用の部品である。ASTからComposeで描くコードは、まだ書いていない。

第六に、エミュレーターの上でのKotlinのテストである。テストの枠組みは、まだ用意していない。

次のときに、この決定を見直す。

- 同時に取っても、最初の取り込みが遅すぎるとき。フォルダーをZIPで1回で取る方法（`downloadZip`）を検討する。
- 編集とアップロードを入れるとき。書き込みの権限、定期の仕事を回す場所、消えたファイルの扱い（Alternative 4）を決め直す。
- 画像を描くとき。`assets`のファイルも取る。
- 裏での同期が要るとき。WorkManagerがKotlinから`sync()`を呼ぶ形を検討する。
- BoltFFIの`desktop_pack`がWindowsで通るようになったとき。PCのJVMでのテストを検討する。

## Consequences

### 良い結果

Androidのシェルは、PCと同じ取り込みと検索を使う。Kotlinが書くのは、Dropboxとの間でファイルを運ぶことと、画面を描くことだけである。

アプリは、Dropboxを読むだけである。権限が読み取りだけなので、アプリの不具合でDropboxのノートが壊れることはない。

アプリの中のデータは、いつでも捨てて作り直せる。DBの形を変えるときも、移行を書かずに済む。

SDKが、認証の画面の行き来と資格の更新を持つ。

### 悪い結果

Markdownが、端末にもう1組できる。今のデータで約5MBである。

最初の取り込みには、時間がかかる。その間の進み具合を見せる画面が要る。

同期は、アプリを開いているときにしか動かない。開いた直後は、前の回の中身が見える。

アプリは、Full Dropboxの読み取りの権限を持つ。Markdownのフォルダーの外のファイルも、読める立場にある。

Dropboxで誤ってファイルを消すと、次の同期で、アプリのページも尋ねられずに消える。Dropboxで元に戻せば、次の同期で戻る。

コードブロックと表の描き方が、Kotlinにもう1つできる。ASTの形が変わると、ここも直す。

画像は、最初の版では見えない。

Kotlinのテストは、エミュレーターの上でしかRustを呼べない。テストが遅くなる。

Kotlinのプラグインの版が、Dropbox SDKに縛られる。

### 中立的な結果

リポジトリに、`frontend-android`が増える。BoltFFIとKotlinの型の生成物は、リポジトリに入れない。

App keyとフォルダーのパスは、ビルドする人が自分で渡す。`BUILD.md`に、渡し方を書く。

`journal-core`の、消えたファイルについて尋ねる入口（`MissingFilesPrompt`）は、Androidでは「尋ねずに消す」という実装になる。

編集を入れる次の版で、索引のコミットと書き出しを回すスレッドをどこに置くかを決める。
