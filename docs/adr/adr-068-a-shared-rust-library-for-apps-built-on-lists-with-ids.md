# ADR 068: A Shared Rust Library for Apps Built on Lists with IDs

## Status

Superseded by ADR 091

## Context

### 必要性

PetaJournalのほかにも、Rustのコアとネイティブの画面で作りたいアプリがある。
1つは画像ビューアーの`sosuisen/sss-image-viewer`である。
もう1つはファイルエクスプローラーの`sosuisen/gallery-explorer`である。
あるいはこの2つを合体させたアプリである。
どのアプリも、Windows、macOS、Linuxで動作する形にしてみたい。
いずれも日常的に使っているアプリである。
加えて、技術的な検証も目的とする。

Rustを採用するのは、起動速度と実行速度のためである。
ネイティブの画面を採用するのは、日本語入力の問題の少なさと、OSのイベントの取り扱いの容易さのためである。

現代のエージェントを用いた開発の課題の一つに、人間のレビューするテストが積みあがる点がある。
このため、複数のアプリで共通化できる処理や知識はDRY原則でまとめ、テストの数を減らしたい。
Cruxのようなクロスプラットフォームのフレームワークを用いることもその手段の1つである。

CruxでPetaJournalをクロスプラットフォーム対応したところ、Web、Emacs、iOS、Android、macOS、Windowsでおよそ問題なく動作している。
しかし、Cruxだけでは複数のネイティブプラットフォームのコードの共通化が十分にできないことに気づいた。

対象のアプリの画面は、IDで管理できる部品の並びが中心である。
PetaJournalの場合それは、アウトラインの行、サイドバーのページ、検索の結果である。
画像ビューアーとエクスプローラーでは、フォルダの中の項目、お気に入り、開いているウィンドウである。

対象のプラットフォームにはWinUI、AppKit、SwiftUIのようなネイティブのGUIが含まれる。
それぞれのプラットフォームは薄いシェルとして、コードを出来る限り共通化することが狙いである。


### PetaJournalの今の境界

Cruxを利用している。

ADR 024は、Cruxの`ViewModel`を描画のたびに丸ごとbincodeで通すと決めた。
差分は、シェルのUIの仕組みに任せた。
ADR 063は、変わっていないときだけ読み直しを飛ばす`view_if_changed()`を足した。

その結果、ネイティブのシェルで1文字打つと、次の4つが起きる。

1. コアが`view()`で`ViewModel`を丸ごと作る。
   全部の`Row`と、その`RichText`を含む。
2. `ViewModel`を丸ごとbincodeで書き、FFIを越える。
3. C#やSwiftが丸ごと読み、新しいオブジェクトを作る。
4. シェルが、作ったものと画面の行を、項目のIDで突き合わせて差分を探す。

4つとも、行の数に比例する。
変わったのは1行でも、全部の行を扱う。

4の突き合わせは、シェルごとに別々に書かれている。
WinUIは`StickyWindow.Sync`と`RowModel.Set`で、Emacsは`shell.rs`の10種類の`tell_*`で、手で比べる。
Leptosの`<For key>`、SwiftUIの`ForEach`、Composeのキーは、毎回新しい配列を受け取り、部品の仕組みで比べる。
同じ判断が6つのシェルに散っている。
これは、判断をコアに集めるという、ADR 052とADR 057の考えに反する。

### CruxのViewModelの考え方と合わない部分

Cruxはフレームワークである。
アプリは`App`トレイトの`update`と`view`を書き、それを`Core`が呼ぶ。
`ViewModel`は、形を問わない1つの値である。
`Render`は「何かが変わった」という合図だけを運ぶ。
どこが変わったかは、シェルが自分で調べることになる。
画面がIDつきの部品の並びで、シェルがネイティブのGUIのアプリでは、この調べる処理を、シェルの数だけ書くことになる。

Cruxは、エフェクトをシェルが実行する形を基本にしている。
シェル側をやや厚くすることで、コアを複数プラットフォームに対応させやすくするためである。

一方、PetaJournalのネイティブのシェルはなるべく薄くするポリシーに従って、コードを共通化してきた。
結果として共通する処理である`Api`、`Sse`、`Timer`を、
`client-native-bridge`がRustの中で実行している（ADR 024）。
このシェルでもコアでもない共通処理の層は、Cruxの概念にない。
残るシェルの責務は、`Render`、`Navigate`と、`Ui`の一部だけである。

現在のPetaJournalがcrux_core 0.20.0から使っている部分は、次のとおりである。

- `Command`の非同期のエフェクトの実行と、`Core`。
  `client-core`には、`async move`が70か所、`Command::all`が44か所、`send_event`が77か所ある。
- `EffectRouter`と、bincodeの境界。
  `client-native-bridge`だけが使う。
- 型の生成。
  Swiftの型だけが使う。

`middleware`、`capabilities`、`testing`は使っていない。
Cruxから実際に得ている価値は、ほぼ`Command`である。
`harness.rs`は`Command`のイベントとエフェクトを取り出し、サーバーの答えをその場で返す。
そのため、コアの振る舞いをサーバーなしで決定的に試せる利点がある（ADR 058）。
`harness.rs`自身は、Cruxの`testing`ではなく、PetaJournalが書いたものである。

### 現状の課題

#### PetaJournal

- 差分を取る判断が、6つのシェルに散っている。
- 1回のキーで、行の数に比例する処理が4段ある。
  ADR 063の時点では、1000項目でも1回の読み取りは数msだった。
  速さよりも、DRY違反のほうが問題である。
- サーバーの答えを`send_event`で`Event`に戻すため、`SplitDone`などの内部の変種が、シェルの型に出ている（#767）。
- 型の生成が2通りある。
  C#とKotlinの型は、Cruxに付いてくるfacet_generate 0.19ではコンパイルできない。
  このバージョンでは未修正のバグのためである。
  `client-native-bridge`の`codegen.rs`は、バグの修正された0.22.3を直接呼ぶ。
  結果として、Cruxの生成器を通るのはSwiftの型だけになってしまった。
  登録する型の一覧も2つある。
  C#では、生成されたファイルを書き換えている（`closed record`、.NETの版）。
- crux_coreを`=0.20.0`で固定している。
  Cruxは、0.19.0でミドルウェアを`EffectRouter`に置き換えたように、APIを変える。
  版を上げるたびに、型の生成の回避策も確かめ直すことになる。

#### GalleryExplorer

- Rustと`windows-reactor`（宣言的なWinUIのライブラリ、プレビュー版）で書いている。
- これは`windows-reactor`がどの程度使えるのかの試験を兼ねて制作した。
- 案の定、0.100.0には、キーのイベント、項目の仮想化、`ScrollViewer`のスクロール、`MenuFlyout`がない。
  そのため、Win32のフック、`StackPanel`、Tabキーを送る方法、Win32のメニューで補っている（GalleryExplorerのADR 001、ADR 002）。
- `windows-reactor`はWindowsでしか動かない。
- 画面に関わる判断は、すでに`explorer`と`domain`に分けてあり、テストできる。

#### sss-image-viewer

- JavaFXで書いている。
- 起動を速くするために、AOTとCDSを使っている。
- Windowsだけを対象にしている。

### 類似事例

| 事例 | 何を差分にするか | 差分を作る場所 | シェル |
|---|---|---|---|
| matrix-rust-sdk（`matrix-sdk-ui`、`eyeball-im`） | データのリスト（`VectorDiff`） | 同じプロセスのRust | Element XのSwiftUIとJetpack Compose |
| Hotwire（Turbo Streams） | IDを狙った`append`、`replace`、`remove` | サーバー | ブラウザ、Hotwire Native |
| Phoenix LiveView、LiveView Native | 画面のテンプレート | サーバー | ブラウザ、SwiftUI、Jetpack Compose |
| Redwood（Cash App） | 画面の部品の木 | 同じプロセスのKotlin | SwiftUI、UIKit、AndroidのView、DOM |
| Dioxus | 仮想DOM（Mutationの一覧） | 同じプロセスのRust | Web、デスクトップ、ターミナルなど |
| React Native（Fabric） | 画面の部品の木 | 同じプロセスのJavaScript | iOSとAndroidのネイティブの部品 |
| Crux | 差分は作らない。`ViewModel`を丸ごと渡す | なし | どれでもよい |

差分の単位は、2つに分かれる。
画面の部品の木を差分にするもの（LiveView、Redwood、Dioxus、Fabric）では、どの部品を置くかまでコアが決める。
データのリストを差分にするもの（matrix-rust-sdk、Turbo Streams）では、どう描くかはシェルが決める。
PetaJournalには、付箋紙、アウトライナー、Emacsのように、見た目がまったく違うシェルがある。
そのため、データのリストを差分にする形が合う。
いちばん近い手本は、matrix-rust-sdkである。
Rustのコアが通信と同期の判断を持ち、部屋の一覧やタイムラインを`VectorDiff`の流れとしてシェルへ渡している。

### この考え方に意味はあるか

議論の中で、開発者は次の疑問を出した。
Webの世界には、画面の作り方としてMVUかSignalsの二大潮流がある。
この考え方は、その中間に見える。
それでも、この考え方に意味はあるのか。

この疑問への答えは、次のとおりである。
この考え方は無意味ではない。
ただし、新しい発明でもない。
境界をまたぐときに現れる、すでに知られた形である。
Webで2択に見えるのは、Webのフロントエンドには、多くの場合この境界がないためである。

#### Webで2択になる理由

Webのフロントエンドでは、状態と画面が、同じ実行環境の同じ言語の中にある。
描く先は、DOMだけである。

- MVU（Elm、Redux、React）は、状態から画面を丸ごと作り直す。
  差分は、フレームワークが仮想DOMで取る。
- Signals（Solid、Leptos、Vue、Angular）は、値の依存関係を追う。
  変わった値に関わる所だけを直す。

どちらでも、差分をどこで取っても安い。
そのため、差分をどこで取るかは問題にならない。

#### 境界があると、中間の形が現れる

Webでも、境界があるところには、同じ中間の形が現れている。
サーバーとブラウザの間である。
Phoenix LiveView、Hotwire（Turbo Streams）、htmxがそうである。
サーバーは、MVUのように状態から画面を作る。
しかし、ブラウザへ送るのは、IDを指定した差分だけである。
境界を越える費用が高く、境界の向こうで差分を取り直したくないためである。
PetaJournalのFFIとbincodeの境界も、同じ立場にある。

#### ネイティブのGUIは、もともとこの形で話す

もう1つの理由は、ネイティブのGUIの側にある。
WinUIとWPFの`ObservableCollection`は、`INotifyCollectionChanged`で、`Add`、`Remove`、`Move`、`Replace`、`Reset`を知らせる。
SwiftUIの`@Observable`とComposeの`SnapshotStateList`は、変更を細かく追う仕組みで、Signalsに近い。
`INotifyCollectionChanged`の5つの知らせは、`eyeball-im`の`VectorDiff`とほぼ同じである。
つまり、この考え方は、ネイティブのGUIが最初から使っている言葉で、コア側も話すようにするものである。

#### この考え方の正体

この考え方は、次の3つの組み合わせで構成される。

- コアはMVUである。
  `update`は純粋で、`view`を作る。
  PetaJournalのテストのしやすさ（ADR 058）は、ここから来ている。
- シェルはSignalsである。
  ネイティブのGUIの、細かく変更を追う仕組みを使う。
- リストの差分を取ることは、2つをつなぐ通訳である。
  MVUの丸ごとの値を、Signalsの側の「変わった所だけ」に直す。
  この差分モジュールは、境界の手前の1か所にのみ置かれる。

この考え方が中間に見えるのは、MVUとSignalsの間にある境界を、共用の差分モジュールで埋めているためである。

#### 意味が薄くなる条件

次の場合は、この考え方の意味は薄くなる。

- コアと画面が同じ言語で、同じプロセスにあるとき。
  Leptosだけのアプリなら、Signalsで足りる。
  PetaJournalのLeptos版も、この考え方の効果がいちばん小さいシェルである。
- 行が少なく、シェルも1つのとき。
  丸ごと送って、画面の部品に比べさせれば十分である。
  ADR 063のとおり、1000項目でも1回の読み取りは数msである。

PetaJournalでの主な効果は、速さではない。
同じ突き合わせの判断を、6つのシェルから消すDRY違反の解消である。

## Decision

IDつきの部品の並びを中心にしたアプリのために、クロスプラットフォームの共用のRustライブラリを作る。
ただし、いきなり作らない。
次の順に、1つずつ進める。

### 言葉の定義

- **IDつきのリスト**：画面の部分のうち、長さに上限がなく、各項目がIDを持つもの。
  例は、PetaJournalの`ViewModel`の`outline.rows`、サイドバーのページの一覧、検索の結果、バックリンク、アトラスのカードである。
- **リストの差分**：IDつきのリストに対する、挿入、削除、移動、更新の操作の列。
- **パネル**：画面の部分のうち、形が決まっていて小さいもの。
  変わったときに丸ごと送る。
  例は、`ViewModel`の`calendar`、`config`、`connection`、`title`、`history`である。
- **共用ライブラリ**：リストの差分とパネルでコアとシェルの境界を作るための、Rustの部品の集まり。
  複数のアプリが使う。

### 特徴

- リストの差分モジュールが、IDつきのリストに対応する通訳である。
- パネルは、MVUと同じく、変わったときに丸ごと渡す。
  パネルが持つのは、表示の論理までである。
  たとえば`CalendarView`は、どの日をどの週に置くかを決めた`weeks`を持つ。
  全部のシェルで同じ答えになるべき判断のためである。
  どの部品で、どこに、どう描くかは、シェルが決める。
- リストとパネルを分ける基準は、変わり方である。
  項目ごとに入ったり、出たり、動いたりするものはリストにする。
  小さくて形が決まっていて、差分を取る手間に見合わないものはパネルにする。
- パネルは、変更を知らせる単位でもある。
  シェルは、変わったパネルだけを描き直せる。

### 進め方

1. **PetaJournalの差分の処理を共通にする。**
   リストの差分とパネルを、Rustの側で1回だけ作る。
   シェルは、受け取った差分を当てるだけにする。
   WinUIの`StickyWindow.Sync`のような、ネイティブのシェルごとの突き合わせをなくす。
   PetaJournalのリファクタリングは、いったんここで止める。
   Cruxを置き換えることや、#767の内部のイベントは、この段階では扱わない。
   この作業の前と後ろでベンチマークをとる。
2. EmacsとLeptosのシェルも差分を受け取る形に変えるかを、1の結果を見て考える。
   変えた場合のアーキテクチャの良し悪しと、ベンチマークが必要。
3. **sss-image-viewerを、WinUIとAppKitで作り直すための共用ライブラリを作る。**
   このとき、GalleryExplorerとPetaJournalでも使えることを念頭に置く。
4. **GalleryExplorerも、共用ライブラリで作り直す。**
5. **2つのアプリで共通にできたことを確かめてから、PetaJournalへの導入を検討する。**
6. **sss-image-viewerとGalleryExplorerを合体させたアプリなどは、その次に検討する。**

1を先にするのは、効果がPetaJournalのシェルのコードにすぐ表れるためである。
また、差分の境界の形を、いちばん大きなアプリで先に確かめられるためである。
共用ライブラリを、PetaJournalではなく画像ビューアーで先に作るのは、PetaJournalのコードが大きく、作り途中のライブラリを入れる危険が大きいためである。
使うアプリが2つそろうまで、共通の形は見えない。

### このADRで決めないこと（要検討）

実装の際に改めて比較検討したほうがよい。

**ライブラリかフレームワークか**

- フレームワークでは、フレームワークがアプリのコードを呼ぶ。
  Cruxはこちらである。
  ライブラリでは、アプリのコードがライブラリを呼ぶ。
- 議論では、部品はライブラリにし、フレームワークが提供するような組み立て済みの「標準のループ」を使うかどうかは選べる形で用意する案に傾いた。
  2つのアプリの形が違うことと、使うアプリが2つでは共通の形が見えないことが理由である。

**部品のつなぎ目**

- 非同期の処理が`Model`を変える方法。
  `async`の処理は、`&mut Model`を持ったまま待てない。
  Cruxのように答えを`Event`にして送り返すか、「`Model`をこう変える」関数をループに送るかを選ぶ。
  前者は#767の原因である。
  後者では、内部のイベントが要らなくなるが、テストで関数の中身は見られない。
  これが決まると、実行器の形が決まる。
- 1回分の処理がいつ終わったかを、ループがどう判断するか。
  差分は、1回分の処理にまとめて送る。
- どのスレッドでコアを動かすか。
  サーバーの答えやタイマーは別のスレッドから戻るので、メインスレッドへ渡す決まりが要る。

**差分の作り方**

- 毎回`view`を作って前回と比べるか、`Model`の中のリストを監視できる型にするか（`eyeball-im`の形）。
  前者では、毎回差分をとる必要がある一方、差分の部品は`Model`に何も求めない。
  後者では、変わった分だけ処理すれば済むが、`Model`が共用ライブラリの型に依存する。

**Cruxとの関係**

- 共用ライブラリをCruxの上に作るか、Cruxを置き換える自分のコアにするか。
  PetaJournalの`Command`と`harness.rs`の決定性は、どちらでも保つ必要がある。
  自分のコアは、実行器、要求と答えの対応、ルーター、境界で、2000行前後と見込んでいる。

**境界の形式と型の生成**

- facet_generateを、Cruxを通さずに直接呼ぶ形にそろえるか。
  PetaJournalでは、Swiftの型だけがCruxの生成器を通っている。
- リストの差分の型を、Swift、C#、Kotlinの型として生成できるか。

**シェルの技術**

- WindowsのシェルをC#のWinUIにするか、`windows-reactor`を続けるか。
  GalleryExplorerは`windows-reactor`の制約（キー、仮想化、スクロール、メニュー）に何度も当たっている。
  `windows-reactor`はプレビュー版であるが、開発自体は活発である。
  状況をみて決める。
  C#の問題は起動速度であるが、AOTで常に改善されつつはある。
- macOSで、AppKitとSwiftUIをどう使い分けるか。
  画像ビューアーの枠なしや全画面のウィンドウは、AppKitのほうが扱いやすい。
- LinuxをGTK4（gtk4-rs）にするか。
  Rustから`Core`を直接呼べるので、境界の形式が要らない。

**画像のアプリでの切り分け**

- 画像の画素は境界を越えさせず、コアはパスだけを渡す。
  表示用のデコードと描画は、WIC、ImageIO、GdkPixbufのようなOSの仕組みに任せる。
- ズーム、パン、ウィンドウのドラッグをシェルが持ち、残す値だけを操作の終わりにコアへ伝えるか。
- Rustで速くするのを、フォルダの読み取りと並べ替え、EXIFの読み取り、サムネイルの生成とキャッシュ、前後の画像の先読みの判断に絞るか。

**その他**

- 共用ライブラリを置くリポジトリと、その名前は、misoを予定。蟹味噌とシェルの関係。


## Alternatives

### Alternative 1: CruxとADR 024の形を続ける

`ViewModel`を丸ごと通し、差分はシェルに任せる。
新しく作るものはない。
しかし、差分の判断は6つのシェルに散ったままである。
シェルやアプリを足すたびに、同じ突き合わせを書くことになる。
そのため、選ばなかった。

### Alternative 2: PetaJournalの中だけで差分を作る

進め方の1だけを行い、共用ライブラリは作らない。
作業は最も少ない。
しかし、sss-image-viewerとGalleryExplorerでは、同じ仕組みをもう一度作ることになる。
そのため、最終の形としては選ばなかった。
1の段階は、この案と同じである。

### Alternative 3: 共用ライブラリを先に作り、すぐPetaJournalに入れる

PetaJournalを最初の利用者にする。
いちばん大きなアプリで、すぐに効果を確かめられる。
しかし、PetaJournalのコアは約2.7万行あり、作り途中のライブラリに合わせて変えると、壊したときの費用が大きい。
使うアプリが1つでは、共通の形も見えない。
そのため、選ばなかった。

### Alternative 4: 既存のフレームワークを使う

Dioxus、Redwood、LiveView Nativeは、画面の部品の木を差分にする。
どの部品を置くかまでコアが決めるので、見た目がまったく違うシェルを持てない。
Redwoodはコアの言語がKotlinで、LiveView NativeはElixirのサーバーが要る。
matrix-rust-sdkの`eyeball-im`は、リストの差分の部品だけで、ループやエフェクトの実行は含まない。
そのため、全体としては選ばなかった。
`eyeball-im`は、共用ライブラリの部品の候補として残す。

### Alternative 5: RustだけのGUIで書く

Slint、egui、DioxusのネイティブのレンダラーなどのRustのGUIで、すべてのプラットフォームの画面を書く。
境界がなくなり、言語も1つになる。
しかし、ネイティブのGUIを使いたいという目的に反する。
OSのIME、ネイティブイベントへの対応、アクセシビリティ、見た目に合わせる作業も、自分で負うことになる。
そのため、選ばなかった。

## Confidence Level

進め方の順番には、確信がある。
小さく始めて、2つのアプリで共通の形を確かめてから広げるためである。
共用ライブラリの形には、確信がない。
ライブラリかフレームワークか、非同期の処理が`Model`を変える方法、Cruxとの関係は、まだ決まっていない。

次のときは、このADRを見直す。

- 1の作業で、差分を共通にしても、シェルのコードがほとんど減らないと分かったとき。
- Cruxが、差分を作る仕組みや、内部のイベントを隠す仕組みを持ったとき。
- sss-image-viewerやGalleryExplorerの画面が、IDつきのリストとパネルに分けられないと分かったとき。
- `windows-reactor`が、キーのイベントや仮想化を持ち、プレビューでなくなったとき。
- 3つめのアプリが加わり、フレームワークにする根拠ができたとき。

## Consequences

### 良い結果

- 差分の判断が、Rustの1か所に集まる。
  シェルは、差分を当てる処理とパネルを差し替える処理だけを持つ。
- ネイティブのシェルで1回のキーごとに扱うデータが、変わった行の分だけになる。
- 共用ライブラリができれば、3つのアプリが同じ境界の作り方を使える。
- sss-image-viewerは、JavaFXのAOTとCDSの工夫に頼らずに、速く起動できるようになる。
- GalleryExplorerは、`windows-reactor`の制約から抜けられる可能性がある。

### 悪い結果

- 1の段階で、PetaJournalには、Crux、`EffectRouter`、自前の差分の仕組みが重なる。
  5の段階まで、この重なりは残る。
- #767の内部のイベントと、型の生成の二重化は、5の段階まで残る。
- 共用ライブラリを、複数のリポジトリで保守することになる。
- 3と4の段階では、PetaJournalの開発の時間が、ほかのアプリに回る。

### 中立的な結果

- ADR 024の「`ViewModel`を丸ごと通す」決定とADR 063は、1の作業で置き換わる。
  そのときに、新しいADRで記録する。
- 共用ライブラリの形を決めるときに、このADRの「このADRで決めないこと」が、次のADRのContextになる。
