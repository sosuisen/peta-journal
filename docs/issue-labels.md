# issueのラベル

GitHub Issuesのissueには、この一覧から選んだラベルを付ける。
issueで作業を管理すること自体は、ADR 066で決めた。

ラベルは、次の3つの軸で付ける。

- 種類：作業の種類を付ける。
- 場所：作業がまたがるスコープのすべてに付ける。
- 条件：当てはまるときだけ付ける。

新しいラベルが必要と考えられる場合は、ユーザーに尋ねること。

## 種類

| ラベル | 付けるissue |
|-------|------------|
| `bug` | 誤った振る舞いを直す |
| `feature` | 新しくできることが増える |
| `usability` | 同じことがより楽になる |
| `investigation` | 調べて、結果をまとめる |
| `verification` | 検証の仕組みを入れる。lintなどの静的解析、自動テストなどの動的解析、ランタイム検証、形式検証、その他の検証の仕組みである |
| `refactor` | 振る舞いを変えずにコードを直す |
| `dedup` | 重複したコードや決まりを、1か所にまとめる |
| `ci` | CIの設定やスクリプトを直す |
| `chore` | 上記に当てはまらない雑務 |

`feature`を選ぶ場合は、`docs/storymap-*.md`への追加が検討されるべきである。
追加された場合、追加済みの`docs/storymap-*.md`へのリンクを書き、追加されなかった場合は、storymap未追加と書く必要がある。

`feature`と`usability`は、できることが増えるかどうかで分ける。
できることが同じまま、操作や見え方が楽になるだけなら、`usability`を付ける。
`usability`のissueは、`docs/storymap-*.md`への追加を検討しなくてよい。

`dedup`を付けたissueには、`refactor`を付けない。
`dedup`は`refactor`の一部だが、別のラベルにして探しやすくしている。

`dedup`を分けている理由は、このプロジェクトがクロスプラットフォームの開発だからである。
同じ機能を、Web、Emacs、iOS、Android、macOS、Windowsのシェルで作っている。
シェルごとに同じ処理を書くと、片方だけが変わり、振る舞いが食い違う。
そのため、共通の部分をRustのコアや共有のライブラリに集めることに注目している。

コミットメッセージの種類は、`dedup`のissueでも`refactor`にする。
`dedup`は、Conventional Commitsの種類ではないためである。

## 場所

場所のラベルは、`docs/conventional-commit.md`のスコープと同じ名前にする。

スコープが4つ以上になっても、省略しない。
コミットのスコープを省略する規則は、ラベルには当てはめない。
ラベルは、場所ごとにissueを探すために使うためである。

## 条件

| ラベル | 付けるissue |
|-------|------------|
| `needs-device` | 実機が要る作業 |
| `needs-developer` | 開発者がいるときに行う作業 |
| `env:macos` | OS共通のコードなのに、macOSでだけ起きる問題 |
| `env:windows` | OS共通のコードなのに、Windowsでだけ起きる問題 |

`needs-developer`は、たとえば、キーとマウスを使う画面のテストや、開発者が先に手で後片付けをする作業に付ける。
