検証の仕組み

この文書は、peta-journalのコードを、何で、どこで確かめるかをまとめる。

更新日：2026-11-24

方針

  • 検証は手元でもCIでも同じ道具で回す。
    CIでは整形せず、未整形のファイルがあれば失敗させる。
  • CIでは、ミューテーションテストだけは回さない。PRの前に、手元で回す。
  • 守らせたい決まりは、ビルドかテストを失敗させる形にする。
    人間がレビューで見るのは、道具で守らせられない部分だけである。
  • 個々の検証ツールの方針は、verificationスキルを参照。

シェルがコアを通っているかのチェック（shell-check）

ADR 064の静的なチェックは、client/tools/shell-checkにある。
できたチェックから順に、clientのcargo testで回す（ADR 064の2026-11-24の追記）。
見つかれば、手元でもCIでもテストが落ちる。

S2は、rules/にルールのファイルがあるシェルを、すべて調べる。
シェルを足すときは、mainで何も出ない状態にしてから、ルールのファイルを置く。

手元だけで回すもの

次のテストは、CIでは回さない。
PRの前に、変えた範囲に関わるものを手元で回す。

  • stickies-winの画面のテスト（PetaScreens.Tests）。
    本物のマウスとキーを使うので、回す前に開発者に確かめる。
    回している間、開発者はPCに触れない。
  • outliner-reactのe2e（Playwright）。
    テスト用のサーバーを一時フォルダで起こすので、開発者のノートには触れない。
  • stickies-macとoutliner-iosのビルドとテスト。
    macOSでしか回せない。
    Windowsで変えたときは、issueのチェックボックスに残す。
  • outliner-androidの画面のテスト。
    エミュレーター（Medium_Phone_API_35）で回す。

方針に足りないところ

2026-11-24の時点で、次の点が方針に届いていない。

  • カバレッジの9割を、Rust（journal、client、atlas）とtodoのほかは、ビルドで確かめていない（#1078）。
    npm run coverageは数字を出すだけで、失敗させない。
  • カバレッジを測る設定がないモジュールがある（C#、Swift、Kotlin）。
  • CIに入っていないモジュールがある（outliner-react、stickies-win、stickies-mac、outliner-ios、outliner-android）。
    これらの整形の確かめは、手元でしか行われていない。
