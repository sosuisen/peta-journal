# フォルダ同期の将来の課題

2026-11-03に話し合った、Markdownフォルダ同期の品質を上げる案。まだ着手していない。狙いは「トランザクションや難しい手順なしで、Markdownファイルを介して2台のPCを合わせる」ことなので、その中で少ないコードで効くものだけを挙げる。いまの仕組みは[folder-sync-journeys.md](folder-sync-journeys.md)を見ること。

## いまの仕組みのどこが強く、どこが弱いか

構造の面では、すでに両側が同じ規則で同じ結果に収束する設計になっている。ページと項目のidがファイルに入る。`idx`は分数添字である。同じパスの2ページは古いidが勝つと両PCが同じ判定をする。タグはファイルとDBの和集合を取る。これはCRDTが「収束」と呼ぶ性質そのものである。

弱いのは、項目の本文の合流である。競合の判定はページ単位の`modified`で行う（`import_service.rs`）。ファイルが新しければ、ファイルの項目でDBの項目を丸ごと置き換える。DBが新しければ、ファイルを`.conflict`に退避してDBで上書きする。そのため、PC Aが項目Xを、PC Bが同じページの項目Yを編集すると、Dropboxが片方のファイルを正にし、負けた側の編集はDBから消える。残るのはDropboxの「conflicted copy」と`.conflict`のファイルだけで、人が拾い直すことになる。

## 候補（効果の大きい順）

### 1. 項目ごとのLast-Writer-Wins

メタデータ行に`modified`を1つ足し、`ItemMerger`で項目ごとに「ファイルとDBの新しい方」を採る。CRDTのLWWレジスタを項目単位に置く形である。書き出しに属性1つ、読み込みに属性1つ、合流に比較1つの追加で済む。同じページの別の項目を2台で編集しても、両方が残る。

2026-11-05に実装した。規則は次のとおりである。

- 両方にある項目は、`modified`の新しい方を採る。同じなら、ファイルを採る。
- DBだけにある項目は、次のどちらかなら残す。ファイルのページの`modified`より新しい。前回の同期より新しい（まだどのファイルにも書いていないので、相手が消せない）。それ以外は、向こうで消した項目として消す。
- ファイルだけにある項目は足す。ただし、ユーザーがここで、項目の`modified`より後に消した項目は足さない。消した項目は、DBの`deleted_items`に日時とともに記録する。ファイルが古く、項目がすでに別のページへ動いているときも足さない。
- `deleted_items`と、前回の同期との比較は、話し合いの案にはなかった。案のままでは、2台が同時に足した項目のうち、先に足した方が消えるためである。日付の比較だけでは「まだ見ていない項目」と「ここで消した項目」を見分けられない。前回の同期には、このPCがそのページのファイルを最後に書いたか取り込んだときの、ファイルの更新時刻を使う。
- 手で編集したファイルは、項目の`modified`が変わらないまま中身だけが違う。この項目はファイルを採り、`modified`を今の時刻にし、すぐに書き戻す。
- `modified`のない古い形のファイルでは、ファイルのページの`modified`を、すべての項目の日付として扱う。
- アトラスは今までどおりページ単位で決める。各PCが自分のページから書くため、項目の日付を持たせるとファイルが揃わない。
- 負けたファイルは、前回の同期より後の変更を失うときだけ、`.conflict`に残す。ファイルがこのPCの前回の同期より新しくないときも残す。手元の古い内容から手で編集したファイルだからである。

残る隙間は1つある。Bが足して書き出した項目が、それより後にAが書いたファイルで消えることがある（AがBのファイルを見ずに書いた場合）。Dropboxでは、このときどちらかの版がconflicted copyになるので、案2で拾う。

### 2. Dropboxのconflicted copyを合流の入力にする

1ができれば、conflicted copyは「もう1つの版」として同じ規則で合流でき、合流後に消せる。負けた側の編集が自動で戻る。`path_mapper`でファイル名の形（`name (PC名's conflicted copy 日付).md`）を見分ける処理が要る。

### 3. `idx`が衝突したときの決め方

2台が同じ隙間に同時に挿入すると同じ`idx`になり、いまは順序の食い違いとして計算し直している。`idx`が同じなら項目idの順で並べる、と決めておけば両側が同じ順に収束する。小さな変更である。

## 勧めないもの

AutomergeやYrsのような本物のCRDTは勧めない。操作の履歴や各デバイスの状態ベクトルをバイナリで持つ必要があり、Markdownファイルは正本ではなく投影になる。上の狙いから外れる。

## ハイブリッド論理時計（HLC）

1は壁時計の比較なので、2台の時計のずれに弱い。ただしHMTIDがすでに時刻順を前提にしているので、新しい前提ではない。時計のずれで編集が消えた、と実際に困ってから検討する。

HLCは、壁時計の部分と論理カウンタの部分を持つタイムスタンプである。自分で変更を作るときは、壁時計が持っている値より進んでいればそれを採ってカウンタを0にし、進んでいなければ持っている値のままカウンタを＋1する。相手の値を受け取ったときは、自分の壁時計、自分の持っている値、相手の値の最大を採り、相手の値が最大なら相手のカウンタ＋1にする。これで「見てから直した」変更は必ず見た変更より大きな値になり、壁時計の部分は実際の時刻から大きくは離れず、人が読める。

PetaJournalに置くなら、項目の`modified`をHLCにし、ファイルを取り込むたびにファイルの中で一番大きい`modified`で自分の時計を進める。壁時計の部分はいまの`modified`と同じ形で書け、カウンタはその後ろに小さな数を1つ足すだけである。

HLCが守るのは「見てから直した」順序だけである。2台が互いの変更を見ずに同じ項目を直したら、それは本当の同時編集で、HLCでも片方を選ぶしかない。その場合は`.conflict`に退避するいまの扱いが正しい。

## 項目の順序（`idx`）と振り直し

2026-11-03に`fractional_index.rs`を調べ、次が分かった。末尾に足すと31個ごとに1文字伸びる。隣り合う2つの間に続けて入れると1個ごとに1文字伸びる。先頭に入れ続けると62回目で`panic`する。実機のDBでは最長69文字、20文字より長い項目が1369あった。振り直しは「隙間が作れなかったとき」にしか走らず、いまの`midpoint`は文字を足せばいつでも隙間を作れるので、実際にはほぼ走らない。

直し方は次のとおり。

- アルゴリズムは、rocicorpの`fractional-indexing`と同じ規則にする。整数部と小数部を分け、整数部の長さを先頭の文字で表し、末尾の`0`を禁じ、中点は残りの全桁で取る。末尾に足しても桁数は対数でしか伸びず、同じ隙間に入れても約6個ごとに1文字で済む。
- 隙間が作れないときは`panic`せず`NoGap`を返し、呼び出し側が振り直す。古い形の`idx`（`z0`など）は新しい規則では不正な値なので、同じく`NoGap`になり、そのページは振り直される。これで古い`idx`は使われたときに自然に消える。
- 振り直しは長さで決める。作った`idx`が16文字を超えたら振り直す。16文字は、同じ隙間に約80個を続けて入れたときの長さで、振り直し後は2〜3文字に戻る。

項目単位の同期を見据えて、振り直しは次の4つを守る。

1. **`modified`を変えない。** `idx`の変更は順序の変更であって、項目の変更ではない。振り直しが`modified`を進めると、相手のPCの同時の編集にすべて勝ってしまう。
2. **順序は`idx`の値ではなく並びで合流する。** 相手の`idx`は振り直す前の古い値かもしれない。`order_planner`のように、ファイルの並びを正とし、最長増加部分列を残して残りを計算し直す。
3. **決定的にする。** 同じ並びなら同じ`idx`になるようにし、両方のPCが振り直しても同じ値に収束するようにする。
4. **範囲を隙間の周りに絞る。** 閾値を超えた項目の前後で`idx`の短い項目を錨として探し、その間だけを振り直す。長くなるのは同じ隙間に続けて入れた一続きなので、変わるのはその一続きだけで、相手と衝突する範囲が縮む。

同時挿入の決め方も合わせて決める。2台が同じ隙間に同時に入れると同じ`idx`になる。「`idx`が同じなら項目idの順」と決めれば両側が計算なしで同じ順に収束するが、`(page_id, idx)`のUNIQUE制約を`(page_id, idx, id)`に緩めるか外すかの判断が要る。

## 進め方

1から始める。合流のテストは、2台のデバイスの形（`journal-server-rust/crates/server/tests/it/atlas_sync.rs`）で書く。`idx`の直しは、`panic`を止める変更、アルゴリズムの置き換え、長さによる振り直しの順で、同期の話より先に進めてよい。
